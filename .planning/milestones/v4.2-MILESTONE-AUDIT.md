### ❌ BLOCKER — DEPLOY-03 / PII-01 seam

- **From:** Phase 32 PII-01 — added `/api/snapshot` to `PII_GET_ROUTES` (`server.js:422`), mounts `requirePiiApiKey` (`server.js:429`).
- **To:** Phase 33 DEPLOY-03 — `update-snapshot.yml` lines 46-48 fetch `GET /api/snapshot` with **no `x-api-key` header**.
- **Failure mode:** P32 is already live in production (deployed by P33's first gated deploy, commit `04c09d9`). The next nightly run gets HTTP 403, trips `exit 1`, and the production snapshot goes stale — exactly the staleness DEPLOY-03 was meant to fix.
- **Why every phase still passed:** P33's DEPLOY-03 UAT checked a snapshot `generated_at 2026-06-18T10:00:31Z`, generated *before* the P32 hardening deploy landed. The break is only observable on the next scheduled run.

**Fix:** Add `MW_API_KEY` (= Railway `API_SECRET_KEY`) as a GitHub Actions secret on `koa-inn/steins-and-vines-staging`, then add `-H "x-api-key: ${{ secrets.MW_API_KEY }}"` to the curl in `update-snapshot.yml`. A regression check (assert the workflow sends the header, or a smoke test that the live snapshot is < 25h old after P32) would prevent silent recurrence.
