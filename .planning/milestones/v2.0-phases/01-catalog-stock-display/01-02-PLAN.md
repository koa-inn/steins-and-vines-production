```javascript
  // Stock overflow warning — fires when cart qty would exceed stock_on_hand (D-01, D-02, D-03)
  function kioskCheckStockOverflow(product, newQty) {
    var stock = parseFloat(product.stock_on_hand) || 0;
    var isService = (product.product_type || '').toLowerCase() === 'service';
    // Skip: services have no stock tracking, weight items are bulk, out-of-stock handled elsewhere (D-04)
    if (isService || kioskIsWeightItem(product) || stock <= 0) return true;
    if (newQty > stock) {
      var name = product.name || 'This item';
      return confirm('"' + name + '" — only ' + stock + ' in stock, cart would have ' + newQty + '. Add anyway?');
    }
    return true;
  }
```

Key design decisions in this helper:
- `stock <= 0` returns true (skip) because the existing out-of-stock confirm at lines 1117-1118 already handles this case (D-04)
- `kioskIsWeightItem(product)` returns true (skip) because weight items are bulk ingredients where Zoho stock may not be precise (Assumption A1 from RESEARCH.md)
- `isService` returns true (skip) because services have no physical stock
- Uses em dash (—) in the confirm message for visual consistency with the D-02 pattern
- Returns boolean: true = proceed, false = user cancelled

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Zoho API -> kiosk frontend | stock_on_hand and product.name from Zoho could contain any value |
| Client-side cart -> server-side sale | Cart quantities are client-side state; server validates at Zoho invoice creation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03 | Tampering | kioskCheckStockOverflow client-side bypass | accept | The overflow check is advisory only (D-03 explicitly allows override). Server-side Zoho invoice creation is the authoritative gate for stock validation. A user bypassing the client-side confirm has the same effect as clicking OK -- both result in the sale proceeding to server-side processing. |
| T-01-04 | Tampering | product.name in confirm dialog | mitigate | `confirm()` is a native browser dialog that does not interpret HTML -- XSS via product name is not possible in the confirm string. DOM rendering paths already use `escapeHTML()`. |
| T-01-05 | Information Disclosure | stock_on_hand in confirm dialog | accept | Stock levels are already visible on product cards in the kiosk UI. Showing them in the confirm dialog does not expose new information. |
</threat_model>
