Replace the existing `loadSession` with a version that returns email even when token is expired, but only within 7 days:
```javascript
function loadSession() {
  try {
    var raw = localStorage.getItem(SESSION_KEY);
    if (!raw) return null;
    var data = JSON.parse(raw);
    var sevenDays = 7 * 24 * 60 * 60 * 1000;
    if (data.login_at && (Date.now() - data.login_at > sevenDays)) {
      localStorage.removeItem(SESSION_KEY);
      return null;
    }
    var tokenValid = data.expires_at > Date.now() + 5 * 60 * 1000;
    return { email: data.email, token: tokenValid ? data.token : null, expires_at: data.expires_at, tokenValid: tokenValid };
  } catch (e) { return null; }
}
```

`clearSession` remains unchanged -- it removes the entire localStorage entry (used on explicit sign-out).

**Change 3: Add `tryRefreshToken` function** (after `showSignInButton`, before `onTokenResponse`). This is the single entry point for ALL refresh paths per AUTH-03. It checks both `_refreshInFlight` and `_handlingUnauthorized` before calling `requestAccessToken`:
```javascript
function tryRefreshToken() {
  if (_refreshInFlight || _handlingUnauthorized) return;
  var session = loadSession();
  var email = (session && session.email) || userEmail || '';
  if (!tokenClient) return;
  _refreshInFlight = true;
  var dot = document.getElementById('bp-auth-dot');
  if (dot) { dot.className = 'bp-auth-dot bp-auth-dot--refreshing'; dot.title = 'Refreshing session...'; }
  try {
    tokenClient.requestAccessToken({ prompt: '', login_hint: email });
  } catch (err) {
    _refreshInFlight = false;
    if (dot) { dot.className = 'bp-auth-dot bp-auth-dot--offline'; dot.title = 'Not signed in'; }
    handleUnauthorized();
  }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser localStorage | Session metadata (email, login_at, token expiry) stored client-side; accessible to XSS |
| Browser -> Google OAuth | requestAccessToken popup crosses to Google's auth server |
| Browser -> Apps Script | checkAuthorization() validates token server-side after every refresh |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Information Disclosure | localStorage `sv-brewpad-session` with email + login_at | accept | Email is not sensitive PII in this context (staff email already visible in UI). Token expires in 1 hour. No new data exposed beyond existing pattern. |
| T-05-02 | Spoofing | Forged `sv-brewpad-session` with fake email for login_hint | mitigate | `login_hint` only pre-fills the Google account selector -- it does NOT bypass authentication. `checkAuthorization()` call in `onTokenResponse` validates the actual token against Apps Script. Forged email cannot grant access. |
| T-05-03 | Denial of Service | Rapid visibilitychange events triggering repeated tryRefreshToken | mitigate | `_refreshInFlight` mutex prevents concurrent calls. Only one requestAccessToken can be in flight at any time. Subsequent triggers are no-ops until the mutex clears. |
| T-05-04 | Elevation of Privilege | Stale token used during refresh window | mitigate | Server (Apps Script) rejects expired tokens with 401-equivalent. `isUnauthorizedError()` on every API response triggers `handleUnauthorized()`. No client-side token validation bypass. |
| T-05-05 | Tampering | Modified `_refreshInFlight` via browser console | accept | In-memory variable in IIFE scope. Attacker with console access already has full control. No escalation path beyond what's already available. |
</threat_model>
