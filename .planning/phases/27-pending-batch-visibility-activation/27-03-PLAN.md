<objective>
Add the guided "Schedule & Activate" flow (BATCH-03): a dedicated modal that lets staff pick a fermentation schedule template (with live preview), a start date, and an optional vessel/location, then promotes the pending batch to Primary in a single confirmed step — generating the schedule's tasks and honoring the chosen start date. Also fix the backend footgun where the pending→active transition always stamps the date as "now".

Purpose: Pending batches are created with no schedule and no tasks. When a batch needs a real schedule and/or a non-today start date, one-click activation is wrong. This flow assigns the schedule (creating tasks) and sets the correct start date in one step.
Output: A Schedule & Activate modal reachable inline and from the detail modal, a single-step promote orchestration, and a backend fix so the chosen start date drives fermentation_started_at and task due dates.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-06 | Tampering | New 'start_date' allowedField in update_batch | mitigate | start_date is written through the existing allowedFields loop which applies sanitizeInput; the value is a date string from a native <input type="date">, and updateBatchSchedule normalizes it via toDateOnly before computing due dates, so malformed input degrades to a no-op date, not code execution |
| T-27-07 | Tampering | Two-step promote (update_batch then update_batch_schedule) with chained version | mitigate | Each call passes expectedVersion (the second uses the newVersion returned by the first); the backend optimistic-lock checks (adminApi.gs:2090, 2285) reject stale writes with version_conflict, preventing a concurrent edit from corrupting the half-promoted batch |
| T-27-08 | Denial of Service / data integrity | Step 1 succeeds, Step 2 (schedule) fails — batch left active with no tasks | accept | Surfaced to the operator via an explicit toast directing them to assign the schedule from the detail modal; the state (active, no tasks) is identical to a one-click activation, which is a supported state — no data corruption |
| T-27-09 | Input validation | schedule_snapshot array built client-side | mitigate | The array is built from server-provided template steps (fermSchedulesData), not free user text; updateBatchSchedule sanitizeInputs each step title/description on write |
| T-27-SC | Tampering | npm/pip/cargo installs | accept | No new package installs — existing build toolchain only |
</threat_model>
