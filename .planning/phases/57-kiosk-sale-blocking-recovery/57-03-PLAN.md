<objective>
Fix the CONFIRMED cause from `57-DIAGNOSIS.md` (branch h5-stale-catalog, variant 2 — the captured case): a long-open iPad presents a STALE client catalog containing a phantom item (`1099000000000109115`) that no longer exists in Zoho. Staff add it; the server's price-anchoring guard correctly hard-rejects the sale (400); the only recovery today is a manual "Refresh the product list".

This plan makes the CLIENT catalog self-heal so the phantom is never presented, and blocks a stale cart line before the sale POST — without ever trusting client-supplied rates and without weakening the server guard. It also folds in the two `57-DIAGNOSIS.md` beacon findings' CLIENT halves so this failure class is observable unattended next time.

Purpose: Satisfy Phase 57 SC#3 (confirmed cause fixed, RED-first) — the client half.
Output: A RED-first client freshness fix + pre-checkout phantom guard + beacon extension + rebuilt artifacts.

## Fix design (why this branch, why client-side)
- 57-DIAGNOSIS.md confirmed the item does NOT exist in Zoho (`get_item` → "not available"; 19 digits vs the usual ~18). A server rebuild will STILL not find it, so a server-only fix cannot heal the CAPTURED case. What heals it is client catalog freshness. See 57-04 for the server-side auto-reconcile that covers the OTHER variant (a current item missing from a stale SERVER cache).
- Today `kioskLoadProducts` only re-fetches when `!_kioskProductsLoaded` (line 814), and `kioskRetryStalledLoads` (886) only fires for a catalog that never loaded. A long-open, successfully-loaded catalog is NEVER refreshed → phantoms persist indefinitely. That is the gap this plan closes.
</objective>
