<objective>
Instrument the kiosk so a failure is captured to a durable sink BEFORE staff tap Retry and it vanishes. This is the prerequisite for the whole phase: today the catch at `kiosk-core.js:801-811` paints `'Failed to load products: ' + err.message` on screen and the exact error (text, HTTP status, which endpoint, auth state) is lost the instant the grid is cleared. There is ZERO frontend error capture anywhere (verified 2026-07-15).

This plan is fully specifiable now — it does NOT guess the root cause. It builds the lens (57-02 looks through it, 57-03 fixes what it reveals).

Purpose: Satisfy Success Criterion #1 — a kiosk-side failure is reported to a durable sink with real error text, HTTP status, endpoint, and auth state.
Output: An ES5 client-error beacon in `kiosk-core.js`, a device-token-gated + rate-limited `POST /api/kiosk/client-error` endpoint that scrubs and durably captures the report via the existing Sentry path, and regression tests on both sides.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| kiosk browser → prod middleware | The staff iPad runs on the shop floor; its requests are untrusted client input. The device token is a shared kiosk secret (low individual trust). The new `/api/kiosk/client-error` route accepts client-authored strings. |
| middleware → Sentry / logs | Scrubbed client strings flow into durable, human-read sinks (log-injection + PII-retention surface). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-57-01 | Information Disclosure | beacon payload (client + server) | mitigate | Frontend whitelists exactly six fields (never token value, card number, or customer record); auth_state is a LABEL not the token. Server re-validates the whitelist, drops all extra fields, and redacts any 13-19 digit run (potential PAN) before capture/log. #1 threat. |
| T-57-02 | Tampering (log injection) | POST /api/kiosk/client-error message | mitigate | Strip CR/LF and control chars and truncate to 500 chars before the string reaches log.warn or captureExceptionSafe. |
| T-57-03 | Denial of Service | POST /api/kiosk/client-error | mitigate | Device-token gate (KIOSK_ROUTES allowlist) + dedicated clientErrorLimiter (60s window, max 20, Redis store) + express.json 1mb cap + per-field length caps, so the endpoint cannot be spammed to flood Sentry or Redis. |
| T-57-04 | Elevation of Privilege | authTiers KIOSK_ROUTES | mitigate | Endpoint added to the EXPLICIT exact-path allowlist only; it returns 204 with no body and performs no money/data side-effects, so a leaked device token can at most write scrubbed telemetry. |
| T-57-05 | Repudiation | Sentry capture | mitigate | Capture tags source='kiosk-client' + endpoint + http_status + auth_state so a captured occurrence is attributable and diagnosable in 57-02. |
| T-57-SC | Tampering (supply chain) | npm installs | accept | No new packages — reuses already-vetted express-rate-limit and @sentry/node. No install step in this plan. |
</threat_model>
