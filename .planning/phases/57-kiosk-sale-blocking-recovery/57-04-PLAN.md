<objective>
Add the SERVER-side safety net for the OTHER staleness variant identified in `57-DIAGNOSIS.md` ("CRITICAL design nuance", variant 1): an item that DOES still exist in Zoho but is missing from the middleware's stale catalog cache. Today the price-anchoring guard (pos.js:324-333) hard-rejects it and staff must manually refresh. This plan makes the SERVER auto-reconcile — on a catalog-miss it forces ONE bounded rebuild (the same `?bust` mechanism the manual refresh uses) and re-checks before rejecting — so a current-but-uncached item self-heals, while a genuinely-invalid/phantom item still (correctly) rejects.

It also lands the SERVER half of 57-DIAGNOSIS's beacon finding 2: accept and store a validated Zoho-shaped `item_id` un-redacted, so the 13-19-digit PAN redaction no longer destroys the one field that made the diagnosis possible.

Purpose: Satisfy Phase 57 SC#3 (confirmed cause fixed) — the server safety-net half, and make the failure observable.
Output: A RED-first bounded auto-reconcile + un-redacted structured item_id in client-error logging.

## Fix design (why bounded, why price-anchoring stays)
- The manual "Refresh the product list" works because it rebuilds the catalog via `/api/kiosk/products?bust=1` (catalog.js:800-817: `cache.del` → cold Zoho refetch → `cache.set`). Auto-reconcile reuses EXACTLY that rebuild, once, server-side, on a miss.
- This does NOT fix the CAPTURED case (a phantom that isn't in Zoho at all — a rebuild still won't find it); that is 57-03's client fix. This is the complementary safety net for variant 1, and it is the ONLY case a server change can heal.
- Non-negotiable: the guard still rejects an item absent after rebuild; client rates are still ignored. The rebuild is bounded to one per sale attempt (a local guard) so a persistent miss cannot stampede Zoho.

## Deployment reality
There is NO staging middleware — this deploys straight to the PROD Railway instance (57-05). It touches the money path (the sale route), so it is planned as the SAFETY NET and should go live only after 57-03's client fix is verified. Keep the change tightly scoped and reversible.
</objective>

| T-57-04-02 | Denial of Service | rebuild-on-miss | mitigate (single-sale) / accept (cross-request) | One-shot local guard: `rebuildKioskCatalog` runs at most once **per sale attempt** (Test C) — no hot loop within a single `processSale`. **Residual, accepted:** this is a per-invocation guard, NOT a global in-flight-rebuild coalescing lock, so N concurrent sales missing an item would each trigger their own rebuild.
