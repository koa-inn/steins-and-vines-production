# Phase 27.1: Code Review Report

**Reviewed:** 2026-06-11T15:09:38Z
**Depth:** standard
**Files Reviewed:** 2
**Status:** fixed (all Critical + Warning findings resolved; Info findings IN-01/IN-02 out of fix scope)

## Summary

Phase 27.1 adds inline "Delete" buttons for pending batches in two places: the admin Batches list (`js/admin.js`, `renderBatchList`) and the BrewPad "Needs Scheduling" dashboard rows (`js/brewpad.js`, `renderDashboard` + delegated handler in `initDelegation`). Both wire a confirm dialog (`showConfirm` / `showConfirmSheet`) to `adminApiPost('delete_batch', ...)`.

The wiring is mostly sound (event delegation in BrewPad, per-element listeners in admin, `e.stopPropagation()` to avoid row-open in admin, confirm-before-destroy on both, button disable + re-enable on error). However, there is one **BLOCKER**: the admin-side button injects customer-controlled values (`product_name`, `customer_name`) into HTML attributes using an `escapeHTML` implementation that does **not** escape double-quotes, producing a stored/attribute-injection XSS sink in the admin panel. There is also a real correctness bug: the BrewPad delete refreshes the *batches* tab data but never refreshes the *dashboard* it is rendered on, so a just-deleted row stays visible and re-clickable.

## Critical Issues

### CR-01: Attribute-injection XSS in admin inline Delete button (escapeHTML does not escape `"`)

**Status:** Fixed in 45c176a — admin `escapeHTML` replaced with a quote-safe replace-chain (escapes `&`, `<`, `>`, `"`, `'`), mirroring `js/lib/utils.js`; all 112 element-content callers remain safe.

**File:** `js/admin.js:5688` (sink), `js/admin.js:5291-5295` (vulnerable helper)

**Issue:** The new Delete button serializes customer-controlled fields into double-quoted HTML attributes:

```js
actionCell += '... data-product="' + escapeHTML(String(b.product_name || '')) + '" data-customer="' + escapeHTML(String(b.customer_name || '')) + '">Delete</button>';
```

But admin.js's `escapeHTML` escapes only via `textContent`/`innerHTML`, which does **not** encode the double-quote character:

```js
function escapeHTML(str) {
  var div = document.createElement('div');
  div.textContent = str;
  return div.innerHTML;   // escapes &, <, > but NOT "
}
```

Confirmed with jsdom: a `customer_name` of `" onmouseover="alert(1)` passes through `escapeHTML` unchanged for the quote, breaks out of the `data-customer="..."` attribute, and injects a live `onmouseover` event handler onto the button. Because `customer_name` originates from sales-order/contact data (an online-order customer can set their own name), this is a **stored XSS** that fires in the authenticated admin Batches view — the highest-trust surface in the app.

Note: this is newly introduced by phase 27.1. The pre-existing `data-version="..."` attribute on line 5686 uses `b.last_updated` (a server timestamp, not user-controlled), so the prior code did not expose this sink with attacker-controlled data. The BrewPad equivalent is NOT affected because `js/brewpad.js`'s `escapeHTML` (line 6) explicitly does `.replace(/"/g, '&quot;')`.

**Fix:** Use an attribute-safe escaper for these values. Either switch the admin Delete button to a quote-escaping helper, or stop putting these values in attributes (they are only needed for the confirm message — read them from the batch row data instead). Minimal fix — add quote escaping to a dedicated attr escaper and use it here:

```js
function escapeAttr(str) {
  return String(str == null ? '' : str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;');
}
// ...
actionCell += '... data-product="' + escapeAttr(String(b.product_name || '')) +
  '" data-customer="' + escapeAttr(String(b.customer_name || '')) + '">Delete</button>';
```

(Or follow the BrewPad pattern and make admin's `escapeHTML` escape `"` as well — but verify no callers depend on the current quote-passthrough behavior first.)

## Warnings

### WR-01: BrewPad delete leaves the deleted batch visible on the dashboard (stale UI, re-clickable)

**Status:** Fixed in eb21237 — success handler now calls `loadDashboard()` (refetches `_dashSummary` and re-renders the dashboard); cache-invalidation flags kept so the batches tab is fresh on next visit.

**File:** `js/brewpad.js:4544-4558`

**Issue:** The "Needs Scheduling" Delete button lives on the **dashboard** (rendered by `renderDashboard()` from `_dashSummary.needsScheduling`). On success the handler does:

```js
_batchesLoaded = false;
_allBatchesData = [];
_eagerLoadTime = 0;
_dashLoadTime = 0;
loadBatches();   // refreshes the BATCHES tab, not the dashboard
```

`loadBatches()` re-fetches and calls `renderBatchList()` — it never re-renders the dashboard and never refetches `_dashSummary`. The user is still looking at the dashboard, so the just-deleted row remains on screen with `_dashSummary` still containing it. Setting `_dashLoadTime = 0` only forces a reload on the *next* dashboard navigation (or the 5-min auto-refresh). Clicking the still-visible Delete again will POST a second `delete_batch` for an already-deleted ID, surfacing a "Failed:" toast.

**Fix:** Refresh the surface the button is actually on. Call `loadDashboard()` (which refetches `_dashSummary` and calls `renderDashboard()`) on success; keep the cache invalidation so the batches tab is also fresh:

```js
.then(function () {
  showToast('Batch ' + bid + ' deleted', 'success');
  _batchesLoaded = false; _allBatchesData = [];
  _eagerLoadTime = 0; _dashLoadTime = 0;
  loadDashboard();   // re-renders the dashboard the user is viewing
})
```

### WR-02: Confirm dialog `customer` field diverges from displayed customer name (admin)

**Status:** Fixed in 7b2c50d — `data-customer` now populated from `getCustomerDisplayName(b)`, the same resolver the row cell uses.

**File:** `js/admin.js:5688` vs `js/admin.js:5679`

**Issue:** The table cell renders the customer via `getCustomerDisplayName(b)` (a fallback-aware resolver), but the Delete button's `data-customer` and therefore the confirm prompt use the raw `b.customer_name`. When `customer_name` is empty but a display name exists under another field, the confirmation reads "Delete SV-B-… (Product)" with no customer, weakening the operator's "am I deleting the right batch?" check on an irreversible action.

**Fix:** Populate `data-customer` from the same resolver used for display:

```js
'... data-customer="' + escapeAttr(String(getCustomerDisplayName(b) || '')) + '">Delete</button>'
```

### WR-03: Delete not guarded against empty `batch_id`

**Status:** Fixed in 6d9670b — both handlers bail early with a "Missing batch ID" error toast when the id is empty, before showing the confirm.

**File:** `js/admin.js:5777-5784`, `js/brewpad.js:4537-4545`

**Issue:** Both handlers read `data-batch-id` and POST it unconditionally. In BrewPad the attribute is built from `it.batch_id || ''`, so a malformed/partial `needsScheduling` entry yields `batch_id: ''`. The confirm message renders "Delete  (Product …)" with a blank ID and, on confirm, sends `delete_batch` with an empty id — relying entirely on the Apps Script backend to reject it. A defensive client guard avoids an ambiguous destructive prompt.

**Fix:** Bail early when the id is empty before showing the confirm:

```js
var bid = nsDelBtn.getAttribute('data-batch-id');
if (!bid) { showToast('Missing batch ID', 'error'); return; }
```

## Info

### IN-01: Duplicated delete logic across three call sites

**File:** `js/admin.js:5773-5798` and `js/admin.js:6092-6111`; `js/brewpad.js:4535-4561` and `js/brewpad.js:2598-2620`

**Issue:** The delete flow (confirm → disable → `adminApiPost('delete_batch')` → toast + cache-invalidate + reload, with error re-enable) is now copy-pasted in four places (two per file). The cache-reset incantation in BrewPad (`_batchesLoaded`/`_allBatchesData`/`_eagerLoadTime`/`_dashLoadTime`) is repeated verbatim and is exactly where WR-01 diverged. Divergence between copies is how the stale-dashboard bug arose.

**Fix:** Extract a `deleteBatch(batchId, opts)` helper per file (or shared) that owns the POST + cache invalidation + refresh, and have each button call it with an `onDone` for surface-specific re-render.

Worth folding into a class while this block is being touched. No correctness impact.
