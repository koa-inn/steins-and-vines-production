<objective>
Add an inline Delete button to pending rows in the admin Batches list so staff can delete duplicate pending batches in one place, beside the Phase 27 Activate / Schedule & activate buttons, instead of editing the Google Sheet by hand.

Purpose: Pending batches are sometimes auto-created for something already made into a batch; staff currently clean these up by deleting the row directly in the Batches sheet tab. This surfaces the existing, fully-wired `delete_batch` action inline (D-01) with a confirmation step.

Output: Modified `js/admin.js` (source) + rebuilt `js/admin.min.js` / `js/main.min.js`. No backend changes (D-06: `deleteBatch()` stays unchanged).
</objective>

<decision_coverage>
This plan implements: D-01 (inline Delete on admin pending rows), D-04 (detail-modal Delete untouched), D-05 (UI-gated to pending status only), D-06 (backend deleteBatch() unchanged, `{ batch_id }` only), D-07 (silent child cascade preserved), D-08 (generic attached-tasks warning), D-09 (confirm shows batch ID + product + customer), D-10 (irreversible framing, no backup mention), D-11 (reuse showConfirm() custom dialog).
</decision_coverage>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin browser → Apps Script (`delete_batch`) | Staff-initiated mutating request crosses to the Google Apps Script backend; authenticated via the existing staff Google-OAuth path (`adminApi.gs` ~line 301). No new boundary is introduced by this phase. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27.1-01 | Tampering | Client-side `if (status === 'pending')` UI gate | accept | D-05/D-06: gate is UI-only by design. The detail-view Delete already deletes any-status batches through the same authenticated `delete_batch` action, so a crafted request deleting a non-pending batch grants no privilege the staff user does not already have. No server-side status guard added. |
| T-27.1-02 | Repudiation | `delete_batch` deletes rows with cascade, no audit trail | accept | Audit logging of who deleted a batch was explicitly not raised as a need (CONTEXT deferred). Nightly Drive backup (`apps-script/backup.gs`) provides recovery in practice; UI copy intentionally frames as irreversible (D-10) to keep staff cautious. |
| T-27.1-03 | Denial of Service (accidental) | Fat-finger delete of the wrong duplicate | mitigate | Confirmation dialog shows batch ID + product + customer (D-09) so staff verify identity before deleting; `e.stopPropagation()` + row-click guard prevent the row-open click from also triggering anything destructive. |
| T-27.1-04 | Information Disclosure | XSS via product/customer name in confirm copy or data attributes | mitigate | `escapeHTML()` is applied to `data-product` / `data-customer` attribute values at render time (matching the existing Activate-button convention); the confirm message is rendered as text by `showConfirm`, not innerHTML-injected. |
| T-27.1-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in this phase — only edits to existing source + `npm run build` of the existing toolchain. No `[ASSUMED]`/`[SUS]` packages introduced; no install checkpoint required. |
</threat_model>
