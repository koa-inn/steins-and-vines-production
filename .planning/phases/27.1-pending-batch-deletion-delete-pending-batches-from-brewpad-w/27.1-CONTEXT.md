# Phase 27.1: Pending Batch Deletion - Context

**Gathered:** 2026-06-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Give staff a way to delete pending (duplicate) batches from the UI with a confirmation step, removing the batch row via the existing Apps Script `delete_batch` action instead of manual Google Sheet edits. The problem being solved: a pending batch sometimes gets auto-created for something that was already made into a batch, and today staff clean these up by deleting the row directly in the Batches sheet tab.

**In scope:** inline Delete affordance on the two list surfaces where pending batches surface (admin Batches list pending rows; BrewPad dashboard "Needs Scheduling" rows); confirmation dialogs using the existing custom-dialog patterns; post-delete refresh of the affected views.

**Out of scope:** changes to how pending batches are created; changes to the backend `deleteBatch()` cascade/status behavior; deletion of non-pending batches via the new inline buttons (existing detail-view Delete already covers any-status deletes); undo/restore UI.

**⚠ Key scoping fact (verified in code):** the seed assumed a `delete_batch` action would need to be created — it already exists and is fully wired. `adminApi.gs` has the `delete_batch` action (staff OAuth path, ~line 301) calling `deleteBatch()` (~line 2232), and BOTH detail views already call it with confirmation (admin detail modal `js/admin.js:6063`; BrewPad detail pane `js/brewpad.js:2594`). This phase is therefore a small frontend-only change: surface inline delete where pending batches appear in lists.

</domain>

<decisions>
## Implementation Decisions

### Delete button placement
- **D-01:** Inline Delete button on **admin Batches list pending rows**, beside the Phase 27 "Activate" / "Schedule & activate" buttons (`js/admin.js:~5686`).
- **D-02:** Inline Delete on **BrewPad dashboard "Needs Scheduling" rows** (`js/brewpad.js:~1033`).
- **D-03:** BrewPad batch list **cards** (Pending filter) do NOT get an inline Delete — they stay clean tap-targets that open the detail pane, which already has Delete Batch. Avoids accidental fat-finger deletes on mobile.
- **D-04:** Existing detail-view Delete buttons (admin modal + BrewPad detail) are untouched.

### Status restriction policy
- **D-05:** Restriction is **UI-gated only**: the new inline Delete buttons render only on rows with status `pending`. No server-side status guard is added.
- **D-06:** Backend `deleteBatch()` stays unchanged (deletes any status, cascades children, releases vessel) — the existing any-status detail-view Delete buttons depend on this behavior and must keep working.

### Child rows handling
- **D-07:** Keep the existing **silent cascade** (BatchTasks, PlatoReadings, VesselHistory rows deleted; vessel released). No block-if-children, no count fetch before confirm.
- **D-08:** The confirmation dialog copy warns generically that any attached tasks/readings/history will be removed (pending batches can have task rows if a schedule was attached).

### Confirmation dialog copy
- **D-09:** Confirm shows **batch ID + product name + customer name** so staff can verify they're deleting the right duplicate — e.g., "Delete SV-B-000123 (Pinot Grigio — Jane D.)? Any attached tasks will be removed. This cannot be undone."
- **D-10:** No mention of nightly-backup recoverability in the copy — keep the "cannot be undone" framing so staff stay cautious (backup recovery is staff knowledge, not UI copy).
- **D-11:** Reuse existing custom dialog patterns: `showConfirm()` in admin (`js/admin.js:138`), `showConfirmSheet()` with the danger button class in BrewPad (`js/brewpad.js:1678`). No native `confirm()`.

### Claude's Discretion
- Exact button styling/label (text "Delete" vs icon) and position within each row's action cluster — follow each surface's existing danger-button conventions (`admin-btn-danger`, `bp-danger-btn`).
- Post-delete refresh mechanics — reuse the existing post-delete refresh sequences already used by the detail-view delete handlers (admin: `loadBatchesData()` + `loadBatchDashboardSummary()` + `vesselsData = null`; BrewPad: cache-flag resets + `loadBatches()`).
- Exact wording differences between the admin and BrewPad confirm dialogs, as long as D-08/D-09/D-10 hold.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`delete_batch` Apps Script action** — complete, cascading, already authenticated via the staff OAuth path. Zero backend work expected.
- **`showConfirm()` (admin) / `showConfirmSheet()` (BrewPad)** — custom confirmation dialogs already used by the existing delete flows; BrewPad's takes an `okCls` of `bp-confirm-btn--danger` for destructive actions.
- **Existing delete handlers as templates** — `js/admin.js:6063` and `js/brewpad.js:2594` show the exact API call, button-disable, toast, and refresh sequence to replicate inline.
- **Phase 27 inline button wiring** — `batch-activate-btn` / `batch-schedule-activate-btn` delegation in `renderBatchList` shows how per-row buttons coexist with the row's open-detail click handler (`e.target.classList.contains(...)` guards at ~5699).

### Established Patterns
- **Pending rows are pinned to top** of the admin list (Phase 27 D-04) and carry `data-batch-id` + `data-version` attributes.
- **Row click opens detail** — inline buttons must stop propagation / be excluded from the row-open handler, as the Activate buttons already are.
- **Post-mutation refresh** — admin: `loadBatchesData()`, `loadBatchDashboardSummary()`, `vesselsData = null`; BrewPad: `_batchesLoaded = false`, `_allBatchesData = []`, `_eagerLoadTime = 0`, `_dashLoadTime = 0`, `loadBatches()`. The BrewPad dashboard "Needs Scheduling" section re-renders from the dash summary, so that cache must refresh too.
- **ES5 vanilla JS + build step** — edit `js/admin.js` / `js/brewpad.js` source, then `npm run build` regenerates minified artifacts. Never edit `.min.js` files.

### Integration Points
- Admin: pending-row action cell in `renderBatchList` (~5686) ↔ new inline Delete button + delegated handler.
- BrewPad: "Needs Scheduling" row markup in the dashboard renderer (~1033) ↔ new inline Delete button + handler (the rows currently only contain a batch chip + text).
- Both ↔ `adminApiPost('delete_batch', { batch_id })`.

### ⚠ Planner notes
- The "Needs Scheduling" row data items (`d.needsScheduling`) include `batch_id`, `product_name`, `customer_name` — enough for the D-09 confirm copy without an extra fetch. The admin list rows render from full batch objects, so the same fields are available there.
- A row can go stale (batch activated/deleted elsewhere) — the backend returns `not_found` for an already-deleted batch; surface that error via the existing toast pattern and refresh.

</code_context>

<specifics>
## Specific Ideas

- The confirm must identify the batch well enough to distinguish duplicates: batch ID + product + customer (D-09) — duplicates look identical by ID alone.
- Frame deletion as irreversible in the UI even though the nightly Drive backup (`apps-script/backup.gs`) makes it recoverable in practice (D-10).
- Inline delete belongs *beside* the Activate buttons so the "this pending batch is a duplicate" decision happens in the same place as the "this one is real, activate it" decision.

</specifics>
