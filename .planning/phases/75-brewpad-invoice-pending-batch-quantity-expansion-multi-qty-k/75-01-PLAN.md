<objective>
Fix the invoice→pending-batch derivation bug: `POST /api/batch/bulk-create` (`zoho-middleware/routes/pos.js:3216-3331`) loops the correct number of times per kit line but sends an identical `batchPayload` that never sets `unit_total`. The Apps Script dedup guard (`apps-script/adminApi.gs:1964-2028`) defaults `unit_total` to 1 when absent, so it admits unit 1 and rejects units 2+ as `duplicate_so_number` — collapsing a qty-3 kit line (INV-000171) to a single pending batch.

This is a byte-for-byte repeat of the already-fixed sale-path bug (INV-000137) in `createBatchesFromSale` (`lib/brewpad-integration.js:345-410`). Port that fix: switch the raw `kitBatchQuantity` loop to `planKitBatches` (fee-slot cap, D-04), compute `unitTotalBySku`, and set `unit_total` on every create payload. No Apps Script change, no schema change, no data migration — the existing guard already implements the D-02 reconcile formula once given the right `unit_total`.

Purpose: BrewPad staff see one pending batch per paid kit unit, and repeated Pull-from-Zoho polls converge to exactly the invoice line quantity without duplicating (D-01/D-02/D-04).
Output: A regression test that reproduces INV-000171 (fails before the fix, passes after), then the one-field fix on the bulk-create route.

## Decision — D-01 backfill trigger for the already-broken INV-000171 (planner decision, explicit per research Open Question 1)

**Decided: ship the idempotent `unit_total` fix as the core, always-in-scope deliverable; deliver D-01 "auto-backfill on next reconcile" via the fix's idempotency, and backfill INV-000171 itself by a one-time manual single-invoice re-import (`GET /api/batch/scan-invoices?number=INV-000171` → Create Batches), which has NO `alreadyHasBatch` skip filter and works once the fix lands. Do NOT modify the date-window scan's `alreadyHasBatch` skip condition (pos.js:3156-3160).**

Rationale: the date-window scan intentionally hides already-linked invoices from the Pull-from-Zoho candidate list for the common (correct) single-batch case; making it count-aware is a larger, riskier UX change that overlaps not-yet-built Phase 62/63 reconciliation work (research Open Question 1, Pitfall 3). The single-invoice re-import path already resurfaces INV-000171 with zero code change. The live re-import + "3 of 3" confirmation is an owner operational follow-up (requires a prod middleware deploy — no staging middleware exists per project convention) and is captured in this phase's verification section, NOT as a code task.

## Decision — shared-helper extraction (planner decision, explicit per research Open Question 2)

**Decided: do NOT extract a shared payload-building helper between `createBatchesFromSale` and the bulk-create route in this phase.** Rationale: CLAUDE.md working principles (implement the simplest solution for a simple problem; don't touch unrelated code; one logical change per commit). Extracting would modify the working, money-adjacent sale path (`createBatchesFromSale`) for no correctness gain in this bug fix. The mirror-the-pattern approach keeps the change confined to the one broken route. Recurrence-prevention via a shared helper is recorded as a follow-up candidate, not executed here.
</objective>
