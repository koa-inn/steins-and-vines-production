# Phase 29.3: Pull non-kiosk batch sales into BrewPad - Context

**Gathered:** 2026-06-13
**Status:** Ready for planning

<domain>
## Phase Boundary

A "Pull from Zoho" control in BrewPad that bulk-scans a bounded window of recent
Zoho invoices, finds **ferment-in-store sales** (those carrying a **Maker's Fee**
line item) that have **no batch yet**, and creates **pending** batches for them —
deduped by `zoho_so_number` and bounded to respect Zoho rate limits.

**Why this phase exists:** BrewPad batches today are only created by the kiosk/website
checkout path (`createBatchesFromSale`, fired fire-and-forget from `routes/pos.js`),
and only when the sale carries a Maker's Fee. An invoice completed **directly in Zoho
Books** never runs that path, so no batch appears in BrewPad. This phase closes that gap.

**In scope:**
- Bulk-scan endpoint (middleware): list a bounded window of recent invoices, skip those
  already carrying `cf_batch_status`, detail-fetch the rest, detect Maker's Fee, extract
  kit line items + customer.
- A confirm sheet in BrewPad listing candidate invoices before any batch is created.
- A single-invoice "import this invoice number" fallback path.
- Dedup by `zoho_so_number` (middleware pre-check + Apps Script idempotency guard).
- `js/brewpad.js` "Pull from Zoho" control + confirm sheet + list refresh.

**Out of scope:**
- Changing how kiosk/online checkout creates batches (that path stays as-is).
- Editing/activating the created batches (they land as `pending` — Phase 29.2 handles activation).
- Server-side Redis caching of the batch list (client TTL only today; not introduced here).
- Any non-ferment-in-store invoice (no Maker's Fee = not a candidate, by definition).

</domain>

<decisions>
## Implementation Decisions

### Scan window & rate limiting
- **D-01:** Scan window is **last ~30 days with a hard page cap** (e.g. max 3–4 Zoho
  list pages ≈ ~200 invoices). The cap is mandatory — Zoho quota exhaustion has bitten
  this project before (tax-fix saga). The planner picks the exact page/day numbers; the
  shape is date-bounded + hard ceiling, not unbounded.
- **D-02:** Before any per-invoice detail fetch, **skip invoices that already carry the
  batch custom field** (`cf_batch_status`, written by `syncBatchToZoho`). Zoho's list
  endpoint **does** return `custom_fields`, so this filter is free and cuts the expensive
  detail-fetch count.
- **D-03:** Maker's Fee detection requires the **per-invoice detail GET** (`/invoices/{id}`)
  — Zoho's list/search endpoint does **not** return `line_items`. Do NOT rely on
  `line_items` off the list response (the existing `GET /api/batch/search-invoices` maps
  `inv.line_items || []` off the list and almost certainly returns empty — latent gap, do
  not depend on it).

### Candidate invoice statuses
- **D-04:** Candidate statuses are **paid + sent + draft** (exclude **void**). The user
  explicitly wants **drafts included for flexibility**, NOT excluded.
- **D-05:** Draft candidates must carry a **visual draft indicator (badge)** in the confirm
  sheet so staff can see a candidate came from an unfinalized invoice and choose to skip it.
  The always-confirm gate (D-06) is what makes including drafts safe — the human decides.

### Create flow (confirm gate)
- **D-06:** After the scan, **always show a confirm sheet** listing found candidates
  (invoice #, customer, kit items, draft badge where applicable). Staff approve before
  **any** batch is created. No silent auto-create. Matches the sensitive-write confirm +
  toast + warning vocabulary established in Phases 29.1 / 29.2.
- **D-07:** Created batches land as **`pending`** (reuse `callAppsScriptCreateBatch` per
  kit line item, as the kiosk path does). Activation is out of scope (Phase 29.2).
- **D-08:** Kit line-item extraction **excludes** the Maker's Fee item **and** the
  Materials Fee item (reuse `detectKitItems` logic in `brewpad-integration.js`).

### Single-invoice import fallback
- **D-09:** Also expose a **single "import this invoice number" path** alongside the bulk
  scan — staff type a known INV/SO number → resolve via the existing
  `GET /api/batch/customer-by-number` (which **does** return `line_items`) → create the
  batch. Cheap (1–2 Zoho calls), precise, and usable when staff already know the invoice
  without running a full scan.

### Dedup (locked from SEED — belt-and-suspenders)
- **D-10:** Dedup by `zoho_so_number` in **two places**:
  1. **Middleware pre-check** — fetch existing batches (Apps Script `get_batches`) and skip
     invoices already represented before offering them as candidates.
  2. **Apps Script `create_batch` idempotency guard** — `adminApi.gs` `createBatch`
     (~:1899) currently has **no** dedup by `zoho_so_number`; add a guard there so a
     concurrent/duplicate create cannot land twice. This is a latent duplicate-risk fix
     worth doing regardless of the scan feature.

### Carried forward from prior phases (not re-decided)
- **Confirm before sensitive Zoho-touching writes** (29.1 D-02) → applies to bulk create.
- **Server-authoritative resolution** (29.1) → middleware/Apps Script resolves contacts and
  line items; the client never trusts client-supplied batch data.
- **Reuse the detail-pane confirm sheet + toast + warning UX vocabulary** (29.1 / 29.2).

### Claude's Discretion
- Exact scan numbers (days / max pages / invoice count ceiling) within the D-01 shape.
- Where the bulk-scan endpoint lives (new route in `routes/pos.js` vs a dedicated route file)
  and its exact request/response shape — research/planner's call, keep consistent with the
  existing `/api/batch/*` endpoints.
- Exact confirm-sheet markup and where the "Pull from Zoho" control sits in the BrewPad
  filter bar (`renderBatchList` ~:1573, filter bar ~:1605–1622) — keep consistent with
  existing BrewPad controls.
- Confirm-sheet behavior on **partial failure** (some batches create, some fail) — surface
  per-row success/failure with the existing toast/warning vocabulary; planner decides exact UX.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`detectKitItems` / `findMakersFeeItem` / `findMaterialsFeeItem`** — exact Maker's-Fee
  detection and kit-item extraction the scan needs, already battle-tested by the kiosk path.
- **`callAppsScriptCreateBatch`** — single-batch create resolving `{ ok }`; the confirm-step
  bulk create loops this per kit item (same as `createBatchesFromSale`).
- **`GET /api/batch/customer-by-number`** — full INV/SO resolution **with** `line_items`;
  the single-invoice import (D-09) is essentially this endpoint + a create call.
- **`get_batches` (Apps Script)** — existing-batch list for the middleware dedup pre-check.
- **BrewPad detail/confirm UX** — established confirm-sheet + toast + warning pattern, plus
  `_batchesLoadTime` client TTL to refresh the list after a write.

### Established Patterns
- **Server-authoritative**: middleware/Apps Script resolve and validate; client supplies
  intent (which candidates to create), not authoritative batch data.
- **Sensitive Zoho-touching writes go through a confirm sheet** with toast feedback and
  warning-on-failure (29.1 / 29.2; void-failure alerts).
- **Zoho rate-limit caution**: bounded windows + hard caps; minimize detail fetches (the
  `cf_batch_status` skip in D-02 exists for exactly this).
- **Fire-and-forget batch creation** is how the kiosk path works today — but this phase is
  staff-initiated and confirm-gated, so creation is synchronous-to-the-confirm, not fire-and-forget.

### Integration Points
- New bulk-scan endpoint under `/api/batch/*` (middleware) → list + filter + per-invoice detail
  fetch + Maker's-Fee detection + dedup pre-check → returns candidates to the client.
- New "Pull from Zoho" + single-import controls in `js/brewpad.js` filter bar; confirm sheet;
  `_batchesLoadTime` invalidation + list refresh after create.
- Apps Script `createBatch` gains a `zoho_so_number` idempotency guard (D-10).

</code_context>

<specifics>
## Specific Ideas

- The motivating case: a ferment-in-store sale invoiced **directly in Zoho Books** (not via
  kiosk/website), which today produces **no BrewPad batch**. This feature lets staff sweep
  those in.
- Drafts are deliberately **in** the candidate set (user's call) because staff want flexibility
  to pull a batch before an invoice is finalized — but a **draft badge** in the confirm sheet
  keeps it honest, and the confirm gate means a draft is never silently turned into a batch.
- Behavior should feel like the rest of BrewPad's Zoho-touching controls: confirm → toast →
  warning-on-failure, then refresh the list.

</specifics>

<deferred>
## Deferred Ideas

- **Server-side Redis cache for the batch list** — only a client TTL exists today; not
  introduced here. Its own concern if scan volume warrants it.
- **Scheduled/automatic background scan** — this phase is staff-initiated only. A cron-style
  auto-pull is a future enhancement, not this phase.
- **Activation of the created pending batches** — out of scope; Phase 29.2 owns activation.
- **Fixing `GET /api/batch/search-invoices` to fetch real `line_items`** — noted as a latent
  gap (D-03); this phase routes around it rather than fixing it unless the planner finds it cheap.

None of the above were folded into this phase's scope — discussion stayed within the bulk-scan boundary.

</deferred>
