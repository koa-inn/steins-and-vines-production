# Phase 29.3 — Design Seed (pre-discuss notes)

> Captured from the conversation that created this phase, so the analysis survives a `/clear`.
> Read this during `/gsd-discuss-phase 29.3` and `/gsd-plan-phase 29.3`.

## Problem
BrewPad batches are created **only** by the kiosk/website checkout flow, and **only** when the sale
carries a **Maker's Fee** line item (`detectKitItems` returns `[]` without one —
`zoho-middleware/lib/brewpad-integration.js:43-58`, `createBatchesFromSale` at :153, fired
fire-and-forget from `routes/pos.js:518` (kiosk) and `:1134` (online)). An invoice completed
**directly in Zoho Books** never runs that path → no batch appears in BrewPad. (Not an amount
issue — `findMakersFeeItem` ignores price: `lib/checkout-helpers.js:160-171`.)

## Chosen approach (user decision)
**Bulk auto-scan** (option B), driven through GSD. A "Pull from Zoho" refresh in BrewPad that finds
ferment-in-store invoices with no batch yet and bulk-creates pending batches.

## Hard constraint that shapes the design
Zoho Books' **invoice list/search endpoint does NOT return `line_items`** — only the per-invoice
**detail GET** (`/invoices/{id}`) does. So Maker's-Fee detection requires a detail fetch per
candidate. NOTE: the existing `GET /api/batch/search-invoices` (`routes/pos.js:1340-1369`) maps
`inv.line_items || []` off the **list** response, so it almost certainly returns empty line_items —
a latent gap to be aware of (do not rely on list line_items).

## Design outline to plan against
1. **Candidate selection (bounded, rate-limit-aware):** list a bounded window of recent invoices
   (e.g. last N / last 30 days; decide statuses — paid? sent? all?). Zoho list **does** return
   `custom_fields`, so **skip invoices that already carry the batch custom field**
   (`cf_batch_status`, written by `syncBatchToZoho` in `brewpad-integration.js:251-270`) to cut
   detail fetches.
2. **Detail fetch per remaining candidate** → `findMakersFeeItem` on its line_items → if present,
   it's a ferment-in-store sale; extract kit line items (exclude Maker's + Materials Fee) and
   customer (name/contact_id).
3. **Dedup by `zoho_so_number`:** fetch existing batches (Apps Script `get_batches`) and skip
   invoices already represented. ALSO add an idempotency guard in Apps Script `create_batch`
   (`apps-script/adminApi.gs:1899` — currently has **no** dedup by zoho_so_number; latent duplicate
   risk worth fixing regardless).
4. **Confirmation step:** surface the found candidates and let staff confirm before bulk-creating
   (avoids surprise batches). Reuse `callAppsScriptCreateBatch` per kit item → batches land as
   `pending`.
5. **UI:** "Pull from Zoho" control in the BrewPad batch filter bar (`js/brewpad.js` ~`renderBatchList`
   :1573, filter bar ~:1605-1622), a confirm sheet, then invalidate `_batchesLoadTime` to refresh the
   list. No server-side Redis cache for the batch list today (client TTL only).

## Open questions for discuss-phase
- Scan window: how many invoices / how far back? Hard cap to respect Zoho rate limits (history of
  quota exhaustion — see tax-fix saga).
- Which invoice statuses count (paid / sent / draft / void)?
- Auto-create vs always-confirm? (recommended: confirm.)
- Where does dedup live — middleware pre-check, Apps Script guard, or both? (recommended: both.)
- Should this also expose a single "import this invoice number" path as a fallback (cheap, 1-2 calls)?
