# Phase 29.3: Code Review Report

**Reviewed:** 2026-06-14
**Depth:** deep
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Phase 29.3 introduces a bounded Zoho invoice scan, a bulk-create endpoint, and a
BrewPad "Pull from Zoho" confirm sheet. The server-authoritative architecture, D-01
page-cap enforcement, D-02 cf_batch_status skip, and D-04 draft inclusion are all
correctly implemented. Auth (x-api-key), XSS escaping in the confirm-sheet HTML,
the dedup graceful-degradation path, and the per-invoice sequential chain respecting
Zoho rate limits are solid.

Two blockers need fixing before this ships:

1. The Apps Script `createBatch` dedup guard introduced by D-10.2 blocks the **second kit
   item** from any multi-kit invoice — silently returning `duplicate_so_number` for the
   same invoice's second create call. This is a regression that also breaks the existing
   kiosk path (sequential bulk-create) whenever a customer buys two kits in one transaction.

2. The single-invoice mode (`?number=INV-XXXXXX`) calls Zoho's
   `GET /invoices/{invoice_id}` path with an **invoice number** (e.g., `INV-000123`),
   not the numeric internal ID Zoho requires. The endpoint returns 502 in production for
   every single-import attempt. SO-prefixed numbers additionally hit the wrong Zoho
   endpoint entirely (`/invoices/` instead of `/salesorders/`).

## Critical Issues

### CR-01: Apps Script dedup guard breaks multi-kit invoices (regression)

**File:** `apps-script/adminApi.gs:1910-1922`
**Issue:** The D-10.2 idempotency guard added to `createBatch` scans existing
`BATCHES_SHEET_NAME` rows and returns `{ ok:false, error:'duplicate_so_number' }` the
first time any row with a matching `zoho_so_number` is found. This is correct for
preventing a replay of a single-kit invoice, but it fires on the **second kit item** of
a multi-kit invoice too, because both kit-item creates share the same `zoho_so_number`.

Because `bulk-create` in `pos.js` chains kit-item creates **sequentially** (via
`kitChain`), the first kit succeeds and writes `zoho_so_number = INV-000001`; the
second kit create finds that row and returns `duplicate_so_number`. The second batch is
silently dropped. The middleware surfaces this as `ok:false, error:'duplicate_so_number'`
in `kit_results`, but the per-invoice summary may still mark the overall invoice as
`ok:false` depending on which item failed, confusing the operator.

This also regresses the **kiosk path** (`createBatchesFromSale` in
`brewpad-integration.js:159`), which fire-and-forgets parallel creates per kit item —
whichever finishes first will block the others.

The test suite in `batch-scan-invoices.test.js` covers the 2-kit-item case at the
middleware level (line ~567) but mocks `callAppsScriptCreateBatch`, so the Apps Script
dedup guard is never exercised and the failure is invisible to CI.

**Fix:** The dedup guard must be tightened to check both `zoho_so_number` **and**
`product_sku` together, so that two different kits from the same invoice are permitted
while a true duplicate (same invoice + same SKU) is blocked:

```javascript
// In createBatch, replace the current guard with:
if (payload.zoho_so_number && payload.product_sku) {
  var existingBatches = sheetToObjects(BATCHES_SHEET_NAME);
  for (var di = 0; di < existingBatches.length; di++) {
    var sameInvoice = String(existingBatches[di].zoho_so_number || '').trim() ===
                      String(payload.zoho_so_number).trim();
    var sameSku     = String(existingBatches[di].product_sku || '').trim() ===
                      String(payload.product_sku).trim();
    if (sameInvoice && sameSku) {
      return {
        ok: false,
        error: 'duplicate_so_number',
        message: 'A batch for SO/invoice ' + payload.zoho_so_number +
                 ' + SKU ' + payload.product_sku + ' already exists: ' +
                 existingBatches[di].batch_id
      };
    }
  }
} else if (payload.zoho_so_number && !payload.product_sku) {
  // Fallback: invoice-level dedup when no SKU provided (should not happen from this phase)
  var existingBatches2 = sheetToObjects(BATCHES_SHEET_NAME);
  for (var dj = 0; dj < existingBatches2.length; dj++) {
    if (String(existingBatches2[dj].zoho_so_number || '').trim() ===
        String(payload.zoho_so_number).trim()) {
      return { ok: false, error: 'duplicate_so_number',
               message: 'A batch for SO/invoice ' + payload.zoho_so_number + ' already exists' };
    }
  }
}
```

### CR-02: Single-invoice mode uses invoice number as Zoho path ID — always 502 in production

**File:** `zoho-middleware/routes/pos.js:1508`
**Issue:** The single-invoice fallback path (D-09) validates `req.query.number` with
`/^(INV|SO)-\d+$/i` and then calls:

```javascript
return zohoGet('/invoices/' + rawNumber)
```

Zoho Books `GET /books/v3/invoices/{invoice_id}` expects a **numeric internal ID**
(e.g., `109900000000567890`), not a human-readable invoice number like `INV-000123`.
Sending a number-format string in the path will result in a Zoho 404 or error response,
which the `.catch` handler converts to a `502` returned to the client. Every
single-import attempt by staff will fail with "Failed to scan invoices from Zoho".

Additionally, `SO-` prefixed numbers hit the wrong endpoint (`/invoices/` instead of
`/salesorders/`), making them doubly broken.

The tests mock `zohoGet` so they pass regardless; no test exercises real Zoho path
behaviour.

**Fix:** The single-invoice mode should search by number first (as the existing
`customer-by-number` endpoint does at line 1372), retrieve the internal `invoice_id`,
then proceed:

```javascript
// Single-invoice mode (D-09)
if (req.query.number) {
  var rawNumber = (req.query.number || '').trim().toUpperCase();
  if (!/^(INV|SO)-\d+$/.test(rawNumber)) {
    return res.status(400).json({ error: 'bad_request', message: 'number must match INV-NNNN or SO-NNNN format' });
  }

  var isInv = /^INV-/.test(rawNumber);
  var listPath   = isInv ? '/invoices'    : '/salesorders';
  var filterKey  = isInv ? 'invoice_number' : 'salesorder_number';
  var entityKey  = isInv ? 'invoices'     : 'salesorders';
  var idField    = isInv ? 'invoice_id'   : 'salesorder_id';
  var detailKey  = isInv ? 'invoice'      : 'salesorder';
  var detailPath = isInv ? '/invoices/'   : '/salesorders/';

  var filterParams = {};
  filterParams[filterKey] = rawNumber;

  return zohoGet(listPath, filterParams)
    .then(function (listData) {
      var docs = listData[entityKey] || [];
      var doc = null;
      for (var i = 0; i < docs.length; i++) {
        if (String(docs[i][filterKey] || '').toUpperCase() === rawNumber) { doc = docs[i]; break; }
      }
      if (!doc) return res.json({ candidates: [] });

      return zohoGet(detailPath + doc[idField])
        .then(function (detailData) {
          var inv = detailData[detailKey] || {};
          var lineItems = inv.line_items || [];
          var kitItems = brewpadIntegration.detectKitItems(lineItems);
          if (kitItems.length === 0) return res.json({ candidates: [] });
          return res.json({
            candidates: [{
              invoice_id: doc[idField],
              invoice_number: rawNumber,
              customer_name: inv.customer_name || '',
              customer_id: inv.customer_id || '',
              status: inv.status || '',
              kit_items: kitItems.map(function (k) { return { sku: k.sku || '', name: k.name || '' }; })
            }]
          });
        });
    })
    .catch(function (err) {
      log.warn('[batch/scan-invoices] single-invoice fetch failed for ' + rawNumber + ': ' + err.message);
      return res.status(502).json({ error: 'zoho_error', message: 'Failed to scan invoices from Zoho' });
    });
}
```

This mirrors the proven two-step approach of `customer-by-number` and correctly handles
both `INV-` and `SO-` prefixes. Update the test to stub the two-step chain instead of
the single direct lookup.

## Warnings

### WR-01: No format validation on `invoice_ids` in `POST /api/batch/bulk-create`

**File:** `zoho-middleware/routes/pos.js:1652-1664`
**Issue:** The only validation on the `invoice_ids` body parameter is that it is a
non-empty array (line 1653). Each element is used directly in:

```javascript
return zohoGet('/invoices/' + invoiceId)
```

A client (or an attacker in possession of the semi-public `MW_API_KEY`) can supply
crafted strings such as `"../contacts"` or `"?organization_id=ATTACKER_ORG"` that
traverse to unintended Zoho API paths. While the Zoho token restricts what the
traversal can access to the same organization's data, it could expose contact lists,
purchase orders, or other Zoho resources not intended to be accessible through this
endpoint.

**Fix:** Add a format guard before the chain loop:

```javascript
var VALID_INVOICE_ID = /^\d{15,20}$/;
for (var vi = 0; vi < invoiceIds.length; vi++) {
  if (typeof invoiceIds[vi] !== 'string' || !VALID_INVOICE_ID.test(invoiceIds[vi])) {
    return res.status(400).json({ error: 'bad_request',
      message: 'Each invoice_id must be a Zoho numeric ID (15-20 digits)' });
  }
}
```

Additionally add a size cap (the scan is bounded at ~200 invoices by D-01, so
`invoice_ids.length > 200` should be rejected) to prevent quota amplification from
a single request:

```javascript
if (invoiceIds.length > 200) {
  return res.status(400).json({ error: 'bad_request', message: 'invoice_ids must contain 200 or fewer items' });
}
```

### WR-02: `_pullSheetBackdropHandler` added without guard — double-registers on rapid re-open

**File:** `js/brewpad.js:2283`
**Issue:** `openPullFromZohoSheet` calls `sheet.addEventListener('click', _pullSheetBackdropHandler)`
unconditionally every time it is invoked. The sheet DOM element is created once and
reused (the `if (!sheet)` guard at line 2273 prevents duplicate creation). But
`hidePullSheet` removes only **one** listener registration via `removeEventListener`.
If the user clicks the "Pull from Zoho" button a second time before the sheet is hidden
(e.g., during the async scan), an extra handler accumulates that persists until the next
`hidePullSheet` call, causing the backdrop to close the sheet twice (harmless but
surprising) or leak a listener permanently if the sheet element is ever detached.

**Fix:** Guard the `addEventListener` call:

```javascript
// In openPullFromZohoSheet, replace line 2283 with:
sheet.removeEventListener('click', _pullSheetBackdropHandler); // remove any existing first
sheet.addEventListener('click', _pullSheetBackdropHandler);
```

### IN-02: Duplicated single-import button event-wiring code

**File:** `js/brewpad.js:2171-2207` and `js/brewpad.js:2307-2344`
**Issue:** The single-import button `click` handler is implemented twice, identically:
once in `renderPullCandidates` (wired after the candidate list renders) and once in
`openPullFromZohoSheet`'s loading-state setup (wired before the scan completes). Both
blocks contain the same 30+ lines of fetch logic. There is no defect in the current
duplication (both paths work correctly), but a future change to the handler will need to
be made in two places.

**Fix:** Extract to a named helper `_wireSingleImportBtn()` that accepts the
`importBtn` element reference and calls `renderPullCandidates` on success, then call it
from both sites.
