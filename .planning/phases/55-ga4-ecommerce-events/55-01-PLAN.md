# 55-01 — Review + ship GA4 ecommerce events

## Objective

Ship the already-written, uncommitted GA4 ecommerce tracking (`add_to_cart`, `begin_checkout`,
`purchase`) to production via staging, after an adversarial money-path review and green gates.
Do NOT re-implement. This closes ANALYTICS-01. The GTM-side wiring is Phase 56.

## Preconditions

- The GA4 changes are present uncommitted in the working tree (verify with `git status`;
  see 55-CONTEXT.md for the file list). If the tree is clean, STOP — the code is missing and
  this becomes a build phase, not review-and-ship; escalate to the owner.

## Tasks

### T1 — Review the diff (correctness + safety) — money path is priority
- `git diff` the GA4 changes. Read `js/modules/03-events.js`, `07-catalog-kits.js`,
  `11-cart.js`, and especially **`12-checkout.js`**.
- Confirm on `12-checkout.js`:
  - `purchase` fires ONLY in the confirmed-Helcim-success paths (single-cart `.then(oR)` AND
    dual-cart success callback), never on button click or a failed/abandoned attempt.
  - Fires **exactly once per order** — dedup by `transaction_id`; verify the id is unique per
    order and stable across a retry of the same order (OQ-3).
  - Fires BEFORE cart/idempotency state is cleared (so the items/total are still available).
  - **No payment/charge/cart logic was altered** — the diff adds only analytics calls.
  - Every GA4 helper is wrapped (try/catch or equivalent) so analytics can NEVER throw into
    the checkout flow.
- Confirm `add_to_cart` sits beside each existing `trackEvent('add_to_cart', …)` (5 in
  `11-cart.js` + 1 in `07-catalog-kits.js`) and `begin_checkout` is in the initial-submit
  idempotency block (fires once).
- Review `tests/frontend/ga4-ecommerce.test.js` for meaningful coverage (dedup, success-only
  purchase, item mapping, currency CAD).
- **OQ-1:** check whether the diff adds the GTM container snippet to `products.html`. If not,
  add it (matches the other public pages; staging pages + `admin.html` stay untagged).

### T2 — Re-run the gates (CLAUDE.md)
- `npm test` (frontend, incl. `ga4-ecommerce.test.js`) — green.
- `cd zoho-middleware && npm test` — green (no middleware change, but required).
- `npm run lint` — clean.
- If T1 changed any `js/modules/*` file (e.g. products.html tag or a fix), re-run `npm run build`
  so `js/main.js` / `js/main.min.js` + HTML cache stamps regenerate. Never hand-edit the bundles.

### T3 — Commit as one logical change
- Stage the GA4 files only (analytics diff + `ga4-ecommerce.test.js` + regenerated bundles/stamps).
  Keep it a single coherent commit.
- Suggested message: `feat(analytics): add GA4 ecommerce events (add_to_cart, begin_checkout, purchase)`.

### T4 — Ship to staging + GA4 DebugView UAT (checkpoint: human)
- `git push origin main` → staging.steinsandvines.ca. Never straight to prod.
- With GTM Preview + GA4 DebugView, run a test order on staging and confirm:
  - exactly one `purchase` with populated `ecommerce` (`transaction_id`, `value`,
    `currency: "CAD"`, `items`), plus `add_to_cart` and `begin_checkout`;
  - re-triggering the success path for the same order produces NO second `purchase`.
- NOTE: this needs the Phase 56 GTM event tags to actually see events in GA4 — coordinate so
  the tags exist in Preview (unpublished) for the DebugView check, or verify via the dataLayer
  directly if the tags aren't built yet.

### T5 — Promote to production (after staging approval)
- Per CLAUDE.md deploy flow (blessed `gated-deploy.yml` dispatch, or break-glass if warranted).
- Confirm the events fire on the live site.

## Success criteria

Maps to Phase 55 SC#1–6 in ROADMAP.md. Done when: diff reviewed safe (money path intact),
both suites + lint green, one commit shipped to staging and verified in GA4 DebugView (single
`purchase`, no double-count), `products.html` GTM-tagged, and promoted to prod after approval.

## Threat model

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser checkout success callback → dataLayer.push | analytics reads order data at the Helcim-success point; must not mutate or block the money path |
| dataLayer → GTM/GA4 | ecommerce payload leaves the site; must carry no PII beyond order-level fields (id/value/items) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-55-01 | Denial of Service (self-inflicted) | GA4 helper throwing inside the checkout success path | mitigate | Every `ga4*` helper wrapped so a throw cannot propagate into checkout; verify in T1; `ga4-ecommerce.test.js` covers the throw-safety |
| T-55-02 | Tampering / integrity (revenue double-count) | `purchase` firing more than once per order | mitigate | Dedup by unique `transaction_id`; fires only on confirmed Helcim success, once per single/dual path; T4 DebugView asserts no second `purchase` on success-path replay |
| T-55-03 | Repudiation (phantom/absent revenue) | `purchase` firing on a failed/abandoned attempt, or not at all | mitigate | Fires strictly inside the confirmed-success callbacks, before state clears; T1 review + T4 live UAT |
| T-55-04 | Information Disclosure | PII leaking into the dataLayer/GA4 payload | mitigate | Confirm the ecommerce object carries only order-level fields (transaction_id, value, currency, items) — no name/email/address; T1 review |
| T-55-05 | Tampering | money/charge/cart logic altered under cover of an "analytics" diff | mitigate | T1 confirms the diff adds ONLY analytics calls; both gate suites green (no behavioural test regressions) |
| T-55-SC | Tampering | npm installs | accept | Zero new runtime dependencies (analytics uses the existing dataLayer/GTM already on the page) — confirm no package.json/lockfile additions in the diff |
</threat_model>
