<objective>
Land the middleware half of the kiosk quote≠charge fix. Two server changes, both backward-compatible with the currently-deployed kiosk JS so this plan can deploy to prod BEFORE the frontend (67-02):

1. Remove the silent 5% tax guess in `computeTax` — an unresolvable catalog tax becomes fail-closed (matches the Phase 52 fail-closed money-path doctrine). CRITICAL path split: on the SALE path (no charge yet) this is an early 400 naming the item; on the CONFIRM path (a terminal charge may ALREADY exist) it must flow through the existing void-on-failure machinery — never a bare 400 after a charge (pos.js:816-819 invariant).
2. Add a pre-charge assertion — when the client sends its displayed grand total, the server compares it to its own computed `grandTotal` before charging Helcim and rejects any divergence beyond $0.01. Server-computed totals remain the ONLY source of financial truth; the client value is asserted against, never trusted for pricing.

Purpose: make any client/server total divergence LOUD (fail-closed) instead of silently under-charging the displayed quote, and stop guessing tax rates — without ever creating an orphan charge.
Output: hardened `zoho-middleware/routes/pos.js` + updated/new middleware regression tests. This plan is the deploy-first unit; the frontend (67-02) only starts sending the asserted field after this ships.
</objective>

  client_grand_total : number   // the kiosk's displayed grand total (totals.total)
  client_tax_total   : number   // the kiosk's displayed tax total (totals.tax) — sent for observability
The server ASSERTS on client_grand_total only (compares to its computed grandTotal, tolerance $0.01).

<confirm_path_invariant>
<!-- Verified against pos.js during plan revision. -->
`/api/kiosk/sale/confirm` reconciles charges that may have ALREADY run on the physical terminal
(manual confirm, `body.transaction_id`). The route comment at pos.js:816-819 states the invariant:
"NEVER bare-400 after a charge → orphan charge (money taken, no invoice)". The void-on-failure
machinery lives in the route's OUTER `.catch` (pos.js:1370-1433): it engages ONLY for errors
THROWN into the promise chain — it branches on tagged errors first (`err.__manualVerify`,
~1374-1384) and then, for any other thrown error, voids via `moneyPath.voidWithTimeout` with the
`_helcimForVoid` wrapper when `body.transaction_id` is set (~1391-1430), else 502 (~1432).
An early `return res.status(400)` inside the confirm chain (e.g. at the computeTax call site ~976)
BYPASSES this catch entirely. Therefore: the confirm path's unresolved-tax rejection MUST be a
tagged THROW into the chain, never an early return.
</confirm_path_invariant>
</context>
