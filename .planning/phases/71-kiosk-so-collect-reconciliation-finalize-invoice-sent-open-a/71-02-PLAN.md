<objective>
Dead-code cleanup (NOT a money-path bug fix). Plan-check confirmed the `else` branch at `checkout.js:693` that books `salesorders_to_apply` is **unreachable**: the deposit-booking block at line 680 is guarded by `if (transactionId && depositAmount > 0 && soId)`, and `depositAmount` is only nonzero when `transactionId` is truthy (line 496) while `useInvoice = !!transactionId` (line 562). So entering the block guarantees `useInvoice === true` and the `else` never runs. It has been dead since the 2026-05-07 checkout refactor (commit f6d6e52dc). In the reachable path `soId` is itself the invoice id (line 584: `zohoEntity = useInvoice ? data.invoice : data.salesorder`; line 691: `invoice_id: soId`).

Because the branch is unreachable, there is no live orphaned-advance defect here to fix — the collect flow (71-01) was the real bug. This plan instead **removes the dead trap** so a future refactor that flips the `useInvoice` invariant cannot silently reintroduce the `salesorders_to_apply` orphaned-advance bug, and pins the deposit path's correct shape with a regression assertion.

Purpose: eliminate a latent orphaned-advance trap; make the invariant explicit and enforced.
Output: the dead else-branch removed and replaced with a loud invariant guard; a regression test asserting the deposit path only ever books via `invoices[]`; the reachability finding recorded in the SUMMARY.

Scope note (CONTEXT decision 4, "flag and scope out" fork): CONTEXT/PATTERNS treated checkout.js:693 as the same live bug as the collect path. Reachability analysis proves it is NOT live — so this is reframed from "sibling money-path fix" to "dead-code cleanup + documentation." Do NOT describe or commit this as a money-path bug fix. If, on reading the file, the cleanup looks riskier than a pure dead-branch deletion (unexpected reachability, shared control flow), STOP and reduce this plan to documentation-only: record the finding in the SUMMARY, make no code change, and say so.
