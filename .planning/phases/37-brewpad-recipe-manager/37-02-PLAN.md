<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BrewPad client → middleware writes | POST/PUT recipe writes from a shared iPad over `x-api-key` |
| Form/catalog input → DOM | Recipe metadata + ingredient names rendered into innerHTML |
| Client activation check → server authority | Inline guardrail is UX; server re-validates on PUT |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-04 | Information disclosure | `renderIngredientRows` / detail innerHTML | mitigate | Every group label, ingredient name, sku, and error string passes through `escapeHTML` before innerHTML (XSS via recipe name/notes/ingredient fields) |
| T-37-05 | Elevation of privilege | client-side Activate guardrail | mitigate | `canActivateRecipe` is UX-only; payload always carries `ingredient_count` so `PUT /api/recipes/:id` re-enforces `locked_price>0 AND ingredient_count>=1` server-side (recipes.js L399-412) and returns 422 — server is the authority (D-06) |
| T-37-06 | Tampering | save write path | mitigate | Writes send `x-api-key` via `getRecipesMwHeaders(true)`; reads send no key. Save throws on `!data.ok` so a rejected/partial write surfaces a toast, never a silent partial write |
| T-37-07 | Denial of service | offline write | accept | Network reject is caught and surfaced as a clear error toast; no client-side queue (per discretion) — fail-safe, no data loss |
| T-37-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages; reuses existing build/test deps |
</threat_model>
