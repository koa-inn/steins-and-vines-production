<objective>
Close the cancel/orphan-charge window found while diagnosing the latency ticket, wired to the path that is actually reachable. Today `/api/pos/cancel` → `helcimLib.cancelTerminal()` is a NO-OP; the client sets `cancelled = true` and its poll loop stops immediately (kiosk-core.js:2925), so a slow `terminalPurchase` that lands after cancel leaves the reader live with nobody polling. If the customer then taps, the card is charged with no invoice (orphan) until the reconcile backstop sweeps it up to 10 minutes later.

Critical correction from plan review: because the client stops polling on cancel, `/api/kiosk/sale/status` is NOT hit for the real scenario — the only channel that resolves the approved result regardless of the client is the Helcim **webhook** (`processCardTransactionResult`, webhooks.js:153, which already runs on every APPROVED event and calls the 45-08 reconcile backstop). So the fix lives there.

Mark-and-void (no new void path):
1. `/api/pos/cancel` records a KIOSK_CANCELLED_PREFIX + refNumber flag (client now sends the ref).
2. `processCardTransactionResult`'s APPROVED branch checks that flag; if the ref was cancelled, it voids the charge immediately via `moneyPath.voidWithTimeout` (amount from the existing KIOSK_PENDING_CHARGE record) and skips the normal booking/reconcile-as-usual — voided, never orphaned. This is strictly faster than reconcile.js's 600s guard, which stays unchanged as defense-in-depth.
3. Client: send the refNumber on cancel; gate the "tap card" prompt on the 202.

Output: KIOSK_CANCELLED_PREFIX, hardened `/api/pos/cancel` + webhook APPROVED path, safer client cancel + gated prompt, money-path-critical regression tests proving the void fires via the ACTUALLY-reachable webhook trigger.
</objective>
