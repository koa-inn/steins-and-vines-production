<objective>
Close the cancel/orphan-charge window found while diagnosing the latency ticket. Today `/api/pos/cancel` → `helcimLib.cancelTerminal()` is a NO-OP, and the client cancel handler sets `cancelled = true` and walks away — so a slow `terminalPurchase` that lands after cancel leaves the reader live with nobody polling/confirming; a customer tap then charges the card with no invoice (orphan) until the 45-08 backstop sweeps it up to 10 minutes later.

Fix with mark-and-void (no new void path):
1. `/api/pos/cancel` records a "cancelled" flag keyed by refNumber (new `KIOSK_CANCELLED_PREFIX`).
2. The path that resolves an approved terminal result (`/api/kiosk/sale/status`, and reachable via the webhook flow) checks that flag: an approved charge for a cancelled ref is routed through the existing `moneyPath.voidWithTimeout` (the single void path) — booked or voided, NEVER orphaned.
3. The client cancel handler sends the refNumber and no longer lets an already-approved charge be silently discarded by the `cancelled` guard.
4. Low-risk truthfulness: don't show "Tap, insert, or swipe card" until the 202 arrives.

The 45-08 reconciliation backstop stays as defense-in-depth — this is a strictly faster closure of the same window. No pipeline reorder (that's the deferred latency phase).
Output: hardened `/api/pos/cancel` + status path, `KIOSK_CANCELLED_PREFIX`, safer client cancel + gated prompt, and money-path-critical regression tests.
</objective>

- Mark-and-void, keyed by refNumber via a new `C.CACHE_KEYS.KIOSK_CANCELLED_PREFIX` (mirror KIOSK_PENDING_CHARGE_PREFIX). Fire-and-forget `cache.set(...).catch(()=>{})`, short TTL (cover the poll/webhook window, e.g. the terminal poll timeout + margin).
- Void ONLY through `moneyPath.voidWithTimeout(helcimLib, txnId, amount, { reqId })` — never call helcimLib.voidTransaction directly (audit H5/L18). It needs a real post-approval txnId, which is exactly why cancel-time can't void directly and must mark; the void fires when the approved result later resolves.
- `cancelTerminal()` (helcim.js:405): leave it as a bookkeeping/no-device-call function (Helcim has no documented in-flight-cancel endpoint distinct from reverse/void); do NOT make it silently call voidTransaction (no txnId at cancel time). Its return should stop implying the device was stopped.
- Reuse the response shape from pos-precharge-assertion's "void, never orphan" tests (payment_voided:true + voided_transaction_id) where an approved-after-cancel is surfaced, for consistency.
- Client: cancel handler must POST reference_number; and the status-poll approved branch must not be short-circuited to nothing by `cancelled` — an approved-after-cancel must still drive the server void (either by letting the confirm/void call proceed to a void, or by the server-side flag handling it) rather than being dropped on the floor.
- "Tap card" gating: set the terminal prompt text only after the 202 pending response, not before the fetch.
