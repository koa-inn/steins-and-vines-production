Inside `runCheckout` (the function that builds line items and creates the Zoho SO):

**a) Acquire lock to prevent concurrent redemption (RESEARCH.md Pitfall 1):**

Before the Redis redemption check, acquire a per-email lock to prevent two simultaneous checkout requests from double-burning the code:

```javascript
var promoDiscount = 0;
if (body.promo_code === 'FIRSTBATCH' && customerEmail) {
  var promoKey = C.CACHE_KEYS.PROMO_REDEEMED_PREFIX + customerEmail.toLowerCase();
  var lockKey = C.CACHE_KEYS.PROMO_REDEEMED_PREFIX + customerEmail.toLowerCase();

  // Acquire lock to prevent concurrent double-burn (RESEARCH.md Pitfall 1)
  var lockAcquired = false;
  try {
    lockAcquired = await cache.acquireLock(lockKey, 30);
  } catch (e) {
    // Lock acquisition failed — fail open (allow through)
    lockAcquired = true;
    log.warn('[checkout] Promo lock acquisition failed, proceeding: ' + e.message);
  }

  // Re-validate: check Redis to confirm not already redeemed
  try {
    var promoExisting = await cache.get(promoKey);
    if (!promoExisting) {
      promoDiscount = 20;
    } else {
      log.warn('[checkout] Promo code FIRSTBATCH rejected — already redeemed by ' + customerEmail);
    }
  } catch (e) {
    // Fail open — allow discount if Redis unavailable
    promoDiscount = 20;
    log.warn('[checkout] Promo Redis check failed, allowing discount: ' + e.message);
  }
}
```

The `cache.acquireLock(key, 30)` uses Redis `SET NX EX 30` internally. If the lock is already held by a concurrent request, `acquireLock` returns `false` -- but we treat that as "another checkout is already processing this email's promo" and proceed normally (the first request will burn, the second will see the redeemed key). If Redis is down, `acquireLock` returns `true` (fail-open, matching the established pattern). The 30-second TTL auto-expires the lock if the request crashes.
