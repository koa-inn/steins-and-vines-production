**2. Create `zoho-middleware/routes/promo.js`:**

New route file following the `discounts.js` scaffold pattern. Two endpoints:

**POST /api/promo/validate** (public, no API key required):
- Extract `body.code` (string, trim + toUpperCase) and `body.email` (string, trim + toLowerCase)
- Validate: return 400 if code is empty (`{ error: 'Promo code is required.' }`)
- Validate: return 400 if email is empty or lacks `@` (`{ error: 'A valid email address is required to use a promo code.' }`)
- Validate: return 400 if `code !== 'FIRSTBATCH'` (`{ error: 'That promo code isn\'t valid.' }`)
- Check Redis: `cache.get(C.CACHE_KEYS.PROMO_REDEEMED_PREFIX + email)`
- If value exists: return 400 `{ error: 'This code has already been used for this email address. Each code is one use per customer.' }`
- If null (not redeemed): return 200 `{ ok: true, discountPct: 20, code: 'FIRSTBATCH' }`
- On Redis error: fail open -- return 200 `{ ok: true, discountPct: 20, code: 'FIRSTBATCH' }` and log error with `[promo/validate]` prefix
- Constants at top of file: `var PROMO_CODE = 'FIRSTBATCH';` and `var PROMO_DISCOUNT_PCT = 20;`

**DELETE /api/promo/redemption/:email** (requires API key -- standard middleware protection):
- Extract `req.params.email`, trim + toLowerCase
- Validate: return 400 if empty or lacks `@`
- Call `cache.del(C.CACHE_KEYS.PROMO_REDEEMED_PREFIX + email)`
- Return 200 `{ ok: true, email: email, message: 'Redemption cleared' }`
- On error: return 500 `{ error: 'Failed to clear redemption' }` and log with `[promo/reset]` prefix

Full file structure:

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> /api/promo/validate | Untrusted user input (code, email) crosses from public client to server |
| Browser -> /api/promo/redemption/:email | Admin-only DELETE endpoint protected by API key |
| Server -> Redis | Trusted internal boundary for redemption state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01 | Spoofing | /api/promo/validate | mitigate | Rate limit via existing express-rate-limit on /api; email required at validate time per D-08; redemption burned server-side only after SO creation per D-09 |
| T-08-02 | Tampering | /api/promo/validate body | mitigate | Server extracts and normalizes code/email from body with type guards; never trusts client-supplied discount values in checkout (C3 constraint enforced in Plan 02) |
| T-08-03 | Repudiation | Redemption burn | accept | Redis stores redeemedAt timestamp + soId; sufficient for promo audit trail; low-value target |
| T-08-04 | Information Disclosure | Error messages | mitigate | Error messages do not reveal whether an email exists in the system -- only whether the specific code+email combo was redeemed |
| T-08-05 | Denial of Service | /api/promo/validate | mitigate | Existing rate limiter on /api mount protects against brute-force; fail-open on Redis down means no availability impact |
| T-08-06 | Elevation of Privilege | DELETE /api/promo/redemption/:email | mitigate | DELETE endpoint requires x-api-key header (standard API key middleware); not exempt from API key check |
</threat_model>
