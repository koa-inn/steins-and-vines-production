<objective>
Close audit finding **H2 / MONEY-01**: online `/api/checkout` currently records a Zoho customerpayment for the SERVER-recomputed invoice total and marks the invoice paid-in-full **without ever comparing the amount actually captured on the card**. A tampered `POST /api/payment/initialize {amount: 0.01}` followed by a real order therefore books a $280 invoice as fully paid against a $0.01 capture — a silent reconciliation hole.

The fix: after the Zoho invoice total is resolved (`checkout.js:~585`) and BEFORE any side-effect (inventory decrement, emails) or the customerpayment recording (`~588`/`~623`), read the ACTUAL captured amount via `helcimLib.getCardTransactionById(transactionId)` and assert `captured >= depositAmount` within a ±$0.01 tolerance. On a short capture — or when the amount cannot be verified — throw a tagged error so the EXISTING catch block voids the charge via `moneyPath.voidWithTimeout` (NOT raw `voidTransaction`) and returns a 4xx. Do not introduce a second void path.

Purpose: the books must never say paid-in-full for a charge that did not cover the invoice; nothing internal flags this today.
Output: TDD RED→GREEN — a failing H2 regression suite, then a surgical verification in `checkout.js` that makes it pass with every existing money-path test still green.

Honesty caveat (preserve, do not overstate): this requires ACTIVE client tampering, is the online path only (`checkout.js`, not the kiosk `pos.js` path), and Helcim↔Zoho settlement reconciliation would eventually surface it manually — but the books say paid-in-full so nothing internal flags it, and the fix is cheap. Keep the change surgical.
</objective>

lib/helcim.js — getCardTransactionById(id) resolves:
  { status: string (UPPERCASED, e.g. 'APPROVED'), transactionId: string,
    invoiceNumber: string, cardType: string, amount: number }
  - `amount` is in DOLLARS (same units as depositAmount; e.g. 280.00), sourced from txn.amount.
  - REJECTS (Promise.reject) on API/network error — callers can distinguish failure from a response.
  - Requires the Helcim token's card-transactions READ scope. This same call is the live-verified
    primary path for the terminal webhook handler (STATE decision 36-20 / F2), so read scope is present
    in prod; the ONLINE HelcimPay txn readback is confirmed live in plan 49-02.

lib/money-path.js — voidWithTimeout(helcimLib, token, amount, opts) → Promise<void>
  - Wraps helcimLib.voidTransaction in an 8s timeout; logs + mailer alert on non-timeout failure.
  - This is the ONLY sanctioned void path (raw helcimLib.voidTransaction is forbidden here — audit H5/L18).

routes/checkout.js current shape (grounding for the edit):
  - line ~479 / ~583: `depositAmount` = Zoho invoice `total` (tax-inclusive) once the invoice is created.
  - line ~588–616: fire-and-forget side effects (inventory decrement, staff/customer email, batch create).
  - line ~623–643: records the Zoho `/customerpayments` (marks invoice paid). Wrapped in try/catch that
    only logs — payment-record failure is currently non-fatal.
  - line ~703 catch: computes `status` (default 502; 503 for isSnapshotFallback; 400 when err.response is a
    Zoho 4xx), then runs the dual-cart void guard and `moneyPath.voidWithTimeout`.
  - Dual-cart: one transactionId is shared across cart_key `sv-cart-ferment` + `sv-cart-ingredients`;
    each call creates its OWN invoice for its OWN portion and marks that portion used
    (`helcim:txn:<txn>:<cart_key>`). The catch's dual-cart guard skips the void when the OTHER leg already
    succeeded (would reverse the whole shared charge).
