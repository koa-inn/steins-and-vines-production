<objective>
Run Spike S1 from 92-RESEARCH.md "Open Questions": one read-only look at the live Zoho payments list, invoice list and invoice detail shapes through the staging middleware's own credentials, and commit a sanitized fixture.

Purpose: The D-14 tender join (one customer-payments query per ledger day, joined to the invoices) and the D-01 in-store classifier rule (b) (payment notes) both depend on RESEARCH assumptions A1-A5, which no code in this repo has ever exercised (`GET /customerpayments` has never been called). This plan replaces those assumptions with recorded facts before 92-03 writes the join.
Output: spike script (committed as a STAGING-ONLY read-only dev tool), sanitizer test, sanitized fixture with `_meta` findings.

Join-mode rule (linkage AND notes, both must be proven by the spike):
- `list-join`: payments list rows carry an invoice linkage AND the money-path note text. D-14 as written (one payments query per day, joined).
- `detail-fallback`: the list lacks linkage or notes, but invoice-detail `payments[]` carries the note text. Tender and SO-pay classification come from capped, sequential invoice-detail fetches. This deviates from D-14's "do not make one call per invoice".
- `none`: no readable payment note text in either place. SO-pay invoices (blank reference) cannot be told from back-office invoices, so D-01 cannot be met as written.
Because `detail-fallback` and `none` change what the owner decided (D-14 / D-01), this plan ends in an owner decision gate (Task 3) that pauses ONLY when join_mode is not `list-join`. 92-03 must not build on an unapproved deviation.
</objective>
