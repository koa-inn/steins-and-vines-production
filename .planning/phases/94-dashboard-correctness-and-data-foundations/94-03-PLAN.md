<objective>
Set `batch_type` on create for every path through the single Postgres create choke point.

Purpose: D-08 — new batches never need a backfill; unknown types never block a sale (D-07).
Output: modified `batch-pg-create.js` and `batch-store.js` create, real-PG and unit tests.

**Known gap (documented, by design):** create-time rule 2 reads only the kiosk Redis cache (`zoho:kiosk-products`, 30 min TTL,
sellable items only). The B3 backfill (plan 06) uses a live `fetchAllItems()`. A SKU that is not in the kiosk cache, or a cold cache,
therefore classifies by schedule/name/other at create but by Zoho at backfill. Mitigations: (1) a cache miss never blocks or delays the
create (D-07; tested below); (2) plan 04 re-derives name/other rows when a schedule or recipe is attached; (3) the plan 06 backfill
upgrades NULL/name/other rows when a higher-precedence rule now matches, and never touches manual (D-06); (4) leftovers appear on the
Needs-a-type list (D-07). Not adding a live Zoho call to create is deliberate: it would put a network call on the sale path.

**Build precondition (D-01, not a task):** only after the Phase 87 production cutover is recorded in
`87-CUTOVER-LOG.md`; otherwise stop and report `blocked: D-01`. Postgres store only; sheets mode is untouched.
</objective>
