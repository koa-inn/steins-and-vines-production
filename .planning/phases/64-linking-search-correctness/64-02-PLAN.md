<objective>
Close feedback #10 / OPS-03 success-criterion #2: deleting a batch leaves the linked Zoho
invoice's `cf_batch_status` stranded (INV-000151 held "Pending — SV-B-000185" for a batch that
no longer exists). Deletes flow browser → Apps Script `delete_batch` (`js/brewpad.js:5664` admin
detail, `:7998` Needs-Scheduling) and never touch the middleware, so the invoice field is never
cleaned. `cf_batch_status` is WRITTEN by the middleware (`brewpad-integration.js:478
syncBatchToZoho` → `zohoPut('/invoices/{id}', custom_fields)`), so the fix lives middleware-side.

Two connected deliverables, one core:
1. **Delete-hook (ongoing):** after a successful `delete_batch`, the frontend calls a new
   middleware endpoint with the deleted batch's `zoho_so_number`; the middleware re-derives the
   correct `cf_batch_status` from the batches that STILL exist for that invoice (clear if none).
2. **One-time stale-ref cleanup (existing INV-000151 class):** a bounded, observable route
   (dry-run first) that pages recent invoices, cross-checks each `cf_batch_status` against the
   live batch set, and clears/reports stale refs.

Both share one core helper. No Apps Script change is required: the middleware already reads the
live batch set via `get_batches` + `server_token` (the dedup pattern at `pos.js:2484-2497`) and
writes the invoice field via `zohoPut`.

Both halves are regression-tested: middleware (reconcile core + routes) AND frontend (both
delete sites wire the hook correctly, fire-and-forget).

Purpose: the "unlinked" and status fields stop lying; deleted batches can't strand references.
Output: reconcile core + two routes + frontend hook on both delete sites + rebuilt bundle +
middleware and frontend regression tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BrewPad browser → POST /api/batch/reconcile-* | authenticated staff (legacy/session); untrusted zoho_so_number / dry_run flag |
| middleware → Apps Script get_batches | server_token-authenticated read of the live batch set |
| middleware → Zoho Books zohoPut | outbound write mutating invoice custom fields (prod) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-64-04 | Tampering | reconcile route mutates invoice custom fields | mitigate | Gated to `['legacy','session']` tiers; only ever writes cf_batch_status; the value is derived server-side from the live batch set (never client-supplied); no-op when already correct |
| T-64-05 | Denial of Service | cleanup scan fan-out over invoices | mitigate | Hard MAX_PAGES cap (never request-controlled); dry-run default true so an accidental call reads-only |
| T-64-06 | Repudiation | bulk mutation of prod invoices with no record | mitigate | Route returns a per-invoice report [{invoice_number, action, old, new}]; eventLog entries on writes; blocking human checkpoint gates the one-time apply |
| T-64-07 | Elevation of privilege | delete-hook lets a caller clear arbitrary invoices' status | accept | Caller can only pass a zoho_so_number; the field is re-derived from the live batch set, so the worst case is re-syncing a field to its correct value; auth-tier gated |
</threat_model>
