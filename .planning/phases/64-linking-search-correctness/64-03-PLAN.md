<objective>
Close feedback #7 / OPS-03 success-criterion #3: `adminApiGet` builds
`ADMIN_API_URL + '?action=...&token=' + encodeURIComponent(accessToken)` (`js/brewpad.js:1285`,
and identically `js/admin.js:681`), placing the Google OAuth access token in the URL query string
where it lands in any intermediary/proxy/access log. Move the token into the POST body, matching
the `adminApiPost` precedent (`brewpad.js:1306` sets `payload.token = accessToken` in the body).

Verified constraint (why this is cross-repo): Apps Script `doGet(e)` cannot read request headers,
so a header is not viable — the token must go in a POST body. `checkAuthorization(e)` ALREADY reads
the token from the POST body (`adminApi.gs:445-455`), BUT `doPost`'s OAuth-authenticated switch
(`adminApi.gs:313`) only handles WRITE actions — the READ actions (get_batch, get_batches, etc.)
live only in `doGet`'s switch (`adminApi.gs:128-213`). So switching adminApiGet to POST requires
adding read-action routing to `doPost`. This is an Apps Script change → **manual owner redeploy**
(no CI for `.gs`; verified anti-pattern from STATE — Apps-Script-crossing changes must be exercised
against the live system).

Scope note (surfaced, decided): the identical leak exists in BOTH `brewpad.js` and `admin.js`
adminApiGet (two separate defs, same ADMIN_API_URL). Fixing only one leaves SC#3 half-true, and the
enabling Apps Script change is shared, so BOTH are migrated here as one logical change.

CRITICAL deploy ordering: the Apps Script read-routing MUST be live in prod BEFORE the frontend
POST change ships — otherwise every BrewPad/admin read breaks. The `.gs` change is backward
compatible (doGet untouched), so deploying it first cannot break the current (GET) frontend.

RED-first discipline (CLAUDE.md rule 3): the regression test is pure client-side (mocked fetch,
no Apps Script dependency), so it is authored and RED-run FIRST — before any code changes — then
proven GREEN immediately after the frontend fix, mirroring 64-01's ordering.

Out of scope (surfaced for the owner as a separate concern, NOT fixed here): `admin.js:8137/8148`
and `kiosk-core.js:3074` embed a token in a shareable `batch.html?...&token=` URL — that is the
public batch-view token path, distinct from adminApiGet; flag it, don't touch it in this phase.

Purpose: the short-lived OAuth token stops leaking into URL logs.
Output: shared read-dispatch in adminApi.gs + POST-body adminApiGet on both surfaces + rebuilt
bundles + a RED-first regression test, sequenced behind an owner Apps Script redeploy.
</objective>
