<objective>
Add a first-class "Ready to Bottle" filter to the BrewPad batch view (owner ticket #3), so staff no
longer proxy it with the imprecise "secondary" status filter.

Membership reuses the SINGLE source of truth already computed by the server: a batch is Ready-to-Bottle
iff its `batch_id` is in `_dashSummary.readyToBottle` (adminApi.gs:1847-1883). Implement as a new pure
sibling function next to `filterBatchesByStatus` (js/brewpad.js:188) that intersects `_allBatchesData`
with the `readyToBottle` batch_ids — DO NOT re-derive the packaging-due predicate client-side (the
batch-list payload lacks the per-task/packaging fields). The count chip ("Ready to Bottle (N)") reads
`_dashSummary.readyToBottle.length`. Because 69-01 makes task writes refetch `_dashSummary`, this filter
stays fresh automatically.

This plan also makes a small enabling refactor: loadDashboard() (js/brewpad.js:2817) currently returns undefined, so the "filter selected before the dashboard is loaded" path must be able to chain on it — Task 2 adds a `return` so it yields the fetch thenable (safe: all existing callers are fire-and-forget).

Purpose: precise, one-tap access to the exact bottling workload that matches the dashboard section.
Output: updated js/brewpad.js (+ rebuilt js/brewpad.min.js), new unit tests in brewpad-pure.test.js.

Depends on 69-01 (both edit js/brewpad.js — sequential waves avoid worktree merge conflicts; 69-02 also
inherits 69-01's refetch so the filter reflects task completions immediately).
</objective>
