## Summary

Reviewed the phase 29.2 diff (`e7a54de..HEAD`) covering the `todayPacific()` helper, the status-badge pending guard, the Needs Scheduling row Activate / Schedule & Activate buttons and their delegation handlers, the `buildScheduleActivateSheetHtml` / `openScheduleActivateSheet` / `closeScheduleActivateSheet` sheet, the pending-only detail-pane buttons, and the new test file. Supporting code (`adminApiPost`/`adminApiGet`, `showConfirmSheet`, `callSyncZoho`, `reloadSchedules`, `renderBatchDetail`, and the Apps Script `updateBatch` / `updateBatchSchedule` / dashboard-summary handlers in `apps-script/adminApi.gs`) was cross-referenced to verify contracts.

ESLint reports 0 errors (14 pre-existing `eqeqeq` warnings, none in the new code). The new test file passes, but most of its tests are tautological (see WR-06).

Two blockers were found: the detail-pane Activate success path calls `renderBatchDetail()` with the wrong argument shape (blanking the detail pane after a successful activation), and the Needs Scheduling Activate button plumbs an optimistic-lock version from a field the server never sends, silently disabling concurrency protection and risking lost updates.

## Critical Issues

### CR-01: `renderBatchDetail(b)` called with the wrong argument shape — detail pane renders empty after one-click Activate

**File:** `js/brewpad.js:2611`
**Issue:** `renderBatchDetail(data)` expects `data = { batch, tasks, plato_readings }` (line 2270: `var b = data.batch || {}`). Every other call site (lines 1718, 1726, 1756) passes the `get_batch` response `data` wrapper. The new pending-detail Activate success handler passes the bare batch object `b`. Inside the re-render, `data.batch` is `undefined`, so the function renders an empty batch (`batch_id` undefined, blank header/status, all tasks and plato readings dropped) and corrupts module state (`_detailBatchId = undefined`, `_currentBatchDetail = {}`). The user activates a batch successfully and is rewarded with a broken detail pane.
**Fix:** The handler runs inside `renderBatchDetail`'s closure, where the original `data` argument is still in scope and `b` is a reference to `data.batch` (already mutated to `status: 'primary'`). Replace:
```js
renderBatchDetail(b);
```
with:
```js
renderBatchDetail(data);
```
(or better, re-fetch via `adminApiGet('get_batch', { batch_id: b.batch_id })` so tasks/version are fresh — see WR-02).

### CR-02: Optimistic locking silently disabled for Needs Scheduling Activate — `it.last_updated` does not exist

**File:** `js/brewpad.js:1130` (markup), `js/brewpad.js:5104-5115` (handler); root data at `apps-script/adminApi.gs:1733-1741`
**Issue:** The Needs Scheduling row renders `data-version="' + escapeHTML(it.last_updated || '') + '"`, and the delegation handler sends it as `expectedVersion`. But the dashboard-summary builder in `adminApi.gs` (lines 1733–1741) only emits `batch_id`, `product_name`, `customer_name`, `source`, `zoho_so_number`, and `created_at` for `needsScheduling` items — there is no `last_updated` field. So `data-version` is always `""`, and on the server `updateBatch` skips the lock entirely (`if (payload.expectedVersion)` at adminApi.gs:2090 is falsy for `''`). The version guard the code is clearly built around can never fire from this entry point. Consequence: if another user just Schedule-&-Activated the same batch (e.g., with a future start date and vessel assignment), this one-click Activate silently overwrites `status` and resets `start_date` to today — a lost-update / data-loss path with no warning. The same hole exists in the `nsSaBtn` fallback (`{ batch_id: bid2 }` at line 5145 has no `last_updated`, so step 1 of the sheet flow also skips the lock).
**Fix:** Add the version to the summary payload in `adminApi.gs`:
```js
needsScheduling.push({
  batch_id: bid,
  ...
  created_at: b.created_at || '',
  last_updated: b.last_updated || ''
});
```
Alternatively (frontend-only fix), have the `nsActivateBtn` handler resolve the batch from `_allBatchesData` (as `nsSaBtn` does) and use its `last_updated`, failing closed (re-fetch via `get_batch`) when unavailable.

## Warnings

### WR-01: `reloadSchedules()` does not return its promise — the empty-schedules guard always falls into a 400 ms race

**File:** `js/brewpad.js:4784-4794` and `js/brewpad.js:3839-3851`
**Issue:** `openScheduleActivateSheet` guards against an empty `_fermSchedules` by calling `reloadSchedules()` and waiting on its promise — but `reloadSchedules` has no `return` statement, so `reloadProm` is always `undefined` and the code always takes the `setTimeout(..., 400)` fallback. Apps Script GET calls routinely take 1–3 s, so when schedules haven't loaded (eagerLoad failure, expired session re-entry), the sheet opens with only the "— Select a schedule —" placeholder and never refreshes; the user must close and reopen. The promise branch is dead code, and the comment ("reloadSchedules may not return a promise") shows the gap was known and papered over with a guess.
**Fix:** Make `reloadSchedules` return the chain:
```js
function reloadSchedules() {
  return adminApiGet('get_ferm_schedules')
    .then(...)
    .catch(...);
}
```
Then delete the `setTimeout` fallback branch.

### WR-02: `newVersion` from `update_batch` is never written back to `b.last_updated` — subsequent operations hit spurious version conflicts

**File:** `js/brewpad.js:2521-2543` (badge pending guard), `js/brewpad.js:2594-2612` (detail Activate)
**Issue:** `updateBatch` returns `{ ok: true, newVersion: now }` (adminApi.gs:2228), and the server's conflict rule is `serverTime > clientTime`. Both new activation paths ignore the response and leave `b.last_updated` at its pre-activation value. The batch object stays live as `_currentBatchDetail` (and in the badge path the detail pane is not re-rendered at all), so any later expectedVersion-checked operation against this object — e.g., the Refresh-from-Zoho flow at line 2728 which sends `expectedVersion: batchVersion` — gets a false "Batch was modified by another user" error until the user manually reloads. The existing code at lines 2732–2733 demonstrates the correct pattern (`_currentBatchDetail.last_updated = result.newVersion`).
**Fix:** In both `.then(function (result) {...})` handlers, add:
```js
if (result && result.newVersion) { b.last_updated = result.newVersion; }
```

### WR-03: Stale detail pane after badge-path and sheet-path activation — pending-only buttons remain live on a now-active batch

**File:** `js/brewpad.js:2521-2546` (badge pending guard), `js/brewpad.js:3795-3815` (SA sheet success)
**Issue:** The badge pending guard updates the badge element and the list, but never re-renders the detail pane, so `#bp-activate-detail-btn` and `#bp-sa-detail-btn` (rendered only for `statusKey === 'pending'`) stay visible and enabled on a batch that is now `primary`. Likewise, when Schedule & Activate is opened from the detail footer and succeeds, the success handler refreshes the dashboard (`loadDashboard()`) but leaves the open detail pane showing the pending state. Clicking the leftover Activate button re-submits activation with a stale `expectedVersion` and surfaces a confusing "Batch was modified by another user" error (or, combined with CR-02-style empty versions, silently re-writes `start_date`).
**Fix:** In the badge pending success handler, re-render the detail with the in-scope wrapper: `renderBatchDetail(data);`. In the SA success handler, if `_selectedBatchId === b.batch_id`, re-fetch and re-render the detail (or close the detail pane) after `loadDashboard()`.

### WR-04: Zoho SO sync (`callSyncZoho`) missing from the Needs Scheduling Activate handler and the entire Schedule & Activate flow

**File:** `js/brewpad.js:5104-5127` (ns Activate), `js/brewpad.js:3795-3833` (SA submit)
**Issue:** The badge pending guard (line 2533) and the detail Activate button (line 2601) both call `callSyncZoho(b.batch_id, b.zoho_so_number, 'active')` after activation, keeping the linked Zoho sales order in sync. The Needs Scheduling row's one-click Activate and the Schedule & Activate sheet (both entry points) never call it. The same logical operation has different side effects depending on which button the user happens to press: batches activated from the dashboard row or via the guided sheet leave the Zoho SO status stale. The data is available — `needsScheduling` items carry `zoho_so_number` (adminApi.gs:1739) and the SA sheet receives the full batch object.
**Fix:** After the `update_batch` success in the ns Activate handler, look up the row in `_dashSummary.needsScheduling` (or `_allBatchesData`) and call `callSyncZoho(bid, item.zoho_so_number, 'active')`. In the SA flow, call `callSyncZoho(b.batch_id, b.zoho_so_number, 'active')` once step 1 resolves (including the step1Done partial-failure branch — the batch is active in that case too).

### WR-05: SA sheet submits an empty `schedule_snapshot` when schedule steps fail to parse — batch activates with 0 tasks despite a selected schedule

**File:** `js/brewpad.js:3771-3775` and `js/brewpad.js:3803-3806`
**Issue:** If the selected schedule has no `steps_parsed` and `JSON.parse(sched2.steps)` throws (the catch swallows the error), `schedSteps` remains `[]`. The submit proceeds anyway: server-side, `!payload.schedule_snapshot` is false for an empty array (adminApi.gs:2283), so the batch's `schedule_snapshot` is overwritten with `[]` and 0 tasks are created. The user explicitly picked a schedule but ends up with an activated batch that has none — the only hint is the "activated with 0 tasks scheduled" toast. The same parse-failure path also silently renders an empty preview (line 3712-3714).
**Fix:** Validate before submitting:
```js
if (!schedSteps.length) {
  showToast('Selected schedule has no steps — edit the template first', 'error');
  return;
}
```

### WR-06: New tests are tautological — they assert on local literals, not the implementation

**File:** `tests/frontend/brewpad-activation.test.js:70-155`
**Issue:** The "needs scheduling activation markup" tests (lines 70–92) check that a hard-coded local array contains the strings it was just defined with — they never touch `js/brewpad.js`, so renaming `bp-needsched-activate-btn` in the source cannot fail them, directly contradicting their stated purpose ("a later refactor that renames them will fail these tests"). The same applies to the `bp-sa-*` id-set test (lines 101–127, asserts membership/length of a local literal) and the `step1Done routing` test (lines 133–155), which re-implements the branch logic inline via a local `routeStep` function instead of exercising the real handler — if the real `.catch` routing in `openScheduleActivateSheet` regresses, this test stays green. Only the `todayPacific` and `escapeHTML` tests exercise exported code. The suite provides false regression confidence for the exact contracts it claims to pin.
**Fix:** Export the testable pieces and assert against them, e.g. export `buildScheduleActivateSheetHtml` and assert the produced HTML contains `id="bp-sa-schedule-select"` etc.; render the Needs Scheduling row builder with a fixture item and assert the emitted classes; extract the step1Done routing into a pure exported helper (`classifyActivationError(step1Done, message)`) used by the handler and tested directly.

### WR-07: `sv-bp-batch-*` sessionStorage cache not invalidated by the SA flow or the Needs Scheduling Activate handler

**File:** `js/brewpad.js:3795-3815` (SA success and partial-failure branches), `js/brewpad.js:5104-5127` (ns Activate)
**Issue:** Every other batch-mutation path in the file removes the per-batch detail cache after a write (lines 1995, 2131, 2236, 2496, 2543, 2577, 2610, 2775, 2862...). The new SA sheet flow and the Needs Scheduling one-click Activate do not. Reopening the batch detail within the cache TTL first renders the cached pending version — complete with live Activate / Schedule & Activate buttons and a stale `last_updated` — before the silent background refresh corrects it. A fast user can click the stale Activate button in that window (spurious re-activation attempt / conflict toast).
**Fix:** Add to both success paths (and the SA `step1Done` partial-failure branch, since the batch did change):
```js
try { sessionStorage.removeItem('sv-bp-batch-' + b.batch_id); } catch (e) {}
```

## Info

### IN-01: Double-escaped confirm message in the detail Activate path

**File:** `js/brewpad.js:2590`
**Issue:** `showConfirmSheet` assigns the message via `textContent` (line 1781), so passing `escapeHTML(b.batch_id)` double-escapes: a batch id containing `&` would display as `&amp;`. The badge path (line 2522) and ns handler (line 5106) correctly pass raw strings. Cosmetic with `SV-B-NNNNNN` ids, but the inconsistency invites confusion about which sink escapes.
**Fix:** Drop `escapeHTML()` here: `'Activate ' + b.batch_id + ' now? ...'`.

### IN-02: `todayPacific(offsetDays)` is DST-unsafe for offset arithmetic

**File:** `js/brewpad.js:19-22`
**Issue:** `Date.now() + offsetDays * 86400000` assumes 24-hour days. Across America/Vancouver DST transitions, calling near midnight can skip or repeat a calendar day (e.g., 23:30 PST on spring-forward eve, `todayPacific(1)` lands two calendar days ahead). The offset parameter is currently only exercised by tests, but the helper is exported and will be reused.
**Fix:** Compute the Pacific date string first, then offset via UTC-noon arithmetic on the parsed `YYYY-MM-DD`, or document the limitation.

### IN-03: Backdrop click listener accumulates on `#bp-sa-sheet` across reopen cycles

**File:** `js/brewpad.js:3653-3658`
**Issue:** Each `openScheduleActivateSheet` call adds a new `handleSaBackdrop` listener to the persistent sheet element; the listener only removes itself when a backdrop click fires. Closing via the X button (or after submit) leaves it attached, so reopening stacks duplicates. Harmless today (all duplicates call the idempotent close), but it is a slow listener leak and a foot-gun if close ever gains side effects.
**Fix:** Attach the backdrop listener once, inside the `if (!sheet)` creation branch, and never remove it.

### IN-04: `nsSaBtn` can remain permanently disabled after the get_batch fallback succeeds

**File:** `js/brewpad.js:5142-5146`
**Issue:** In the fallback path, `nsSaBtn.disabled = true` is set before `get_batch`; on success the sheet opens but the button is never re-enabled. If the user cancels the sheet without submitting, the row's Schedule & Activate button stays dead until the next dashboard re-render.
**Fix:** Re-enable in the success handler: `.then(function (r) { nsSaBtn.disabled = false; openScheduleActivateSheet(...); })`.
