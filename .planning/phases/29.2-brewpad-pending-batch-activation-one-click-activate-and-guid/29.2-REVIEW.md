## Summary

Re-review of the phase 29.2 diff (`e7a54de..HEAD`) after gap-closure plans 29.2-04 and 29.2-05: one-click Activate and guided Schedule & Activate for pending batches across three entry points (dashboard Needs Scheduling row, detail-pane status badge, detail-pane footer), the new `bp-sa-*` bottom sheet, the `todayPacific()` helper, the `last_updated` emission in `getBatchDashboardSummary()`, and the new test suite. Supporting code (`adminApiPost`/`adminApiGet`, `showConfirmSheet`, `reloadSchedules`, `renderBatchDetail`, `getBatches`, `getBatchDetail`, and the Apps Script `updateBatch`/`updateBatchSchedule` handlers) was cross-referenced to verify contracts.

**Prior-review fix verification (both confirmed present and sound):**

- **CR-01 (fixed):** `js/brewpad.js:2611` now calls `renderBatchDetail(data)` with the `{batch, tasks, plato_readings}` wrapper. `data` is the enclosing `renderBatchDetail` parameter and `b === data.batch`, so the in-place `b.status = 'primary'` mutation is reflected on re-render and the pending-only footer buttons correctly disappear. The regression test reads the actual source — adequate. However, the parallel status-badge activation path was not given the same treatment (see WR-03).
- **CR-02 (fixed):** `apps-script/adminApi.gs:1741` emits `last_updated: b.last_updated || ''` in the needsScheduling summary. The format is compatible with `updateBatch`'s comparison (`adminApi.gs:2091-2099` parses both sides via `new Date(...).getTime()`; equal timestamps pass; tolerance direction is safe if Sheets truncates precision). Empty value fails open by design. Apps Script deploy human-confirmed per plan 29.2-05.

**Build artifact verified:** `js/brewpad.min.js` is byte-identical to a fresh `terser js/brewpad.js -c -m` rebuild (151,966 bytes), and the last min.js commit (`1dfce81`) matches the last source commit. `brewpad.html` cache stamp present (`?v=mqbo6a1h`). ESLint: 0 errors; the 14 `eqeqeq` warnings are all in pre-existing code outside the phase diff. Tests: 16/16 pass.

**Security:** All interpolations in the new Needs Scheduling row buttons, the `bp-sa-*` sheet HTML, and the schedule preview pass through `escapeHTML`. `showConfirmSheet` renders messages via `textContent` (no injection sink). Optimistic locking blocks double-activation races on every path that carries a version. No new security issues found.

The remaining findings are correctness/robustness gaps in the new flows — most notably a broken schedules-preload guard, silent activation with zero tasks when a template's steps fail to parse, and two stale-UI paths the CR-01 fix did not extend to.

## Warnings

### WR-01: Schedules-preload guard is dead code — sheet races a fixed 400ms timer against an Apps Script round trip

**File:** `js/brewpad.js:3839-3849` (guard) and `js/brewpad.js:4784-4794` (`reloadSchedules`)
**Issue:** `openScheduleActivateSheet` checks `if (reloadProm && typeof reloadProm.then === 'function')`, but `reloadSchedules()` has no `return` statement — it always returns `undefined`, so the promise branch is unreachable dead code. The `setTimeout(_buildAndShow, 400)` fallback always runs instead. Apps Script GET latency is routinely 500ms–3s, so whenever `_fermSchedules` is empty at click time (startup eager-load at line 963 failed, or returned zero templates), the sheet opens with only the "— Select a schedule —" placeholder and never updates when the fetch completes. The user is hard-stuck: submit shows "Please select a schedule" with no recovery except closing and reopening. The "Pitfall 4" comment shows this was a known risk, but the mitigation does not work.
**Fix:** Make `reloadSchedules` return its promise chain:
```js
function reloadSchedules() {
  return adminApiGet('get_ferm_schedules')
    .then(function (r) { /* existing body */ })
    .catch(function (err) { /* existing body */ });
}
```
Then delete the `setTimeout` fallback branch in `openScheduleActivateSheet`. Existing call sites are fire-and-forget and unaffected by the added return.

### WR-02: Schedule & Activate proceeds with zero steps when the template's `steps` JSON fails to parse — activates with a success toast and no tasks

**File:** `js/brewpad.js:3766-3770, 3800-3811`; server guard at `apps-script/adminApi.gs:2284`
**Issue:** If `sched2.steps_parsed` is empty and `JSON.parse(sched2.steps)` throws, the error is swallowed (`catch (eparse2) {}`) and `schedSteps` stays `[]`. The flow submits anyway: step 1 activates the batch, step 2 calls `update_batch_schedule` with `schedule_snapshot: []` — an empty array is truthy, so the server's `!payload.schedule_snapshot` guard does not reject it — which writes `'[]'` to `schedule_snapshot`, creates 0 tasks, and surfaces "Batch activated with 0 tasks scheduled" styled as success. Staff selected a named schedule expecting tasks; the batch silently ends up scheduleless.
**Fix:** Validate before submitting:
```js
if (!schedSteps.length) {
  showToast('Selected schedule has no steps — fix the template or use plain Activate', 'error');
  return;
}
```

### WR-03: Status-badge pending activation leaves stale pending-only footer buttons and stale `b.last_updated` — same bug class as CR-01, missed on this path

**File:** `js/brewpad.js:2518-2547`
**Issue:** The badge-click pending branch updates the badge in place and refreshes the list, but never re-renders the detail pane. Because the pane was rendered while `statusKey === 'pending'`, the footer "Activate" and "Schedule & Activate" buttons remain visible and live on a now-active batch, holding the now-stale `b.last_updated`. Clicking footer "Activate" afterwards fires `update_batch` with the stale `expectedVersion` and yields "Failed: Batch was modified by another user…"; clicking "Schedule & Activate" opens the sheet and step 1 fails with "Version conflict — refresh and try again." The optimistic lock prevents damage, but the UI presents invalid actions that always fail. The CR-01 fix (`renderBatchDetail(data)` after success) was applied only to the footer Activate handler at line 2611 — this parallel implementation of the identical operation was not updated.
**Fix:** Mirror the footer handler: replace the manual badge mutation (lines 2528-2531) with `renderBatchDetail(data);` after the cache updates, or better, extract one shared `activatePendingBatch(b, data)` so the two paths cannot drift again.

### WR-04: Schedule & Activate success/partial paths skip the `sv-bp-batch-<id>` cache invalidation and never refresh the detail pane

**File:** `js/brewpad.js:3800-3830`
**Issue:** Every other batch-mutating path in the file removes the per-batch sessionStorage detail cache after a write (lines 848, 1880, 2543, 2610, 2775, …), but both the step-2 success handler and the step1Done partial-failure handler in the S&A submit flow omit it, and neither re-renders the detail pane when the sheet was opened from `bp-sa-detail-btn`. Consequences: (a) re-selecting the batch renders the cached **pending** detail first (line 1716-1718) — complete with live pending-only Activate buttons and a stale version — until the background refresh corrects it 1-3s later; (b) when launched from the detail footer, the pane behind the closing sheet still shows "Pending" with active buttons (the `loadDashboard()` call refreshes a different pane).
**Fix:** In both the success and step1Done-partial handlers add:
```js
try { sessionStorage.removeItem('sv-bp-batch-' + b.batch_id); } catch (e) {}
```
and, when `_selectedBatchId === b.batch_id`, re-fetch/re-render the detail (e.g., call `selectBatch(b.batch_id)`) instead of only `loadDashboard()`.

### WR-05: Needs Scheduling "Schedule & Activate" fallback leaves the button permanently disabled and can drop the optimistic lock

**File:** `js/brewpad.js:5141-5146`
**Issue:** When the batch is not in `_allBatchesData` (common — at least six paths reset it to `[]`), the handler disables `nsSaBtn`, fetches `get_batch`, and opens the sheet — but never re-enables the button on success. If the user dismisses the sheet without activating, the dashboard is not reloaded and the row's button stays dead until an unrelated refresh. Additionally, the `|| { batch_id: bid2 }` fallback object has no `last_updated`, so if `r.data.batch` is ever missing the subsequent activation silently skips the version check that the CR-02 fix exists to enforce.
**Fix:** Re-enable in the success branch (`nsSaBtn.disabled = false;` after `openScheduleActivateSheet(...)`), and treat a missing `r.data.batch` as an error (`showToast('Batch not found', 'error')`) rather than opening the sheet with a versionless stub.

### WR-06: New "contract" tests are tautological — they assert local literals and reimplemented logic, not the source under test

**File:** `tests/frontend/brewpad-activation.test.js:53-65, 70-92, 101-155`
**Issue:** Three describe blocks provide no regression protection while claiming to:
- The markup tests (lines 70-82) declare `var classes = ['bp-needsched-activate-btn', ...]` inside the test and assert the array contains its own elements. Renaming the class in `buildLifecycleTimeline`'s HTML breaks nothing, despite the header comment "a later refactor that renames them will fail these tests."
- The `bp-sa-*` id-set test (101-127) does the same with a local array — it can never fail against the real sheet HTML.
- The `step1Done routing` test (133-155) reimplements the routing conditional inside the test body (`routeStep`) instead of exercising the code in `openScheduleActivateSheet`; the source can regress freely.
- The "pending status detection" block (53-65) tests JavaScript `indexOf` semantics, not the badge guard.
Only the `todayPacific`, `escapeHTML`, and CR-01 source-scan tests exercise real artifacts. The suite passes 16/16 while guarding almost nothing — false confidence for future refactors.
**Fix:** Follow the CR-01 test's pattern at minimum: read `js/brewpad.js` and assert the class names / ids / routing expression appear in the source. Better: extract the routing function and `buildScheduleActivateSheetHtml` into testable exports and assert on rendered HTML strings.

## Info

### IN-01: S&A error handler reimplements version-conflict detection instead of using `isVersionConflict()`; the `'version_conflict'` substring can never match

**File:** `js/brewpad.js:3813-3815`
**Issue:** The catch checks `msg.indexOf('version_conflict') !== -1 || msg.indexOf('Batch was modified') !== -1`. `adminApiPost` throws `new Error(data.message || data.error)` (line 713), and both server conflict paths set a `message` ("Batch was modified…"), so the error-code substring is dead. The file already exports `isVersionConflict()` (line 64), built for exactly this with case-insensitive matching.
**Fix:** `if (!step1Done && isVersionConflict(msg)) { ... }`

### IN-02: Double-escaping in confirm messages — `escapeHTML()` fed into a `textContent` sink, inconsistently across the three activation paths

**File:** `js/brewpad.js:2590` (escaped) vs `js/brewpad.js:2520` and `js/brewpad.js:5109` (raw)
**Issue:** `showConfirmSheet` renders the message via `textContent` (line 1781), so `escapeHTML(b.batch_id)` in the footer handler would display literal entities (e.g., `&amp;`) if an ID ever contained `&`. Batch IDs are `SV-B-NNNNNN` today, so no visible impact, but the three sibling handlers disagree on whether to escape.
**Fix:** Drop `escapeHTML` in confirm-sheet messages (textContent is already safe) for consistency with the other two paths.

### IN-03: Listener accumulation and redeclared variables in the new sheet/delegation code

**File:** `js/brewpad.js:3669-3674` (backdrop), `js/brewpad.js:3637/3645` (`var inner`), `js/brewpad.js:5106/5151` (`var bid`)
**Issue:** (a) Each `openScheduleActivateSheet` call adds a new backdrop click listener to the persistent `#bp-sa-sheet`; it is removed only when a backdrop tap fires, so closing via the X button leaves listeners stacking across opens (harmless today — `closeScheduleActivateSheet` is idempotent — but a leak pattern). (b) `var inner` is declared twice in `_buildAndShow` (inside the `if (!sheet)` block and again after). (c) `var bid` is declared in both the nsActivateBtn and nsDelBtn branches of the same function scope — safe only because every branch returns.
**Fix:** Bind the backdrop listener once at sheet creation (inside the `if (!sheet)` block); reuse the hoisted `inner`/`bid` without redeclaring.

### IN-04: `todayPacific(offsetDays)` is DST-naive — fixed 86,400,000ms day can be off by one across the Pacific fall-back transition

**File:** `js/brewpad.js:19-22`
**Issue:** `new Date(Date.now() + offsetDays * 86400000)` assumes 24-hour days; on the 25-hour fall-back day, an offset taken shortly after midnight Pacific can land on the same calendar date. All production call sites currently invoke `todayPacific()` with no offset (correct), and the parameter is exercised only by tests — but the helper is exported and invites future misuse.
**Fix:** Document the limitation, or compute the offset in calendar space (format today first, then adjust the Y/M/D parts via `Date.UTC`).
