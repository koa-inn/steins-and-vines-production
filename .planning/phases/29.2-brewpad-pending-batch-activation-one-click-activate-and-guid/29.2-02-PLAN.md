<objective>
Add the activation entry points to the Dashboard "Needs Scheduling" rows.

Two deliverables, building directly on the Wave 1 foundation (`todayPacific()` helper + export, status-badge pending guard from 29.2-01):
1. Extend the Needs Scheduling row render (js/brewpad.js:1111-1126) so each row carries an **Activate** button, a **Schedule & Activate** button, and the existing **Delete** button — all wrapped in a `bp-task-actions` div, every interpolated field escaped via `escapeHTML`.
2. Wire two delegated click handlers in the dashboard click handler: `.bp-needsched-activate-btn` (one-click Activate confirm → `update_batch` with `start_date: todayPacific()` → cache-bust + `loadDashboard()`), and `.bp-needsched-sa-btn` (look up the full batch in `_allBatchesData`, fall back to a `get_batch` fetch, then call `openScheduleActivateSheet(batch)`).

`openScheduleActivateSheet` itself is built in plan 29.2-03. This plan wires the call site; until 29.2-03 lands, the `.bp-needsched-sa-btn` branch references a forward-declared function. Because all three plans modify the same file sequentially (29.2-03 depends on this plan), the function exists by the time the guided sheet is exercised. The one-click Activate path is fully self-contained and works immediately.

Purpose: The Needs Scheduling rows are the always-visible queue of pending batches awaiting activation. This plan turns them from a passive "awaiting schedule" list into actionable rows — staff activate or schedule-and-activate straight from the dashboard without opening the batch detail pane.

Output: Two source edits to `js/brewpad.js` (row render + delegation handlers), new pure-helper tests appended to `tests/frontend/brewpad-activation.test.js`, regenerated `js/brewpad.min.js` via `npm run build`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BrewPad browser → Apps Script (`adminApiPost` / `adminApiGet`) | Batch activation + lookup cross here; auth via existing `accessToken` on every call (unchanged) |
| Batch summary data → rendered row HTML | Untrusted batch fields (`batch_id`, `product_name`, `customer_name`, `last_updated`) interpolated into Needs Scheduling row markup and data-attributes |
| `data-*` attributes → activation payload | `data-batch-id` / `data-version` read back off the DOM and sent in the `update_batch` payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29.2-05 | Tampering (XSS) | `it.batch_id`, `it.product_name`, `it.customer_name`, `it.last_updated` interpolated into row HTML and into `data-batch-id` / `data-version` attributes | mitigate | Every interpolated field passes through `escapeHTML(... || '')` (Task 2 acceptance criteria); button labels are static literals; no innerHTML sink receives raw batch data |
| T-29.2-06 | Tampering | `data-version` / `expectedVersion` empty or stale on one-click Activate overwrites a concurrent update | accept | `it.last_updated` may be absent in the dashboard summary projection (RESEARCH.md Pitfall 1); empty string is a deliberate no-lock fallback. Risk is low — Needs Scheduling rows are short-lived and single-operator; the detail-pane path (29.2-03) carries a full version. Apps Script `update_batch` still validates the pending→primary transition server-side |
| T-29.2-07 | Tampering | `start_date` injected via `update_batch` payload | accept | Client only sends `todayPacific()` output (YYYY-MM-DD); `start_date` is in the Apps Script `allowedFields` allowlist and passes server-side `sanitizeInput` (adminApi.gs:2164) — unchanged |
| T-29.2-08 | Elevation of Privilege | Activation / `get_batch` lookup without auth | accept | Every `adminApiPost` / `adminApiGet` carries the existing `accessToken`; Apps Script validates server-side — unchanged by this plan |
| T-29.2-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed this phase (RESEARCH.md Package Legitimacy Audit: N/A) |
</threat_model>
