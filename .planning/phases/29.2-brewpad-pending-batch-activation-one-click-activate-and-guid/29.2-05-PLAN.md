<objective>
Close the quality gap CR-02 (data-integrity, not a goal blocker): the Needs Scheduling row's one-click Activate button plumbs an optimistic-lock version (data-version, sent as expectedVersion) from it.last_updated, but the Apps Script needsScheduling summary builder (apps-script/adminApi.gs:1733-1741) never emits last_updated. So data-version is always "", the server skips the lock (if (payload.expectedVersion) is falsy for ""), and a concurrent Schedule-&-Activate on the same batch can be silently overwritten by this one-click Activate (lost update, no warning).

The frontend already reads it.last_updated correctly (js/brewpad.js:1130) — no frontend change is needed. The fix is a one-line addition to the Apps Script builder so the field actually flows. Because adminApi.gs is deployed manually (paste into the Apps Script editor, redeploy the existing web-app deployment), this plan includes a blocking human-action checkpoint for the deploy.

Purpose: Re-enable the optimistic lock the activation code was built around, closing a lost-update path under concurrent staff use.
Output: One-line addition to apps-script/adminApi.gs needsScheduling.push(), plus a verified manual redeploy.
</objective>
