### Gap Closure Evidence

#### CR-01 (BLOCKER) — CLOSED

**What was broken:** `js/brewpad.js:2611` called `renderBatchDetail(b)` with a bare batch object. `renderBatchDetail` expects `data = { batch, tasks, plato_readings }` and dereferences `data.batch` at line 2270. Passing a bare batch set `data.batch = undefined`, rendering a blank detail pane and corrupting `_detailBatchId` / `_currentBatchDetail`.

**Fix applied (plan 29.2-04):**
- `grep -n "renderBatchDetail(b)" js/brewpad.js` — no matches (zero)
- `grep -c "renderBatchDetail(data)" js/brewpad.js` — 4 matches (function declaration line 2269 + call sites lines 1726, 1756, 2611)
- Line 2611 in context (lines 2598-2612): success handler mutates `b.status = 'primary'` at line 2599, then calls `renderBatchDetail(data)` — `data.batch === b`, so the re-render shows the now-Primary batch with tasks and plato_readings intact.

**TDD gate:**
- RED commit: fbefc2f — CR-01 regression test failed as expected
- GREEN commit: 1dfce81 — all 16 tests pass

#### CR-02 (data integrity, not goal blocker) — CLOSED

**What was broken:** `adminApi.gs` needsScheduling builder (lines 1733-1741) did not emit `last_updated`, so the NS row Activate button's `data-version` attribute was always `""`. The server's optimistic lock (triggered only when `expectedVersion` is truthy) was silently disabled for all NS row one-click Activates.

**Fix applied (plan 29.2-05):**
- `grep -n "last_updated: b.last_updated" apps-script/adminApi.gs` — match at line 1741
- Full push block verified (lines 1733-1742): `batch_id`, `product_name`, `customer_name`, `source`, `zoho_so_number`, `created_at`, `last_updated` all present.
- Apps Script redeploy: human-confirmed per blocking checkpoint in plan 29.2-05. Web app URL unchanged (existing deployment updated to new version).
