# Phase 29.2: BrewPad Pending Batch Activation - Research

**Researched:** 2026-06-12
**Domain:** Frontend-only — `js/brewpad.js` activation UI (no backend changes)
**Confidence:** HIGH

---

## Summary

Phase 29.2 ports the one-click Activate and guided Schedule & Activate flows from the admin batch panel (`js/admin.js`) into BrewPad (`js/brewpad.js`). All backend capability already exists from Phase 27 — no Apps Script or middleware changes are needed. The work is purely frontend.

There are two distinct UX locations to update: (1) the "Needs Scheduling" rows on the Dashboard tab, and (2) the batch detail pane (triggered from any pending batch card/row). Additionally, the status badge cycling in the detail pane has a confirmed bug: `pending` is not in the `['primary', 'secondary', 'complete']` cycle array, so clicking the badge silently promotes a pending batch to Primary with no confirmation and no start_date stamp. This must be intercepted and routed through the proper activation flow.

The entire Phase 27 activation stack — `update_batch` (flip to primary with `start_date`), `update_batch_schedule` (generate tasks from snapshot), the `step1Done` partial-failure pattern, `expectedVersion` optimistic locking — is already battle-tested in admin.js and transfers directly. BrewPad already has `_fermSchedules` (loaded at eager-init), `_vesselsData`, `bindVesselSearch`, `bindShelfInput`, `bindBinInput`, and `showConfirmSheet` — all needed for the guided flow.

**Primary recommendation:** Add inline action buttons to both the Needs Scheduling rows (Dashboard) and pending batch cards/rows (Batch tab), plus intercept the detail pane status badge for pending batches — routing through `showConfirmSheet` (one-click) or a new `openScheduleActivateSheet` bottom sheet (guided). Copy the Phase 27 two-step orchestration with `step1Done` flag verbatim.

## Architecture Patterns

### System Architecture Diagram

```
Staff taps pending batch row (Dashboard / Batch tab)
  |
  +---> Needs Scheduling row: "Activate" button click
  |       --> showConfirmSheet (warn: no schedule, start=today)
  |             --> adminApiPost('update_batch', {status:'primary', start_date: today})
  |                   --> Apps Script updateBatch (stamps fermentation_started_at)
  |                         --> loadDashboard() + _batchesLoaded=false + re-render
  |
  +---> Needs Scheduling row: "Schedule & Activate" button click
  |       --> openScheduleActivateSheet(batch)   [NEW bottom sheet]
  |             --> <select> schedules, date input, vessel search
  |                   --> sa-submit click
  |                         step1: adminApiPost('update_batch', batchUpdates)
  |                         step2: adminApiPost('update_batch_schedule', {schedule_snapshot})
  |                         success: loadDashboard() + refreshBatchList() + toast
  |                         partial (step1Done): warning toast + refresh
  |
  +---> Open batch detail pane (any pending batch)
          Status badge click (currently silently cycles!)
          --> Intercept: if pending, route to Activate flow instead
          --> showConfirmSheet (same one-click confirm copy)
                OR offer both Activate + Schedule & Activate buttons in detail header
```

### Pattern 2: Guided Schedule & Activate (BrewPad port of admin.js:7257-7425)

**What:** Bottom sheet (same `bp-create-sheet` style) with schedule select, date input, optional vessel/shelf/bin. Two-step orchestration with `step1Done` flag.
**When to use:** "Schedule & Activate" button on Needs Scheduling rows and the detail pane.

Key differences from admin.js version:
- Uses `showConfirmSheet`-style bottom sheet, NOT `openModal` (BrewPad has no modal infrastructure — uses bottom sheets, see `openCreateSheet` pattern at line 3473)
- Uses `todayStr()` or a new `todayPacific()` for date default (see Pitfall 2)
- The schedule preview HTML is identical to admin.js (step-by-step list)
- `_fermSchedules` is already available module-scope (no load-guard needed if dashboard init ran)

```javascript
// Source: admin.js:7379-7424, adapted
var step1Done = false;
adminApiPost('update_batch', {
  batch_id: batchId,
  expectedVersion: batch.last_updated,
  updates: batchUpdates   // { status:'primary', start_date, [vessel_id, shelf_id, bin_id] }
}).then(function (step1Result) {
  step1Done = true;
  var newVersion = step1Result.newVersion || batch.last_updated;
  return adminApiPost('update_batch_schedule', {
    batch_id: batchId,
    expectedVersion: newVersion,
    schedule_snapshot: schedSteps
  }).then(function (step2Result) {
    var taskCount = step2Result.tasks_created || 0;
    showToast('Batch activated with ' + taskCount + ' task' + (taskCount !== 1 ? 's' : '') + ' scheduled', 'success');
    closeScheduleActivateSheet();
    // full refresh
    _batchesLoaded = false;
    _allBatchesData = [];
    _eagerLoadTime = 0;
    _dashLoadTime = 0;
    loadDashboard();
  });
}).catch(function (err) {
  var msg = err.message || 'Unknown error';
  if (!step1Done && (msg.indexOf('version_conflict') !== -1 || msg.indexOf('Batch was modified') !== -1)) {
    showToast('Version conflict — refresh and try again', 'error');
  } else if (step1Done) {
    showToast('Batch activated, but the schedule didn\'t save — assign it from the batch detail', 'warning');
    closeScheduleActivateSheet();
    _batchesLoaded = false; _allBatchesData = []; _eagerLoadTime = 0; _dashLoadTime = 0;
    loadDashboard();
  } else {
    showToast('Failed: ' + msg, 'error');
  }
  submitBtn.disabled = false;
  submitBtn.textContent = 'Schedule & Activate';
});
```

### Pattern 3: Status Badge Pending-Aware Guard

**What:** The status badge click handler at brewpad.js:2497-2531 cycles through `['primary', 'secondary', 'complete']`. `pending` is not in this array, so `indexOf('pending')` returns `-1`, `(-1+1) % 3 = 0`, and the badge silently triggers an `update_batch` to `primary` with NO confirmation and NO `start_date`. This is the bug.

**Fix:** At the start of the badge click handler, check if `b.status === 'pending'` and route to the activation flow instead:

```javascript
// Source: brewpad.js:2497 — add pending guard before the existing order array
statusBadge.addEventListener('click', function () {
  var cur = String(b.status || '').toLowerCase();
  if (cur === 'pending') {
    // Route to activation instead of cycling
    showConfirmSheet(
      'Activate ' + b.batch_id + ' now? No schedule will be attached and the start date is set to today.',
      'Activate', '',
      function () {
        adminApiPost('update_batch', {
          batch_id: b.batch_id,
          updates: { status: 'primary', start_date: todayStr() },
          expectedVersion: b.last_updated
        }).then(function () {
          b.status = 'primary';
          // update badge display + cache + re-render list
          showToast('Batch activated', 'success');
          callSyncZoho(b.batch_id, b.zoho_so_number, 'active');
          // ... cache + renderBatchList
        }).catch(function (err) { showToast('Failed: ' + err.message, 'error'); });
      }
    );
    return;  // <-- critical: bail out before the existing cycle logic
  }
  var order = ['primary', 'secondary', 'complete'];
  // ... existing cycling code unchanged ...
});
```

### Pattern 5: Needs Scheduling Row — Activate Buttons

**What:** Each row in the Needs Scheduling section (brewpad.js:1111-1125) currently renders a "Delete" button only. Add "Activate" and "Schedule & Activate" buttons. The row data `it` contains: `batch_id`, `product_name`, `customer_name`, `source`, `created_at`.

**Problem:** The `it` batch object from `d.needsScheduling` may be a summary object — it may NOT include `last_updated` (needed for `expectedVersion`). The planner must decide whether to pass `expectedVersion: it.last_updated || ''` (safe — backend treats empty/missing as no-check) or fetch the full batch first.

Looking at admin.js pattern (line 5760-5777): when `batch.last_updated` is available from the list data, use it directly. If not, fall back to a `get_batch` call to fetch `last_updated` before opening the guided flow.

```javascript
// Dashboard delegation — add inside initDelegation dashInner click handler
var nsActivateBtn = e.target.closest('.bp-needsched-activate-btn');
if (nsActivateBtn) {
  var bid = nsActivateBtn.getAttribute('data-batch-id');
  var ver = nsActivateBtn.getAttribute('data-version');  // may be empty string
  // one-click confirm flow ...
  return;
}
var nsSaBtn = e.target.closest('.bp-needsched-sa-btn');
if (nsSaBtn) {
  var bid = nsSaBtn.getAttribute('data-batch-id');
  // find batch in _allBatchesData first; if not found, fetch via get_batch
  var batchRow = null;
  for (var i = 0; i < _allBatchesData.length; i++) {
    if (_allBatchesData[i].batch_id === bid) { batchRow = _allBatchesData[i]; break; }
  }
  if (batchRow) {
    openScheduleActivateSheet(batchRow);
  } else {
    // fetch then open
    adminApiGet('get_batch', { batch_id: bid })
      .then(function (r) { openScheduleActivateSheet((r.data && r.data.batch) || { batch_id: bid }); })
      .catch(function (err) { showToast('Failed: ' + err.message, 'error'); });
  }
  return;
}
```

### Anti-Patterns to Avoid

- **Calling `update_batch` without `start_date` on one-click activate:** The backend will use any pre-existing `start_date` or `fermentation_started_at` — not today. The Phase 27 gap-closure (plan 27-04) fixed this in admin.js by adding `start_date: todayPacific()`. BrewPad must do the same.
- **Skipping `expectedVersion`:** Always pass `batch.last_updated` as `expectedVersion` (even if empty string) to benefit from optimistic locking. Empty string means no locking — acceptable for simplicity on the Needs Scheduling rows where `last_updated` may not be in the summary object.
- **Using `openModal`:** brewpad.js has no modal infrastructure. Use the existing bottom-sheet pattern (`bp-create-sheet`).
- **Rebuilding vessel/schedule loading logic:** `_fermSchedules` and `_vesselsData` are loaded at eager-init and cached. The guided sheet can read them directly without refetching (with a guard: if `_fermSchedules.length === 0`, show a warning or trigger `reloadSchedules()` first).
- **Modifying `js/main.js` directly:** It's a build artifact. All source edits go in `js/brewpad.js`.

## Common Pitfalls

### Pitfall 1: `data-version` missing from Needs Scheduling rows
**What goes wrong:** The `it` objects in `d.needsScheduling` (from `get_batch_dashboard_summary`) are summary objects. They likely include `batch_id`, `product_name`, `customer_name`, `source`, `created_at` — but `last_updated` (needed for `expectedVersion`) may NOT be present.
**Why it happens:** The dashboard summary is a denormalized view, not the full batch record.
**How to avoid:** Emit `data-version=""` on the button. An empty `expectedVersion` string is safe — the Apps Script treats it as "no version check." Alternatively, look up `last_updated` from `_allBatchesData` before calling (since all batches are loaded at eager-init). Planner should verify `needsScheduling` items have `last_updated` by checking the Apps Script `get_batch_dashboard_summary` response shape.
**Warning signs:** `expectedVersion` is undefined or null in the payload.

### Pitfall 2: `todayStr()` vs `todayPacific()` — timezone mismatch for `start_date`
**What goes wrong:** `todayStr()` returns UTC date (`new Date().toISOString().slice(0, 10)`). For Squamish (UTC-7/UTC-8), from 5pm onwards, `todayStr()` returns "tomorrow" — wrong `start_date` for fermentation logs.
**Why it happens:** admin.js introduced `todayPacific()` specifically to fix this for the store's local timezone. brewpad.js never needed it because existing date inputs (New Batch form) accept user selection.
**How to avoid:** Add a `todayPacific()` helper to brewpad.js (same implementation: `d.toLocaleDateString('en-CA', { timeZone: 'America/Vancouver' })`). Use it for the `start_date` default in the date input and in the one-click activate payload. The planner must make this call.
**Warning signs:** Staff activates at 6pm and fermentation start date is the next day.

### Pitfall 3: Status badge cycling for non-pending batches must be untouched
**What goes wrong:** The fix for the pending badge routing introduces a regression — the existing `['primary', 'secondary', 'complete']` cycling for active batches breaks.
**Why it happens:** Guard inserted in the wrong place or with wrong condition.
**How to avoid:** Add `if (cur === 'pending') { ...; return; }` as the FIRST statement in the click handler, before `var order = [...]`. The existing order array and cycling logic must remain byte-for-byte identical.
**Warning signs:** Primary/secondary/complete badge click stops working.

### Pitfall 4: `_fermSchedules` empty when Schedule & Activate sheet opens
**What goes wrong:** Staff opens Schedule & Activate and sees no schedule options because `_fermSchedules` hasn't been loaded (e.g., if the BrewPad session started on the Batches tab, not Dashboard).
**Why it happens:** `_fermSchedules` is populated at eager-init (line 957) which runs on dashboard load. If `loadDashboard()` hasn't been called yet, the array is empty.
**How to avoid:** Add a guard at the start of `openScheduleActivateSheet`: if `_fermSchedules.length === 0`, call `reloadSchedules()` first and open the sheet in its callback. Or show the sheet with a loading spinner while fetching.
**Warning signs:** Schedule select dropdown is empty.

### Pitfall 5: Bottom sheet ID collision with existing create sheet
**What goes wrong:** Using `id="bp-create-sheet"` for the new Schedule & Activate sheet collides with the New Batch create sheet.
**Why it happens:** Lazy copy of the create sheet HTML structure.
**How to avoid:** Use a distinct ID for the new sheet, e.g. `id="bp-sa-sheet"`. Give all inner elements distinct IDs (`bp-sa-schedule-select`, `bp-sa-start-date`, `bp-sa-vessel-search`, etc.).
**Warning signs:** Opening Schedule & Activate destroys the create sheet or vice versa.

### Pitfall 6: Detail pane `b.last_updated` may be stale after partial open
**What goes wrong:** If the detail pane was rendered from a preloaded/cached batch, `b.last_updated` may be stale, causing an optimistic lock failure from the Apps Script.
**Why it happens:** The preload cache (sessionStorage) has a 2-minute TTL. If another session updated the batch in those 2 minutes, the version is stale.
**How to avoid:** On version conflict error, show the existing "refresh and try again" toast, clear the sessionStorage cache for that batch, and re-open the detail.

## Open Questions (RESOLVED)

1. **Does `d.needsScheduling[i]` include `last_updated`?**
   - RESOLVED: Plan 29.2-02 adopts the `data-version=""` empty-string fallback — Apps Script skips the optimistic-lock check when `expectedVersion` is empty, with `_allBatchesData` lookup where available.
   - What we know: The `needsScheduling` array comes from `get_batch_dashboard_summary`. Its exact fields are set in `adminApi.gs`.
   - What's unclear: Whether `last_updated` is in the summary projection.
   - Recommendation: Planner should grep `adminApi.gs` for `needsScheduling` or `needs_scheduling` to confirm the projection. If absent, use `expectedVersion: ''` (no locking) or look up from `_allBatchesData` which IS the full batch list.

2. **`todayStr()` vs `todayPacific()` for the activate `start_date`**
   - RESOLVED: Plan 29.2-01 adds `todayPacific()` to brewpad.js and all activation `start_date` payloads use it (Pitfall 2).
   - What we know: `todayStr()` is UTC; `todayPacific()` is store-local. The store is in Squamish (UTC-7 / UTC-8). Gap is 5pm–midnight.
   - What's unclear: Whether staff activate batches in the evening.
   - Recommendation: Add `todayPacific()` to brewpad.js (it's a 3-line function). Keep `todayStr()` for timestamps that don't need timezone precision (measurements, task filter). Tag this as a planner decision.

3. **Where exactly to place the "Activate" and "Schedule & Activate" buttons in batch list cards?**
   - RESOLVED: Plans 29.2-02/03 add buttons only to Needs Scheduling rows and the detail pane — batch list cards remain tap-to-open with no inline activation buttons.
   - What we know: Card view currently shows ID + status badge + product name + customer + task progress + location. Adding two buttons could crowd small cards.
   - What's unclear: UX preference — inline in card footer vs. only in the detail pane (accessed via card tap).
   - Recommendation: Only add activation buttons to the Needs Scheduling dashboard rows (always visible) and the detail pane. The batch list cards are tap-to-open and the detail pane is the natural place to act on a specific batch. This keeps the batch card list clean. The planner can decide differently.

4. **Schedule & Activate bottom sheet — reuse `bp-create-sheet` element or create a new one?**
   - RESOLVED: Plan 29.2-03 creates a new sheet dynamically with unique id `bp-sa-sheet` (showConfirmSheet pattern), leaving `bp-create-sheet` untouched.
   - What we know: `bp-create-sheet` (HTML in brewpad.html) is used by the New Batch flow. It's dynamically populated by `buildCreateForm()`.
   - What's unclear: Whether the HTML element is created dynamically on open or exists in the DOM.
   - Looking at the code: `openCreateSheet()` at line 3473 accesses `document.getElementById('bp-create-sheet')` — it exists in the HTML. A new sheet would either need a separate HTML element or dynamic creation.
   - Recommendation: Create the Schedule & Activate sheet dynamically (same pattern as `showConfirmSheet` at line 1751 — create the DOM element if it doesn't exist, reuse if it does). Use a unique ID `bp-sa-sheet`.
