<objective>
Close G-44-01 on the server side. Today a kiosk gift-cert issue/reload calls the standalone
`/api/kiosk/gift-card/issue` or `/reload` route, which creates a Zoho invoice AND records a
phantom `creditcard` customerpayment (invoice→paid) with NO real Helcim charge — phantom
revenue. The owner-locked fix is **Cart + terminal checkout**: a gift-cert becomes a LINE in
the normal kiosk cart, paid via the existing terminal→invoice→payment flow in `pos.js`, and the
certificate is activated on payment SUCCESS.

This plan reworks the middleware so `pos.js` understands a `gift_cert` line item, prices it
zero-tax from `KIOSK_GIFT_CARD_ITEM_ID`, includes it in the terminal charge, and drives Apps
Script `issue_gift_card` / `reload_gift_card` as the LAST step after the cart invoice + payment
succeed. It also decommissions the phantom-payment behavior of the standalone issue/reload routes.

Purpose: stop overstating collected cash; make gift-cert money-in a real, taxed-correctly,
fail-safe terminal charge that cannot orphan an active cert.
Output: reworked `pos.js`, slimmed `gift-cards.js` (+ `server.js` mounts), updated test suites.
</objective>

<!-- The gift_cert LINE contract (frontend → /api/kiosk/sale and /api/kiosk/sale/confirm).
     This is the contract 44-10 (frontend) will emit. Lock it exactly. -->

A gift-cert cart line arrives as an element of body.items (alongside catalog + custom lines):

  { gift_cert: true,
    gift_action: "issue" | "reload",
    cert_number: "GC-000042",      // /^GC-\d{6}$/ — server re-validates, uppercases, trims
    quantity: 1,                    // always 1; server forces 1
    rate: 50.00 }                   // face value (issue) or reload amount; server bounds (0, 2000]

It is DISTINCT from the existing 44-04 redeem TENDER field body.gift_card
({ cert_number, amount_applied }). The two are orthogonal and may both appear in one sale; do
not conflate them.

Existing server-side gift redemption (44-04) — DO NOT regress. In confirm, the redeem
activation is already the LAST step (axios.post redeem_gift_card after both customerpayments).
The new issue/reload activation must run in that SAME post-payment block.

Apps Script actions already deployed (44-02), call via axios.post {action, server_token, ...}:
  - issue_gift_card { cert_number, face_value, issued_by, notes }
       → { ok:true } | { ok:false, error:"duplicate" } | { ok:false, error:... }   (LockService uniqueness — D-02)
  - update_gift_card_invoice { cert_number, zoho_invoice_number }  → { ok:true }
  - reload_gift_card { cert_number, amount, transaction_ref }
       → { ok:true, new_balance } | { ok:false, error:"not_found"|"invalid_status"|... }
  - redeem_gift_card { cert_number, amount, transaction_ref }  (already wired — leave as-is)

The confirm 201 result body carries gift_card_activation_failed:true + needs_manual_review:true
when issue/reload fails AFTER the terminal charge succeeded — 44-10 reads these flags to alert staff.

Sale idempotency pattern to mirror for CONFIRM (currently only /api/kiosk/sale has it):

  cache.set(...). C.CACHE_KEYS.KIOSK_IDEM_PREFIX + body.idempotency_key.
