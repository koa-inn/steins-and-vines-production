<objective>
`/api/kiosk/salesorder-pay` (`routes/pos.js:1797-1838`) is THE headline defect of this phase. It accepts only `salesorder_id`. It has no `idempotency_key`, no `acquireIdempotencyLock`, and mints a fresh Helcim idempotency key on every call (`helcimLib.generateIdempotencyKey()` at `:1836`). Its sole guard is a Zoho balance check — which two concurrent requests both pass, because neither has taken the money yet. It then charges the terminal for the full sales-order balance. **A double-submit or a retry double-charges a real customer paying a real order.**

Every sibling kiosk route was hardened in Phase 45 (`/api/kiosk/sale` at `:250-263` is the proven pattern). This one was left behind.

This plan makes `salesorder-pay` use the exact same money-path primitives as `/api/kiosk/sale`, plus the three remaining audit-H8 items: a unique terminal reference, a pending-charge record deleted on success, and a void routed through the hardened primitive.

Purpose: Closes M-A1 / audit H8 / roadmap SC#4.
Output: A `salesorder-pay` route that cannot double-charge, and a regression suite that proves it.
</objective>

<locked_decisions>
**D-50-01 — salesorder-pay takes a client `idempotency_key`, with a server-derived salesorder-scoped fallback lock. (The open design decision, delegated to the planner.)**

Chosen: the **hybrid** — option (a) as the primary contract, with a server-side fallback derived from `salesorder_id` when no key is supplied.

Behaviour:
- If the client sends `idempotency_key` (string) → lock on `C.CACHE_KEYS.KIOSK_IDEM_PREFIX + 'sopay:' + idempotency_key.slice(0, 128)`. This is byte-for-byte the `/api/kiosk/sale` pattern (`pos.js:242-263`) — one proven pattern, not two.
- If the client sends NO `idempotency_key` → still lock, on `C.CACHE_KEYS.KIOSK_IDEM_PREFIX + 'sopay:so:' + salesorder_id`. Same primitive, different key source. **Do not add a third primitive.**

Why not pure (a) (require the key, 400 without it — what `/api/kiosk/sale` does)?
Because **there is no staging middleware**: this code goes live on the production Railway instance on deploy, while the iPad kiosk may still be running a cached `kiosk-core.min.js` that does not send the key. Requiring the key outright would hard-400 every sales-order payment until every client refreshes — an outage on the money path, caused by a fix for the money path. The fallback makes the server-side hardening effective on day one regardless of client cache state, and plan 50-04 lands the client key in the same phase.

Why not pure (b) (SO-id-derived only)?
Because it cannot distinguish a legitimate retry from a deliberate second payment, and because it would be a second, divergent pattern from `/api/kiosk/sale`.

**Cost of the hybrid, stated explicitly:** with a keyless (stale) client, a *legitimate* second payment on the same sales order within the lock TTL is rejected 409. This is rare (the route always pays the full balance, so after a successful payment the balance is zero and the balance guard rejects anyway; a second legitimate payment requires lines to be added to the SO and re-paid within 5 minutes). The failure mode is "staff waits and retries", not "customer charged twice". Accepted.

**The fallback lock never serves a cached replay.** On `status: 'replay'` the route returns the cached receipt ONLY when the key was client-supplied. For the SO-id-derived fallback key, a `replay` result is treated as `contention` → 409. Rationale: an SO-id-scoped key is not a statement of intent from the client, so it must never silently return a stale receipt for what might be a genuinely new payment attempt. Lock, yes. Replay-cache, no.

**D-50-01a — Helcim's idempotency key is derived deterministically from the effective lock key,** exactly as `/api/kiosk/sale` does (`pos.js:556-558`): `crypto.createHash('sha256').update(effectiveKey).digest('hex').substring(0, 25)`. This is the second line of defence: even if the Redis lock is bypassed (Redis outage in dev, two Railway instances racing a lock release), Helcim itself refuses the duplicate terminal charge. Replacing `helcimLib.generateIdempotencyKey()` at `:1836` is the single most important line in this plan.

**D-50-01b — the terminal reference becomes unique per attempt** (audit H8: "uses a unique reference"). Today the reference is the bare `soNumber`, which is reused on every attempt against the same order. That reference is passed to `terminalPurchase` as `invoiceNumber`, is the key `pollTerminalResult` polls on, and is the key the pending-charge record and `lib/reconcile.js` are keyed by — so two attempts on the same SO collide on all three. New reference: `soNumber + '-' + <first 6 chars of the same sha256 used for the Helcim key>`, truncated to 64 chars. It MUST be the same string in all three places (terminalPurchase, pollTerminalResult, the pending-charge key) or reconcile will never find the record.
</locked_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| kiosk/admin client → `POST /api/kiosk/salesorder-pay` | Untrusted, replayable request. A double-tap, a browser retry, an iPad network flap, or two staff on two devices all cross here. Auth is device-token/session (`authTiers`), which authenticates the *device*, not the *intent* — an authenticated duplicate is still a duplicate. |
| middleware → Helcim terminal | Real money leaves here. This is the only boundary in the phase where crossing it twice costs a real customer real money. |
| middleware → Redis (lock) | The lock is the primary duplicate guard; Redis degradation must not silently open it. |
| middleware → Zoho (balance read) | The balance check is a *stale read* — it is NOT a guard against concurrency, and was being used as one. |
