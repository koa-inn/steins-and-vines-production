<objective>
The client defeats the server's own money guard.

`js/kiosk-core.js:2446` mints `refNumber = 'KIOSK-' + Date.now()` **inside** `_kioskPushToTerminal`, per invocation, and sends it as BOTH `reference_number` and `idempotency_key`. The Proceed and Skip buttons (`:2105-2113`) are **never disabled on click**. So two taps produce two invocations, two `Date.now()` values, two DIFFERENT idempotency keys — and the Phase 45 server-side idempotency lock never sees a duplicate. **A shipped, high-severity server fix is silently neutered by the client.** Post-Phase-48 de-fork this is live on kiosk.html AND admin.html, because both consume the same `kiosk-core.js`.

The same shape applies to `kioskCollectPayment` (`:3554`), which POSTs `{ salesorder_id: soId }` with no idempotency key at all, from a `.kiosk-so-pay-btn` (`:3309-3312`) that is likewise never disabled — the client half of plan 50-02's headline defect.

Purpose: Closes M-B1. It is the client half of the same defect as 50-01/50-02, and it is cheap.
Output: A kiosk client that cannot fire the same payment twice, and whose retries are recognisable as retries by the server.
</objective>

<locked_decisions>
**D-50-05 — the idempotency key is minted once per PAYMENT ATTEMPT, not per request and not per cart.**

The key must be:
- **stable** across a double-tap (two taps of the same button, same attempt → one key → the server lock fires), and
- **fresh** for a genuinely new attempt (staff hit an error, return to the cart, and re-run the sale → new key → not rejected as a replay of the failed attempt).

Implementation: mint the key when the payment **attempt begins** — at the top of `kioskProceedToPayment()` (which is what transitions into the payment view), storing it in a module-scoped `_kioskPaymentKey`. `_kioskPushToTerminal` then **reads** `_kioskPaymentKey` instead of minting `'KIOSK-' + Date.now()` itself. Because `kioskProceedToPayment` runs once per attempt and `_kioskPushToTerminal` can run more than once within an attempt (the gift-card panel step, the manager stock-override resubmit at `:2470`), this is exactly the right seam.

For the sales-order path: mint `_kioskSoPayKey = 'SOPAY-' + soId + '-' + Date.now()` in `kioskCollectPayment(soId)` — but ONLY when the incoming `soId` differs from the one already in flight. A second call for the SAME `soId` while a payment is in flight reuses the existing key (double-tap) rather than minting a new one. Cleared when the attempt terminates (receipt, error, or cancel).

**Both guards, not one.** Disabling the button is the primary fix (no second request is ever sent). The stable key is the backstop for the paths a disabled button cannot cover: an iPad touch that registers twice before the handler runs, a client-side retry, a browser back/forward re-post, or a stale cached `kiosk-core.min.js` on another device. Neither alone is sufficient; the audit's "a one-line disable-on-click closes it" understates the retry case.

**Re-entrancy guard, not just `disabled`.** `btn.disabled = true` is trivially defeated by a second `onclick` already queued. Each money-path entry point also gets an in-flight boolean checked at the top of the handler (`if (_kioskPaymentInFlight) return;`), because the button element may not even exist on every entry path — `kioskCollectPayment` is reachable from four call sites (`:2387`, `:2402`, `:3312`, `:3701`, `:4019`), only one of which is a button click.

**Re-enable on every terminal outcome.** Every failure path must re-enable the button and clear the in-flight flag, or a single failed sale bricks the kiosk until reload. This is the mirror of the D-50-03 lock-release rule on the server.
</locked_decisions>
