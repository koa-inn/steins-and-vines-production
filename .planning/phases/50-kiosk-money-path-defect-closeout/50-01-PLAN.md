<objective>
`voidTransaction` currently returns `{ ok: true }` on ANY 2xx from Helcim `/payment/reverse` without inspecting whether Helcim actually reversed the charge (`lib/helcim.js:144-157`). Every void-on-failure path in the codebase — kiosk confirm, salesorder-pay, checkout, reconcile — trusts that boolean. A failed-but-200 reversal therefore tells staff "Payment Voided" while the customer stays charged: precisely the failure the void path exists to prevent.

This plan makes `voidTransaction` inspect the actual reversal outcome and fail CLOSED when the response does not positively confirm a reversal.

Purpose: Closes M-A2 / audit H5 / roadmap SC#3. It is Wave 1 because plans 50-02, 50-03 and 50-05 all assert honest void reporting and depend on these semantics.
Output: Hardened `voidTransaction` + a new regression suite covering the 2xx-but-not-reversed response.
</objective>

<locked_decisions>
**D-50-02 — Void confirmation is positive-signal, fail-closed, and logs the raw shape.**

Helcim's `/payment/reverse` response body shape is not documented anywhere in this repo, and there is no staging middleware to probe it against (middleware deploys straight to production). A check that is too strict would make every legitimate void report failure — flooding staff with false `needs_manual_review` alerts and telling them a customer is still charged when they are not. That is a worse operational failure than the bug being fixed.

Therefore the check is deliberately **permissive on the positive side and closed only on genuinely uninformative or negative bodies**:

- CONFIRMED (resolve `{ ok: true, ... }`) iff the response body carries a positive reversal signal:
  - `status` (case-insensitive) is one of `APPROVED`, `COMPLETED`, `REVERSED`, `VOIDED`, **or**
  - `approved === true`, **or**
  - a `transactionId` is present AND `type` (case-insensitive) is one of `reverse`, `void`
- UNCONFIRMED (reject) otherwise — including an empty body `{}`, a body with only an echo of the request, or `status: 'DECLINED'`.

Cost / residual risk (stated explicitly): if Helcim returns a 2xx body containing NONE of the above positive signals for a genuinely successful reversal, this change converts a silent false-success into a loud false-failure (void-failure record + staff alert). That is the correct direction to fail — staff investigate a charge that is actually already reversed, rather than a customer staying charged while the screen says "Voided". Task 3 (checkpoint) closes the knowledge gap by reading the raw logged shape from the first real production void.

**D-50-02a — Rejection, not `{ ok: false }`.** `voidTransaction` REJECTS on unconfirmed. Rationale: every existing caller already has a `.catch` that persists an `sv:void-failure` record, fires `sendVoidFailureAlert`, and sets `needs_manual_review` (`routes/pos.js:1289-1299`, `lib/money-path.js:214-244`, `lib/reconcile.js:264-302`). Rejecting routes an unconfirmed void into that proven fail-closed machinery with zero caller changes. Returning `{ ok: false }` would silently take the `voidWithTimeout` "declined" branch, which logs but sends NO staff alert — a second silent failure.

**D-50-02b — The rejection message must not collide with `isAlreadyVoidedError`.** `lib/reconcile.js:147-165` treats any error whose message or response body contains `already`, `reversal`, `reversed`, or `voided` as a SUCCESS (the charge was voided by another path → clear the pending record, no alert). An unconfirmed-void error whose message contained any of those four substrings would therefore be silently swallowed by reconcile as a success — reintroducing the exact bug, in the sweep. The message text is a load-bearing contract: it MUST NOT contain `already`, `reversal`, `reversed`, or `voided`.
</locked_decisions>
