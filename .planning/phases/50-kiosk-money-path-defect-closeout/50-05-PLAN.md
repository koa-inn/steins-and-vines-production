<objective>
Two remaining money-path gaps, in two files that no other plan in this phase touches.

**M12 / roadmap SC#5 — `pos-recipe.js` has not adopted the money-path primitives.** `/api/kiosk/recipe-sale` (`routes/pos-recipe.js:295`) guards itself with a single coarse global mutex, `cache.acquireLock(C.LOCK_KEYS.RECIPE_SALE, 30)` (`:340`) — "one recipe sale at a time", which is a concurrency limiter, not an idempotency guard: a retry *after* the lock is released charges again. It calls `helcimLib.terminalPurchase(grandTotal, refNumber)` with **no idempotency key at all** (`:348`, two args), so Helcim cannot deduplicate either. And it writes **no pending-charge record**, so an orphaned recipe charge is invisible to `lib/reconcile.js`. Its confirm leg (`:484`) already uses `moneyPath.acquireIdempotencyLock` correctly, but its void path (`:831`) still calls `helcimLib.voidTransaction` raw, outside the hardened primitive (audit H5/L18).

**H3 / roadmap SC#1 — reconcile is not Zoho-authoritative.** `hasMatchingZohoOrder` (`lib/reconcile.js:93-107`) does not ask Zoho anything. It checks whether a Redis key (`kiosk:idem:confirm:<key>`, TTL **300 seconds**) is still present, and returns `false` — "treat as an orphan, void it" — whenever it is not. The code's own comment at `:67-69` names the fix: *"Future improvement: replace the age guard with an authoritative Zoho API check (GET /invoices?invoice_number=<refNumber>) so the decision is based on 'does a Zoho invoice exist?' rather than 'is the record old enough?'"*. Until then, a settled, paid sale whose pending-record deletion failed (one Redis blip at `pos.js:1244`) and whose 300s confirm key has since expired will be classified as an orphan by a late webhook or the 5-minute sweep — **and the sweep will void a charge the customer legitimately paid, against an invoice Zoho has already marked paid.**

Purpose: Closes M12 / roadmap SC#5 and audit H3 / roadmap SC#1's regression ("a settled paid charge is never voided by reconcile").
Output: A recipe money path with the same primitives as every other kiosk money path, and a reconcile sweep that asks the books before it takes money back.
</objective>

<locked_decisions>
**D-50-06 — `recipe-sale` keeps the RECIPE_SALE mutex AND gains an idempotency lock. They are not the same thing.**

The existing `C.LOCK_KEYS.RECIPE_SALE` mutex (D-04/INV-02) exists to serialise recipe sales against each other for *inventory* reasons — one scaled batch at a time so stock checks are not raced. That is a real, separate concern. Do NOT remove it. Add `moneyPath.acquireIdempotencyLock` on `C.CACHE_KEYS.KIOSK_IDEM_PREFIX + body.idempotency_key` as a distinct, *duplicate*-detection guard, acquired BEFORE the RECIPE_SALE mutex (fail fast on a duplicate without queueing behind the inventory mutex).

Client-key contract: the kiosk client already sends `idempotency_key` on `/api/kiosk/recipe-sale` (`js/kiosk-core.js` `recipeSaleBody`, and it becomes stable-per-attempt in plan 50-04). Mirror `/api/kiosk/sale`'s posture exactly (`pos.js:242-248`): the key is **required in production**, optional in non-prod for backward compatibility. Unlike `salesorder-pay` (D-50-01), no server-derived fallback is needed here, because the client has ALWAYS sent this key on this route — there is no stale-client outage risk.

**D-50-06a — the Helcim idempotency key is derived deterministically** (`crypto.createHash('sha256').update(idempotency_key).digest('hex').substring(0, 25)`), exactly as `pos.js:556-558`. `terminalPurchase(grandTotal, refNumber)` currently passes NO third argument, so Helcim mints a random key per call and cannot deduplicate. This is the same defence-in-depth line as D-50-01a.

**D-50-07 — reconcile becomes Zoho-authoritative, with the cache signals kept as a fast path.**

`hasMatchingZohoOrder(ctx)` currently answers "is a 300-second Redis key still present?" and treats its absence as proof of an orphan. Replace the decision with a three-step ladder, in order:

1. **Cache fast path (unchanged):** if the confirm idempotency key is present → settled. Cheap, no Zoho call, covers the common case within 300s.
2. **Zoho authority (new), branching on the record type (D-50-08):** otherwise, ask Zoho whether the sale was actually recorded. WHICH question to ask depends on which surface wrote the pending record — see D-50-08. A positive answer → **settled**. This is the authoritative answer the code comment at `:67-69` asks for, and it is immune to Redis TTL expiry.
3. **Fail CLOSED on an unanswerable Zoho call (changed):** if the Zoho lookup THROWS (network, auth, rate limit), return `settled = true` — i.e. **do NOT void**. This inverts the current fail-safe direction, and that inversion is the entire point of the fix.

   Today an unanswerable check resolves to `false` → "potential orphan" → **void**. The comment at `:86-87` calls this "fail-safe" on the reasoning that "staff will investigate the `sv:void-failure` record if we void incorrectly" — but that reasoning is inverted: an incorrect void takes money back from a customer who legitimately paid, against an invoice Zoho has already marked paid, and no `sv:void-failure` record is even written on a *successful* wrong void. The safe direction is: **when we cannot prove the charge is orphaned, we do not take the money back.** A genuine orphan that we decline to void remains visible — the pending record survives, the next sweep retries, and the `sv:void-failure` / manual-review path already exists for it. An orphan left standing for 5 more minutes is recoverable; a wrongly-voided paid sale is a customer-facing incident.

   Keep the existing `isOldEnough` age guard exactly as it is — it is an independent, still-useful defence, and the audit does not flag it.
**D-50-08 — the authoritative check branches on the record type, because `salesorder-pay` has no invoice `reference_number` to look up. (Blocker fix.)**

A single `zohoGet('/invoices?reference_number=' + ctx.reference_number)` lookup does NOT work uniformly. Verified against source:

- `/api/kiosk/sale/confirm` sets `reference_number: refNumber` on its invoice payload (`pos.js:881`, echoed at `:1223`). ✅ lookup works.
- `/api/kiosk/recipe-sale/confirm` sets `reference_number: body.reference` on its invoice payload (`pos-recipe.js:723`). ✅ lookup works.
- `/api/kiosk/salesorder-pay` creates its invoice with **`zohoPost('/invoices/fromsalesorder?salesorder_id=' + soId, {})` — an EMPTY body** (`pos.js:1907`). Nothing in current code, in plan 50-02, or here sets that invoice's `reference_number` to the payment reference; it inherits whatever the pre-existing SO carried (a customer PO, or blank). ❌ **the lookup returns an empty `invoices` array for a fully legitimate, fully paid sale.**

And the step-1 cache fast path cannot rescue it either: it checks `KIOSK_IDEM_PREFIX + 'confirm:' + key`, a key written ONLY by the two-phase `/confirm` flow. `salesorder-pay` is a synchronous single-call route and never writes it.

So a naive uniform invoice lookup would make every SO-pay pending record resolve to "proven empty" → which D-50-07 (correctly) classifies as a genuine orphan → **void**. The fix for "reconcile wrongly voids paying customers" would itself wrongly void paying customers, on the exact surface this phase exists to harden, triggered by the exact scenario this plan's objective names (a Redis blip failing `cache.del(pendingKey)` on the SO-pay success path).

**Chosen: verify SO-pay records against the SALES ORDER, not an invoice.**

```
if (ctx.salesorder_id)  -> zohoGet('/salesorders/' + ctx.salesorder_id)
                           settled iff  balance <= 0.01  OR  status/order_status in { paid, closed }
else                    -> zohoGet('/invoices?reference_number=' + encodeURIComponent(ctx.reference_number))
                           settled iff  invoices array is non-empty
```

`ctx.salesorder_id` is already part of the pending-charge record shape (written by plan 50-02, and by the pre-existing timeout branch at `pos.js:2003-2009`), so the discriminator needs no new plumbing.

**Why NOT the alternative — having 50-02 PATCH `reference_number` onto the fromsalesorder invoice so one lookup path serves all three surfaces?** It is unsound, not merely risky. `salesorder-pay` treats invoice-creation-from-SO as **explicitly non-fatal**: `pos.js:1919-1924` catches the failure, logs "SO is paid, but invoice creation failed", returns `''`, and responds `ok: true`. **A legitimately paid sales order can therefore have NO invoice at all, by design.** Any invoice-based lookup is structurally incapable of being authoritative for that surface — the uniformity would be cosmetic, and the failure mode (void a paid customer when the invoice leg happened to fail) is precisely the one being fixed. This holds regardless of whether Zoho permits mutating `reference_number` on a converted invoice, so that question does not need to be answered.

The sales order, by contrast, is where the money is actually applied: the customerpayment posts `salesorders_to_apply: [{ salesorder_id, amount_applied: balance }]` (`pos.js:1890`) BEFORE the invoice leg runs. The SO is the durable record of payment; the invoice is a downstream, best-effort side-effect.

**Residual risk, stated:** the SO branch reads `balance` as its settled signal. That Zoho applies a `salesorders_to_apply` customerpayment by driving `so.balance` to 0 is inferred from the route's own use of `so.balance` as the amount to charge (`pos.js:1815`) — it is NOT yet verified against the live tenant. Task 4 is a blocking live probe that confirms it before this branch is trusted. If Zoho does not reduce `so.balance` on payment application, this branch must switch to the SO's `status`/`order_status` field alone, or to a customerpayment lookup — do not ship the branch on the inference.
</locked_decisions>
