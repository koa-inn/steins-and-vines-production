# Phase 29.1: Batch Customer Reassignment - Context

**Gathered:** 2026-06-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Staff can change which customer is tied to an existing batch (e.g. swap a WALK-IN
placeholder for a real customer) from the BrewPad batch detail pane, and propagate
that customer change to the linked Zoho sales order/invoice.

This is the **inverse** of phase 29's "Refresh from Zoho" (which pulls customer data
*from* the linked SO onto the batch). Here the batch is the source of truth and the
change is pushed *to* Zoho.

**In scope:** reassigning the customer on a batch (pick existing or add new), updating
the batch's customer fields, and pushing the new customer to the linked SO/invoice.

**Out of scope:** re-linking a batch to a *different* order (that's the existing
"Change Linked Order" control), bulk reassignment across multiple batches, editing
arbitrary customer profile fields in Zoho.

</domain>

<decisions>
## Implementation Decisions

### Customer selection
- **D-01:** Staff pick the new customer via **search-or-add**: search existing Zoho
  customers by name/email/phone; if not found, enter a new customer inline
  (lookup-or-create a Zoho contact). Covers WALK-IN → real-customer whether or not
  the customer already exists in Zoho.

### Zoho propagation
- **D-02:** Reassignment updates the batch first, then asks the staff member to
  **confirm pushing** the customer change to the linked SO/invoice (sensitive write →
  explicit confirm, not silent).
- **D-03:** When the batch has **no `zoho_so_number`**, reassignment is a batch-only
  field update — no Zoho call is attempted.

### Entry point / surface
- **D-04:** Lives in the **BrewPad batch detail pane**, alongside the existing
  Refresh from Zoho / Link to Invoice controls where the customer is already shown.
  Not added to admin.html in this phase.

### Failure handling
- **D-05:** If Zoho refuses the customer change on an existing SO/invoice, the **batch
  reassignment still succeeds** (batch is source of truth for who's brewing) and a
  clear warning is shown with the reason Zoho couldn't be updated. Do NOT roll back
  the batch change. No atomic all-or-nothing behavior.

### Claude's Discretion
- Exact search UI (reuse the existing `bp-so-search` / Link-to-Invoice search styling
  vs. a dedicated customer search) — planner/researcher's call, keep it consistent
  with the existing detail-pane controls.
- Whether the new-customer inline form reuses the contact lookup-or-create path from
  checkout.js or a new Apps Script/middleware endpoint — research decides.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **Zoho contact lookup-or-create** (`checkout.js`): resolves a contact_id from
  name/email or creates one — directly reusable for both the "search existing" and
  "add new" customer paths.
- **`/api/batch/customer-by-number`** (phase 28): existing read path; the search
  side may reuse Zoho contact search infra.
- **BrewPad detail Invoice section** (`renderBatchDetail` in `js/brewpad.js`):
  established pattern for a labeled control + search dropdown + confirm, with
  optimistic-lock versioning (`expectedVersion` / `last_updated`) and toast feedback.
- **`updateBatch` (adminApi.gs)**: writes batch customer fields; `allowedFields`
  already includes customer_email/phone.

### Established Patterns
- Optimistic locking on batch writes (`expectedVersion` from `last_updated`) — the
  reassignment write must carry the current version (see WR-03/CR-02 fixes this milestone).
- Sensitive Zoho writes use confirm sheets + toast + warning-on-failure (e.g. void
  failure alerts, refresh-from-Zoho).
- Server-authoritative: the middleware/Apps Script resolves the contact, not the client.

### Integration Points
- New control in `renderBatchDetail` Invoice section.
- Likely a middleware endpoint (or Apps Script action) to: resolve/create the contact,
  update the batch row, and attempt the Zoho SO/invoice customer update.
- Cache-bust + dashboard refresh after reassignment (same pattern as activation flows).

</code_context>

<specifics>
## Specific Ideas

- The motivating case is the **WALK-IN placeholder** batch: a walk-in is recorded with
  a placeholder customer, and later staff need to attach the real customer and have the
  linked Zoho order reflect it.
- Behavior should feel consistent with "Refresh from Zoho" (same detail-pane area, same
  confirm + toast + warning vocabulary), just in the opposite direction.

</specifics>

<deferred>
## Deferred Ideas

- **Bulk reassignment** across multiple batches — out of scope; its own phase if needed.
- **Admin.html surface** for reassignment — deferred; BrewPad-only this phase.
- **Editing the Zoho customer profile** (not just which customer is attached) — out of scope.

</deferred>
