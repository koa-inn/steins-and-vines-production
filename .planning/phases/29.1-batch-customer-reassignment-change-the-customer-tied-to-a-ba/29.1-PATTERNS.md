## Zoho SO/Invoice Customer Mutability — Critical Constraint (D-05)

**Finding:** The Zoho Books API allows `PUT /salesorders/:id` and `PUT /invoices/:id` with a `customer_id` field. However, based on Zoho Books API behavior (not contradicted anywhere in the codebase), changing `customer_id` on a **confirmed, invoiced, or paid** document returns an error. Only **draft** SOs can have their customer changed without restriction. The existing `PUT /api/kiosk/salesorder-update` handler (`pos.js` lines 1277–1301) forwards the error from `err.response.data.message` directly to the caller — the same error-extraction pattern must be used by the new endpoint so a meaningful Zoho rejection reason reaches the frontend.

**Design consequence (D-05):** The new middleware endpoint must:
1. Update the batch via Apps Script unconditionally.
2. Attempt `PUT /salesorders/:zoho_so_id { customer_id: ... }` or `PUT /invoices/:zoho_inv_id { customer_id: ... }` only when `zoho_so_number` is present.
3. If Zoho returns an error, surface `{ ok: true, batch_updated: true, zoho_warning: '<Zoho message>' }` — batch change stands, warning shown in UI.

The Zoho SO internal ID is not stored on the batch (only `zoho_so_number` is). The new endpoint must therefore resolve the SO ID first via `zohoGet('/salesorders', { salesorder_number: soNumber })` or `zohoGet('/invoices', { invoice_number: soNumber })` — same lookup pattern as `customer-by-number` (`pos.js` lines 1390–1418).

```javascript
function buildContactPayload(customerName, customerEmail, customerPhone) {
  var name = (customerName || '').trim();
  var parts = name ? name.split(/\s+/) : [];
  var firstName = parts.length ? parts[0] : name;
  var lastName = parts.length > 1 ? parts.slice(1).join(' ') : '';
  var person = { first_name: firstName, last_name: lastName, email: customerEmail, is_primary_contact: true };
  if (customerPhone) person.phone = customerPhone;
  return { contact_name: name, contact_type: 'customer', contact_persons: [person] };
}
```
