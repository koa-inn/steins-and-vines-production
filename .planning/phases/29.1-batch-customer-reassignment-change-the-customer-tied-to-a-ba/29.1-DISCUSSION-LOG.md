## How staff pick the new customer

| Option | Description | Selected |
|--------|-------------|----------|
| Both: search or add new | Search existing Zoho customers by name/email/phone; if not found, enter a new customer inline (lookup-or-create) | ✓ |
| Search existing Zoho only | Pick from existing Zoho customers only; new customers must exist in Zoho first | |
| Enter new details only | Type name/email/phone; always lookup-or-create; no search UI | |

**User's choice:** Both — search existing or add new.
**Notes:** Covers the WALK-IN → real-customer case whether or not the customer is already in Zoho.

---

## Zoho propagation behavior

| Option | Description | Selected |
|--------|-------------|----------|
| Push with a confirm step; batch-only if no link | Update batch, then confirm pushing customer to linked SO/invoice; batch-only when no zoho_so_number | ✓ |
| Always auto-push | Any customer change immediately propagates to the SO/invoice, no extra confirm | |
| Batch-only by default; Zoho push separate | Reassignment changes only the batch; a separate explicit action pushes to Zoho | |

**User's choice:** Push with a confirm step; batch-only if no link.
**Notes:** Sensitive Zoho write → explicit confirm. No Zoho call when the batch has no linked order.

---

## When Zoho rejects the change

| Option | Description | Selected |
|--------|-------------|----------|
| Update batch anyway + warn | Batch reassignment succeeds (source of truth); warn that Zoho couldn't be updated, with reason | ✓ |
| Block unless Zoho succeeds (atomic) | Don't change the batch unless Zoho push also succeeds | |
| Offer a fallback | On rejection, offer relink to a different order or flag for manual fix | |

**User's choice:** Update batch anyway + warn.
**Notes:** Zoho often refuses customer changes on existing SO/invoices; blocking would make the feature frequently unusable. Batch stays the operational source of truth; the Zoho discrepancy is surfaced, not hidden.
