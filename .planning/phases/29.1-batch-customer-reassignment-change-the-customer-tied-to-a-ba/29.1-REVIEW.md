# Phase 29.1: Code Review Report

**Reviewed:** 2026-06-13
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

Reviewed the NEW/changed code for Phase 29.1 (Batch Customer Reassignment) across the
diff `c7309fbb..HEAD`:

- `zoho-middleware/routes/pos.js` — `GET /api/contacts/search` + `POST /api/batch/reassign-customer`
- `js/brewpad.js` — `buildCustomerReassignUpdates`, `fetchReassignSearch`, `submitReassign`, reassign control + inline add-customer + DOM patching
- `css/brewpad.css` — `bp-reassign-*` selectors

The core design decisions hold up: auth guards are present on both endpoints (D-04 / T-29.1-01),
the D-03 batch-only path correctly skips all Zoho document calls, the D-05 no-rollback warning
path returns HTTP 200 with `zoho_warning`, optimistic locking forwards `expectedVersion` and
returns 409 on `version_conflict`, and no email/phone PII appears in `log.*` / `eventLog` calls.
Search results are escaped with `escapeHTML` against XSS.

No Critical issues were found. However, the adversarial pass surfaced **6 Warnings** — most
notably (1) the reassign endpoint does **not** validate `zoho_so_number` format before hitting
Zoho (unlike the sibling `customer-by-number` endpoint, which does), (2) a missing guard when a
freshly-created contact has no `contact_id`, allowing `customer_id: undefined` to be written to
both the batch and Zoho, and (3) **double HTML-encoding** of the warning toast and confirm-sheet
text (both consumers use `textContent`, so the extra `escapeHTML` corrupts display for names
containing `& < >`).

## Warnings

### WR-01: `zoho_so_number` is not format-validated before the Zoho lookup

**File:** `zoho-middleware/routes/pos.js:1644-1652`
**Issue:** The reassign endpoint treats any `zoho_so_number` that does NOT match `/^INV-\d+$/`
as a sales-order number and queries `/salesorders?salesorder_number=<value>`. The sibling
`GET /api/batch/customer-by-number` (lines 1382-1388) validates `/^(INV|SO)-\d+$/` and returns
400 *before* any Zoho call. Here, a malformed value (e.g. `"FOO"`, `"DROP"`, a stray cart string)
silently issues an unnecessary Zoho query, and because no exact match is found, the path falls
through to the "document not found" branch and returns a `zoho_warning` instead of signalling the
caller that its input was invalid. Inconsistent contract between two endpoints that resolve the
same identifier, and a wasted Zoho quota hit per bad request.
**Fix:**
```js
// After: var soUpperCase = soNumber.toUpperCase();
if (!/^(INV|SO)-\d+$/.test(soUpperCase)) {
  // Treat as batch-only / surface as warning rather than guessing salesorder
  eventLog.logEvent('batch.customer_reassigned', {
    batchId: batchId, newCustomerId: contactId, newCustomerName: customerName,
    zohoUpdated: false, zohoWarning: 'Invalid order reference: ' + soNumber
  });
  return res.json({ ok: true, batch_updated: true,
    zoho_warning: 'Invalid order reference: ' + soNumber, new_version: newVersion });
}
```

### WR-02: Freshly-created contact with no `contact_id` writes `customer_id: undefined`

**File:** `zoho-middleware/routes/pos.js:1564-1568, 1593-1597`
**Issue:** In both lookup-or-create branches, the create result is read as
`return (createData.contact || {}).contact_id;`. If Zoho returns 2xx but the body lacks
`contact` or `contact.contact_id` (partial/odd response), `contactId` becomes `undefined`.
That `undefined` is then forwarded as `customer_id: undefined` into the Apps Script `update_batch`
payload (corrupting the batch's customer link) AND into `zohoPut(docPath/docId, { customer_id: undefined })`,
which can blank out or fail the linked order's customer. Unlike `version_conflict`, there is no
guard for "contact resolution produced no id." The reference `resolveCustomerId` in checkout.js
has the same latent gap, but checkout at least caches and surfaces downstream; here it writes
straight to the source-of-truth batch row.
**Fix:**
```js
return zohoPost('/contacts', payload).then(function (createData) {
  var newId = (createData.contact || {}).contact_id;
  if (!newId) { throw new Error('Contact created but no contact_id returned'); }
  return newId;
});
```
Apply to both the email-search create and the name-only create branches. The thrown error will
land in the outer `.catch` → 500, which is correct (no batch write should occur without a real id).

### WR-03: Double HTML-encoding of `zoho_warning` toast text

**File:** `js/brewpad.js:957`
**Issue:** `showToast('Customer saved — Zoho not updated: ' + escapeHTML(data.zoho_warning), 'warn')`.
`showToast` (line 364-383) assigns the message via `msgSpan.textContent = message` — it does NOT
parse HTML. Passing pre-escaped text means a Zoho message containing `&`, `<`, or `>` renders to
staff with literal entities, e.g. `R&D Wines` becomes `R&amp;D Wines`. The `escapeHTML` here is
both unnecessary (textContent is already XSS-safe) and actively corrupts the displayed message.
**Fix:**
```js
showToast('Customer saved — Zoho not updated: ' + data.zoho_warning, 'warn');
```

### WR-04: Double HTML-encoding in the confirm-sheet message

**File:** `js/brewpad.js:1023-1026`
**Issue:** The confirm message is built with `escapeHTML(batchId)` and `escapeHTML(displayName)`,
but `showConfirmSheet` (line 2016) renders it via
`document.getElementById('bp-confirm-sheet-msg').textContent = message`. Same double-encoding bug
as WR-03: a customer named `Bed & Breakfast` shows in the confirm dialog as `Bed &amp; Breakfast`,
which could mislead staff about exactly who they are reassigning to. `textContent` is already
XSS-safe, so the escaping is wrong here.
**Fix:**
```js
showConfirmSheet(
  'Reassign batch ' + batchId + ' to ' + displayName + '? This will also update the linked Zoho order.',
  'Confirm', '', doPost
);
```

### WR-05: Whitespace-only `customer.name` passes validation and creates an empty-named contact

**File:** `zoho-middleware/routes/pos.js:1516-1518`
**Issue:** The guard is `if (!customer.name && !customer.contact_id)`. A name of `"   "` (spaces)
is truthy, so it passes the 400 check. Downstream, `custName = (customer.name || '').trim()`
becomes `''`, `buildContactPayload('', ...)` builds a contact with `contact_name: ''`, and a name
search with `contact_name: ''` may match an arbitrary contact or create a blank-named Zoho contact.
The intent of the validation (require a real name OR a contact_id) is defeated by whitespace input.
**Fix:**
```js
var trimmedName = (customer.name || '').trim();
if (!trimmedName && !customer.contact_id) {
  return res.status(400).json({ error: 'Missing customer: provide name or contact_id' });
}
```

### WR-06: `expectedVersion` can be sent as empty string, weakening the optimistic lock

**File:** `js/brewpad.js:887` (and forwarded at `pos.js:1610`)
**Issue:** `submitReassign` computes `expectedVersion = batchDetail.last_updated || ''`. If
`last_updated` is missing (legacy batch, or a detail object that never carried the field), the
frontend POSTs `expectedVersion: ''`. The middleware forwards it verbatim to Apps Script
`update_batch`. Depending on how `updateBatch` compares `expectedVersion` against the stored
`last_updated`, an empty `expectedVersion` may either (a) be treated as "no version supplied" and
skip the conflict check entirely, or (b) always mismatch. Either way the optimistic-lock guarantee
(T-29.1-02 / T-29.1-07) silently degrades for any batch lacking a `last_updated`. At minimum the
client should refuse to submit without a concrete version, or the contract should be documented.
**Fix:** Block submission when no version is known, e.g.:
```js
if (!expectedVersion) {
  showToast('Cannot reassign — batch version unknown, reload first', 'error');
  return;
}
```
And/or have the middleware reject a falsy `expectedVersion` with 400.

## Info

### IN-01: Duplicated contact name-split logic instead of reusing `buildContactPayload`

**File:** `zoho-middleware/routes/pos.js:1525-1530, 1538-1540`
**Issue:** The first/last split (`name.split(/\s+/)`, `parts[0]`, `parts.slice(1).join(' ')`) is
re-implemented inline in two places, duplicating the exact logic already inside
`buildContactPayload` (checkout-helpers.js:209-212) and the frontend `splitCustomerName`. If the
split rule ever changes (e.g. handling of suffixes), these copies drift.
**Fix:** Extract a shared `splitName(fullName)` helper in `checkout-helpers.js` and import it in
both `buildContactPayload` and `pos.js`.

### IN-02: `submitReassign` reads `_currentBatchDetail` lazily — possible cross-batch mismatch

**File:** `js/brewpad.js:881-889`
**Issue:** `_pendingReassign` is captured on result-click / add-new-save, but `submitReassign`
reads `_currentBatchDetail` for `batch_id`/`zoho_so_number`/`expectedVersion` at submit time. The
flow is effectively synchronous today (click → submit), so this is currently safe, but if a future
async step (e.g. an extra confirm) is inserted and the user navigates to another batch in between,
the pending customer would be applied to the wrong batch. Consider snapshotting `batchId`/`soNumber`
alongside `_pendingReassign` when it is set.
**Fix:** Store `{ batchId, soNumber, expectedVersion, picked }` together in `_pendingReassign`.

### IN-03: Reassign panel state not reset when `renderBatchDetail` re-renders mid-flow

**File:** `js/brewpad.js:847-848, 1057-1063`
**Issue:** `_pendingReassign` and `_reassignSearchTimer` are module-level. If the detail pane is
re-rendered (e.g. a Zoho refresh or list reload) while a reassign panel is open, a stale
`_pendingReassign` can linger and a dangling `_reassignSearchTimer` may fire `fetchReassignSearch`
against a results element that was replaced. Low impact (the new DOM has fresh ids and the timer's
target lookup is null-guarded), but worth clearing on re-render.
**Fix:** In `renderBatchDetail`, `clearTimeout(_reassignSearchTimer); _pendingReassign = null;`
before re-wiring controls.

### IN-04: `.bp-reassign-results` z-index 100 may sit under sticky/overlay layers

**File:** `css/brewpad.css:1995-2003`
**Issue:** The results dropdown uses `z-index: 100`. Per project memory, the BrewPad/admin sticky
header and search overlays use much higher z-indices (header ~200, overlays 1290+). If the reassign
results overlap any sticky element in the detail pane, they could be obscured. Not a functional
bug, but verify stacking against the detail pane's own layering.
**Fix:** Confirm the results render within the detail pane's stacking context; bump z-index if it
overlaps sticky chrome.
