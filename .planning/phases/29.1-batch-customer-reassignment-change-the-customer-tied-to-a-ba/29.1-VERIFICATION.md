### Human Verification Required

#### 1. Warning toast with HTML entities in Zoho message (WR-03)

**Test:** Stage a scenario where the Zoho PUT rejection message contains an ampersand (e.g., link a batch to an invoice for "R&D Wines" and trigger a customer change rejection). Alternatively, inject a mock zoho_warning with `&` via a network interception tool.
**Expected:** The warn toast should display the raw text as-is. Currently `escapeHTML(data.zoho_warning)` is called before passing to `showToast`, which internally uses `textContent`. This double-encodes entities: `R&D Wines` becomes `R&amp;D Wines` in the toast.
**Why human:** Requires browser session with real or mocked Zoho rejection response containing HTML special characters.

#### 2. Confirm sheet customer name with HTML entities (WR-04)

**Test:** Open a batch with a linked order, click Change Customer, search for and select a customer whose name contains `&` (e.g., "Bed & Breakfast"). Observe the confirm sheet modal.
**Expected:** The confirm message should read "Reassign batch SV-B-000001 to Bed & Breakfast? ..." with a literal ampersand. Currently, `escapeHTML(displayName)` is passed to `showConfirmSheet`, which sets `textContent`. The double-encoding would show `Bed &amp; Breakfast` instead.
**Why human:** Visual confirmation in browser is the only way to validate textContent rendering of pre-escaped strings.

#### 3. D-03 batch-only UX path (no linked SO)

**Test:** Open a batch in BrewPad that has no `zoho_so_number`. Click Change Customer, type a search term, pick a result from the dropdown.
**Expected:** The reassignment saves immediately with NO confirm sheet dialog. A success toast appears. The Customer/Email/Phone rows update in place. Middleware logs should show no zohoGet/zohoPut calls.
**Why human:** The no-confirm path is code-verified but the full UX flow (panel closes, toast fires, DOM patches, no dialog) needs staging confirmation.

#### 4. D-05 Zoho rejection warning flow (linked SO, locked state)

**Test:** Open a batch with a linked Zoho SO that is in confirmed/invoiced state. Click Change Customer, pick a different customer, confirm in the dialog.
**Expected:** A `warn` (yellow) toast appears: "Customer saved — Zoho not updated: [Zoho rejection reason]". The batch detail rows (Customer, Email, Phone) already show the NEW customer — not rolled back to the old one. The Zoho SO/invoice still has the old customer.
**Why human:** Requires a real or test Zoho SO in locked state to trigger the rejection; the D-05 warning path cannot be exercised in the automated test suite against production Zoho.
