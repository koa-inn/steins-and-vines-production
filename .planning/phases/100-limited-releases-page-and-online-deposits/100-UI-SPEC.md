### Where new CSS goes (recommendation)

Add a new file `css/limited-releases.css` and register it in the `minify:css` script in `package.json` as `cleancss -o css/limited-releases.min.css css/limited-releases.css` (the same pattern as `catalog-subpage.css`). Link `css/limited-releases.min.css?v=` after `styles.min.css` in the page only. Reason: `styles.css` is already ~7.7k lines and loaded by every page; this page's rules (stepper, sticky bar, kit cards, calendar, confirmation) are page-scoped. All selectors are prefixed `.lr-` (e.g. `.lr-kit`, `.lr-stepper`, `.lr-bar`) so nothing leaks. No new custom properties on `:root`; reuse the existing tokens listed below. The one page-scoped custom property, `--lr-bar-h` (measured sticky-bar height), is set on the `.lr-` page scope, not `:root`. Add the file to `stamp:pages` handling if that script stamps CSS links (check when planning).

### Collection sections

Each collection section contains, in order:
- Header strip (green): `logo.light` image (height 48px, width auto, from JSON dims 700x302 / 700x441 so set `width`/`height` attributes and constrain with CSS height), collection `name` as h2, `theme` as an italic-free Label line, `blurb` as Body. Stacked on mobile; logo left and text right at >= 768px.
- Hero image: `hero_image` full container width, `border-radius: var(--radius-sm)`, `width`/`height` attributes from table below. NO text, badge, gradient, or button is placed over either hero (LE26 has baked-in text and logo; for consistency and the planned guard test, RQ27 gets the same treatment). The first hero on the page (LE26 hero, if it is collection 1) is eager (`loading` omitted, `fetchpriority="high"`); all other images `loading="lazy"`; all `decoding="async"`.
- Brochure link: `.btn-secondary` with `download` attribute, text "Brochure (PDF, 0.6 MB)" for LE26 and "Brochure (PDF, 0.7 MB)" for RQ27 (sizes: 598,938 and 702,266 bytes, rounded to 1 decimal MB; compute at render from a constant, not the filesystem).

Ordering: collections render in JSON `collections` order (LE26 then RQ27). Inside each collection kits render in ascending `release` order (LE26: Dec, Jan, Feb, Mar, Apr; RQ27: Nov, Jan, Feb, Mar, Apr). The combined chronological view (all ten, Nov to Apr) is the release calendar, which is the one place the two collections interleave. Planner note: the handoff test "renders all ten kits in release order" must be asserted per collection (DOM order within each section) plus the calendar order, since the grouped layout means a single flat DOM order of cards is not chronological across collections.

### Quantity stepper (`.lr-stepper`)

- Structure: a `<div role="group" aria-label="Quantity for {short_name}">` containing `<button type="button" aria-label="Remove one {short_name}">` ("-" as a text glyph U+2212), an `<output class="lr-qty" aria-live="off">` showing the number, and `<button type="button" aria-label="Add one {short_name}">` ("+" glyph).
- Buttons 44x44px, `--radius-sm`, 2px burgundy border, cream background and burgundy glyph (Label weight 700, 20px glyph via Heading size); when qty >= 1 the "+" fill flips to burgundy with cream glyph. Count is 44px wide, centred, Body size (16px) at weight 700.

- Press feedback: the existing `:active` opacity 0.85 pattern. No animation beyond a 0.2s colour transition; wrap any transition in the existing `prefers-reduced-motion` convention (no motion required).

### Sticky bottom bar (`.lr-bar`, D-10)

- Visible only on < 768px, only while total kits >= 1, only while the reservation panel is NOT in the viewport (IntersectionObserver on `#lr-reserve`; ES5 code with a graceful fallback of always-visible when IntersectionObserver is unavailable), and not while the payment iframe is open or after confirmation.
- Position: `position: fixed; left: 0; right: 0; bottom: 0; z-index: 1000` (below the cookie notice at 1100, above content; the header is 200 and the search overlay is higher). Background `--color-green`, text `--color-cream`, 16px padding plus `padding-bottom: calc(16px + env(safe-area-inset-bottom, 0px))`. Content: left text "{N} kit(s) · ${X} deposit" (Label 14/700, with a middle dot separator as in the context decision) and right a button "Reserve" (cream background, burgundy text, 44px min height, `--radius-sm`) which scrolls to `#lr-reserve` (`scrollIntoView`, honouring `prefers-reduced-motion` by using auto behaviour) and moves focus to the reservation h2 (`tabindex="-1"`).

## Payment States (HelcimPay flow, mirrors `12-checkout.js` / `reservation.html`)

State machine for the form panel. The pay button text and a single status line (`#lr-pay-status`, `role="status"`, below the button) change per state. While any state other than "ready" or "error" is active, all steppers, "Remove" buttons, fields and checkboxes are `disabled` so the basket cannot change after the amount is fixed. Hide the sticky bar in these states.

| State | Trigger | Button | Status line / UI |
|-------|---------|--------|------------------|
| ready | page load; or kits >= 1 and consent ticked | "Pay $X deposit", enabled | none |
| blocked | kits = 0 or consent unticked | "Pay deposit" or "Pay $X deposit", disabled | `#lr-pay-hint` text |
| starting | click; reCAPTCHA token acquired and `/api/payment/initialize` called for 50 x kits | "Opening secure payment..." disabled, `.btn-loading` | "Preparing your payment." |
| iframe open | HelcimPay iframe shown | disabled, label "Secure payment open" | "Complete your payment in the secure window. We never see your card number." Provide a "Close secure payment" `.btn-secondary` to close the iframe (see below) |
| verifying | Helcim returns approval; `POST /api/preorder/deposit` in flight | "Confirming your reservation..." disabled | "Payment approved. Please keep this page open while we confirm your reservation. Do not pay again." Show a spinner (existing spinner component if present, else a CSS-only 20px ring; hidden under reduced motion in favour of text only) |
| success | server returns ok | form replaced by confirmation (below) | focus to confirmation heading |
| cancelled | user closes iframe / Helcim reports cancel | returns to ready | `role="status"`: "Payment cancelled. You have not been charged." (honest only because the card was never submitted) |
| declined | Helcim reports decline | returns to ready | `role="alert"` under button: "Your card was declined. You have not been charged. Please try a different card or contact your bank." |
| rejected after capture, void succeeded | server returns an error with a flag that the void succeeded | returns to ready (basket preserved) | `role="alert"`: "We could not complete your reservation, and your card has not been charged. Please try again, or call us at (604) 567-4565." Show only when the server response explicitly confirms the void succeeded |
| rejected after capture, void failed or unknown | any server error/timeout/network loss after approval where voided is not confirmed | stays disabled (prevents double charge); show a "Call us" `.btn` `tel:+16045674565` | `role="alert"`: "Your payment went through but we could not confirm your reservation here. Please do not pay again. Call us at (604) 567-4565 or email us and we will sort it out." Include the Helcim transaction reference if the client has it. NEVER say "not charged" in this state |
| reCAPTCHA / validation rejected before capture | 400 from initialize or client validation | ready | field-level errors, or "We could not verify your request. Please try again." |
| network failure before payment | initialize fails | ready | `role="alert"`: "We could not reach the payment service. You have not been charged. Please try again." |
| already processed (idempotent retry) | server indicates this transaction was already booked | success | show the original confirmation |

Copy rule: the words "not charged" or "has not been charged" appear only in states where the client knows no capture happened (cancelled, declined, network failure before initialize, server-confirmed void). The server contract needs a distinguishable response for "voided" vs "unknown"; planner should add a boolean (for example `voided: true`) to the error JSON and tests for both copy branches.

Duplicate-click protection: set a `submitting` flag at click; ignore further clicks until a terminal state.

Leaving the page: while in "iframe open" or "verifying", register a `beforeunload` prompt.
