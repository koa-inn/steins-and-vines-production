Per RDM-03: Each batch created from a recipe sale stores a full ingredient snapshot at time of sale, immune to future recipe edits. The `recipe_id` and `recipe_snapshot` columns must exist in the Batches sheet BEFORE any recipe sale occurs.

**1. Modify `createBatch()` in adminApi.gs** to write `recipe_id` and `recipe_snapshot` using header-lookup AFTER the existing `appendRow` call (do NOT change the appendRow positional arguments -- use header-lookup to avoid positional coupling).

Locate the existing `appendRow` call in createBatch (around lines 1703-1728). AFTER the appendRow but BEFORE the function returns, add:

```javascript
// Write recipe_id / recipe_snapshot by header lookup (avoids positional coupling)
if (payload.recipe_id || payload.recipe_snapshot) {
  var bHeaders = batchesSheet.getRange(1, 1, 1, batchesSheet.getLastColumn()).getValues()[0];
  var newRow = batchesSheet.getLastRow();
  var recipeIdCol = bHeaders.indexOf('recipe_id');
  var snapshotCol = bHeaders.indexOf('recipe_snapshot');
  if (recipeIdCol !== -1 && payload.recipe_id) {
    batchesSheet.getRange(newRow, recipeIdCol + 1).setValue(sanitizeInput(payload.recipe_id));
  }
  if (snapshotCol !== -1 && payload.recipe_snapshot) {
    batchesSheet.getRange(newRow, snapshotCol + 1).setValue(payload.recipe_snapshot);
  }
}
```

Note: `recipe_snapshot` is intentionally NOT passed through `sanitizeInput()` because it is a JSON string that may contain characters that sanitization would strip. It is server-generated (serialized by middleware at sale time), never user-supplied directly.

Since `sheetToObjects()` reads all columns, these fields will be included automatically once the sheet headers exist. No code change needed in getBatchDetail -- just verify that `sheetToObjects(BATCHES_SHEET_NAME)` will pick up the new columns.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-07 | Tampering | BEER_SALES_ENABLED bypass | mitigate | Feature flag checked server-side in middleware with `process.env.BEER_SALES_ENABLED !== 'true'` pattern (same as INVENTORY_LEDGER_ENABLED). UI-only hiding is insufficient -- server rejects recipe sale requests when flag is false. Implemented in Phase 14 kiosk confirm endpoint. |
| T-12-08 | Information Disclosure | recipe_snapshot in Batches sheet | accept | Recipe snapshots contain ingredient names, quantities, and Zoho item IDs. This is operational data visible to staff in Google Sheets. No customer PII is in the snapshot. Low risk. |
| T-12-09 | Tampering | recipe_snapshot integrity | mitigate | recipe_snapshot is serialized server-side by middleware at sale time. It is not passed through sanitizeInput (which would corrupt JSON). The Apps Script createBatch writes it directly from the trusted middleware payload via server_token auth. Client code never supplies recipe_snapshot. |
| T-12-10 | Denial of Service | CACHE_KEYS.RECIPES Redis key | accept | Redis key `sv:recipes` follows existing cache patterns with TTL. No additional risk beyond what exists for `zoho:products`. Standard Redis eviction handles memory. |
</threat_model>
