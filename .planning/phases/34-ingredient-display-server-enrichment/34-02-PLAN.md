Output: enrichment inside recipes.js GET /api/recipes/:id, plus middleware Jest cases.

<!-- CRITICAL DATA-SHAPE FINDING from PATTERNS.md -->
cf_type IS top-level on each cached ingredient entry (entry.cf_type).
cf_subcategory is NOT top-level — it lives inside entry.custom_fields[] as the object whose
api_name === 'cf_subcategory' (use .value_formatted || .value). Mirror the Millable flatten
idiom in catalog.js L551-556.

readCF accessor to add (PATTERNS critical finding):
  function readCF(entry, apiName) {
    var cfs = (entry && entry.custom_fields) || [];
    for (var i = 0; i < cfs.length; i++) {
      if (cfs[i] && cfs[i].api_name === apiName) return cfs[i].value_formatted || cfs[i].value || '';
    }
    return '';
  }

GATE constraint: enrichWithComputedPrice (recipes.js L75) early-returns when

locked-price recipes get no cf fields. Add a SEPARATE always-run enrichment pass in the
GET /api/recipes/:id handler (L237/L240) over result.ingredients / cached.ingredients.

Existing catalog-match + cold-cache fallback pattern: recipes.js L77-90 (map build),

add a new catalog fetch.

D-08 constraint (verified against pos-recipe.js L66-88, L203-225): both money paths iterate
the flat ingredients array by item_id reading specific fields. Adding keys is safe;
