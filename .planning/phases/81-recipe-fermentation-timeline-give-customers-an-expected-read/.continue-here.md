# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each was discovered through failure this session.

- [ ] CONSTRAINT: **Staging/production share ONE Google Sheet and ONE Apps Script deployment.** There is no rehearsal environment for recipe data. Any write through the staging admin UI is a live production write. Mitigation: read the current value first, assert it matches what you expect, and record the verbatim original before writing.
- [ ] CONSTRAINT: **A save toast is the only signal a write failed.** `adminApiPost` does not throw; the UI shows "Could not save recipe. Please try again." and the precise reason is only in the HTTP 422 body. Mitigation: never infer success from absence of an error — capture the PUT response (`{"ok":true}`) or re-read at the source.
- [ ] CONSTRAINT: **A running page does not reload itself after a deploy.** Mitigation: after pushing a frontend fix, assert the *executing* bundle via `performance.getEntriesByType('resource')`, not just the published file on the server.

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| False-success reporting | Reported a recipe save as successful by reading back the value I had just typed into the form, without checking the save actually persisted. The save had failed with HTTP 422. | blocking | Capture the PUT response body and require `{"ok":true}`, or re-read from the Sheet/API. Never treat "no exception" as "saved". |
| Verifying the server instead of the page | Polled the deployed asset, saw the new build, declared staging ready — but the open page was still executing the previous bundle, producing a false "fix didn't work". | blocking | Assert the executing bundle (`performance.getEntriesByType('resource')` or the `<script src>` stamp) before any browser verification of a frontend change. |
| Generalising from a subset | Called Czech Lager "the model to standardise on" after seeing only the 3 active recipes; with all 10 visible, 6 already shared a *different* house pattern. Also initially framed all four `kg` lactic-acid rows as "~20% light" before testing them individually — two were already correct and converting them would have double-converted an active recipe. | blocking | Pull the complete set before proposing a normalisation. For numeric conversions, apply a plausibility test per row (divide by the factor; does it yield a figure a human would measure?) rather than one blanket rule. |
| Batching browser steps past the CDP limit | `javascript_tool` calls exceeding ~45s time out mid-operation, leaving work half-applied and reporting failure for work that partly succeeded. | advisory | Keep each browser call under ~40s. One recipe edit or one save per call; verify at the source afterwards. |
| Autocomplete bound to `mousedown` | `.ing-autocomplete-drop` options ignore `.click()`. | advisory | Dispatch `new MouseEvent('mousedown', {bubbles:true})`. |

<blockers>

- **NEW, UNRESOLVED — admin recipe editor shows 1000× costs for any ingredient whose recipe unit
  differs from its catalog unit.** `js/admin.js:9017` (`renderIngredientRows`) and `js/admin.js:9191`
  (`updateIngredientTotals`) both compute `qty * rate` with **no unit conversion**. `qty` is in the
  recipe's unit (`g`), `rate` is per the catalog's unit (`kg`).
  - West Coast IPA editor shows **Totals $6,059.66 / $13,809.97** for a recipe that sells for $93.73.
  - Correct math: $23.32 cost / $43.75 retail → +$45 service +$5 materials = **$93.75 vs $93.73
    actually charged** (2¢ rounding). **The middleware converts correctly — customers are NOT
    overcharged. This is display-only.**
  - Affects the 20 hop rows stored in `g` (7 recipes) plus gypsum/calcium chloride. Grain is `kg`
    in both places, so grain rows look right — which is why it passes a glance.
  - Same defect *class* as the Phase 73 pricing bug, in a layer Phase 73 did not cover. There is no
    unit-conversion helper anywhere in `js/admin.js` or `js/lib/`.
  - **Recommendation: fix the code, leave the data.** Normalising all hops to `kg` would make the
    editor *appear* correct while hiding the bug.
  - **Nothing was changed for this.** Needs its own plan + regression test.

- **Apps Script deployment config drift (pre-existing, unresolved).** Live deployment is
  `Execute as: Me (hello@steinsandvines.ca)` + `Who has access: Anyone`, but `docs/APPS_SCRIPT.md`
  and `adminApi.gs`'s own header both say it MUST be `User accessing the web app` +
  `Anyone with Google Account`. Consequence: `Session.getActiveUser().getEmail()` returns empty, so
  that limb of `checkAuthorization` is **dead code in production**. NOT an open endpoint — the
  OAuth-token path and server-token bypass both work. Documentary/latent risk. Deliberately untouched.

- **D-04 positive leg unverifiable.** No batch carries a `recipe_id` with a schedule attached; the

  create-batch modal has no recipe identity at all, D-04 is verified in its negative case only.
  Recorded as OPEN in `81-VERIFICATION.md` `human_verification`.

- **Admin swallows `unit_mismatch`.** The middleware returns a precise, actionable 422

  Please try again" — which invites retrying, and retrying can never work. Compounded by the unit
  being rendered as plain text (`<td class="ing-unit">`), not an input: the only way to change it is
  to re-pick the ingredient from the autocomplete, which silently resyncs the unit from the catalog.
  No affordance tells staff this.
