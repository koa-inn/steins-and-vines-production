## Critical Anti-Patterns (do NOT repeat these)

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Green tests ≠ working system | `fda6e40` (quantity-aware batch creation, 2026-07-08) had NEVER worked in prod. Its tests passed; the logic that defeated it lived in `apps-script/adminApi.gs` — which CI does not deploy and Jest cannot reach. Only caught by attempting a real write against the live system. | blocking | For any change whose behaviour crosses into Apps Script, exercise it end-to-end against the live system before declaring it fixed. Never infer deployed behaviour from a passing suite. |
| `curl` against production lies | `steinsandvines.ca` is behind Cloudflare and returns a **403 bot-challenge page** to curl. Grepping that body made me conclude prod had NO GTM snippet and NO Metricool CSP — both were in fact live. | blocking | Verify production HTML **through the browser** (claude-in-chrome), never curl. Staging is not behind Cloudflare and does answer curl. |
| Apps Script needs a MANUAL redeploy | `apps-script/*.gs` is not deployed by CI. A `.gs` change is inert until the owner redeploys from the editor. This gated both the batch fix and the kit registry this session. | advisory | When touching a `.gs` file, state the redeploy requirement in the commit body and flag it to the owner as a human action. |
| Test fixtures can contradict reality | The existing INV-000137 test gave the Makers Fee `quantity: 1` beside a kit `quantity: 3` — a shape that has never existed (the real invoice has fee ×3). It nearly drove a wrong design. | advisory | When a fixture and a fix disagree, check the fixture against real data (Zoho MCP) first. Get explicit approval before editing an existing test (CLAUDE.md rule 10). |
| Jest `mockClear()` leaks one-shot mocks | It does NOT drain queued `mockImplementationOnce` impls, so failing RED tests leaked pending mocks into later tests and produced bogus failures. | advisory | Use `mockReset()` + re-establish a default implementation in `beforeEach`. |

  fermentation slot — verified back to INV-000001 (Feb 2026: kit ×3, fee ×3). It caps every path,
  so the batch count can never exceed what was paid for.

  Tagging 516 Zoho items was considered and rejected: the sheet already IS a maintained registry
  (115 SKUs, 8 brands, stock/pricing/batch sizes; the admin panel reads it).
- **The registry may only NARROW candidates, never fall closed to zero.** A kit added to Zoho but
  not yet in the sheet must still get its batch; silently losing one is worse than mislabelling one.
- **`unit_total`, not a `unit_index` column.** `createBatch`'s `appendRow` is positional, so a new
  column would mean a live sheet-schema migration. Counting existing rows needs no schema change
  and stays retry-safe (once `unit_total` rows exist, further creates are duplicates again).
- **Registry cached in module scope, refreshed hourly** — `createBatchesFromSale` is
  fire-and-forget and must stay synchronous, or existing tests (which assert axios calls
  synchronously) would break.
- **Backfilled INV-000137 only.** An audit found 9 pre-fix invoices / 16 missing batches, but
  backfilling Feb–May orders would create phantom "ready to start" work for wine long since made.
